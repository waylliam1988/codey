# 修订工具按需展示：生产接入、实机复测与失败测试修复

日期：2026-11-03。实验起点：`c00f6551`。

**查资料时，先少展示一个暂时用不上的大工具；要修改时再展开。** 已接入生产代码并完成验证，随本报告提交。没有删除修改旧知识的能力。

最终一轮生产入口实机比较中，查旧资料的总输入 **130,250 → 90,034，减少 30.88%**，请求 **29 → 22**。两组各 6 次查询均保存答案，事前列出的版本、完整 OR 条件、原始引用等核心项目均为 **6/6**。真正修改旧对象仍各 **0/4**，没有把“新建替代对象”算成修订成功。

**不能说“答案完全没有退化”。** 更严格地检查整篇正文，查询组原版 **5/6**、新版 **4/6**；新版两个冲突核查回答对旧主张的转述不准确，其中 seed 122 是原版完整通过、新版仅核心项目通过的配对。原始证据的版本、OR 和完整条件答对，不会自动抵消这项内容问题。这里交付的是查询成本优化，不是研究正确率提升；全部正文、失败和评分分开保留。

## 1. 为什么继续接入

此前 36 次 A/B 的原门槛要求真实修订任务两组也必须成功。两组均 0/6，所以当时按原门槛暂缓，这个历史判断没有改写。

随后用户明确要求：原版修订本来不可靠，双方仍失败不应阻止查资料时的节省。于是另立生产复测门槛：允许已有修订失败继续失败，仍检查原版通过的配对是否丢失事前核心要求、工具能否展开、引用/权限/旧历史是否完整、费用与请求是否降低。**不是把旧实验的失败门槛事后改成通过。**

本次按这个较窄门槛判断成本接入。上面的逐句内容问题仍是实际风险，不能把“核心门槛通过”解释成“内容无损”。

## 2. 生产代码做什么

1. 普通整篇 Research 开始时，用小入口 `prepare_knowledge_revision` 代替完整 `knowledge_commit` 参数说明。
2. 模型确实要修改时，调用小入口。程序检查当前任务、权限和控制限制；这一步不写知识。
3. 准备结果正式结算后，下一轮恢复原来完整的 `knowledge_commit`。旧快照不会因此获得新权限。
4. **如果实际 `knowledge_read` 失败，后续恢复原完整工具和原修订指导。** 出错后的恢复上下文采用原方式，顺利查资料时才继续少展示。
5. 重启从原结算回执恢复；准备步骤在执行前中断，也可以按原空参数安全重放。

这里没有用问题关键词猜测“是否允许修改”。明确指定工具集的任务、其他任务类型、身份、版本、访问范围、引用和发布检查继续走原规则。历史长说明、操作历史、通用研究指导和知识保存通道没有同时删减。

主要位置：

- `codey/research/revision_tools.py`：展示选择、无写入准备、失败读取后的原上下文恢复。
- `codey/operations/kernel_protocol.py`、`codey/research/answer_context.py`：接入实际快照和请求指导。
- `codey/operations/task_execution.py`：原执行委托处理准备工具。
- `codey/runtime/effects/`、`codey/runtime/core/operation_reducer.py`：原回执与安全重放链。

## 3. 实机阶段，不能混在一起算

模型为后台 KoboldCpp 的 `koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，使用实际 Headless Research、原工具执行器、知识数据库与发布事务。固定 SQLite WAL 原文、长历史说明、预算和参数；各阶段首次生成前冻结源码和输入，同一时间只运行一个模型任务。

| 阶段 | 数量 | 结论 |
|---|---:|---|
| 原候选 A/B，seed 101–103 | 36 | 查询输入 −32.78%；两组修订各 0/6；原门槛未通过，历史结论保留 |
| 生产 v1，seed 111、112 | 24 | 查询输入 −26.72%，但错误读取恢复题 seed 112 原版成功、新版失败；未直接交付该版 |
| v2 定点回归，seed 112 | 2 | 针对上一行失败，原版和新版均正确完成，各 3 次请求 |
| 生产 v2，新 seed 121、122 | 24 | 最终独立比较；事前核心门槛通过，仍有逐句内容问题 |

这项工具研究合计 **86 次**，其中接入后的复测及定点诊断 **50 次**。各阶段独立报告，不把失败的 v1 隐藏，也不把定点重跑当作新的独立效果样本。此前说明长度的 24 次和全流程审查的 108 次不混入这些数字。

v1 失败不是“原版也失败”：`history_error-112-production` 先后填错读取参数和目标，重复读取后止损；同 seed 原版正确交付。因此增加了第 2 节的失败读取恢复策略，再使用新 seed 比较。定点复跑只是确认已发现的失败能否恢复。

## 4. 最终 24 次生产入口复测

每组 12 次，包含普通历史查询、错误 ID 后恢复、冲突核查、明确修订、核查后修订、首次研究并保存新候选，共六种情况，各两个 seed。原版对照只恢复原完整工具和原修订指导；新版使用已接入的生产实现，没有实验替换。

| 指标 | 原版对照 | 生产新版 |
|---|---:|---:|
| 运行数 | 12 | 12 |
| 正式保存答案 | 9 | 10 |
| 事前核心要求全部通过 | 8 | 8 |
| 进一步排除附加内容错误后全部通过 | 7 | 6 |
| 模型请求 | 65 | 52 |
| 总输入 token | 272,215 | 200,309 |
| 总输出 token | 6,934 | 5,870 |
| 输入加输出 | 279,149 | 206,179 |
| 各任务耗时相加 | 447.76 秒 | 382.12 秒 |

全组总输入减少 **26.42%**，输入加输出减少 **26.14%**。这些包含未完成的修订任务，不能解释成“每份正确研究都省这么多”。

只看三类查询，每组各 6 次：

| 指标 | 原版对照 | 生产新版 |
|---|---:|---:|
| 正式答案 | 6 | 6 |
| 事前核心要求通过 | 6 | 6 |
| 整篇附加内容检查也通过 | 5 | 4 |
| 请求 | 29 | 22 |
| 输入 | 130,250 | 90,034 |
| 输出 | 3,654 | 3,905 |
| 输入加输出 | 133,904 | 93,939 |

查询输入减少 **30.88%**，输入加输出减少 **29.85%**。两个 seed 组的查询输入均减少：seed 121 为 **66,714 → 44,062**；seed 122 为 **63,536 → 45,972**。

节省不是每种任务都成立。错误 ID 恢复题恢复完整工具后，原版各 3 次请求，新版各 4 次；该小组输入增加。普通历史查询和冲突核查的请求下降，才使查询合计节省。不能只报表现最好的子组。

### 内容检查中发现什么

- `conflict-121-full_control`：核心原文答案正确，但把旧主张说成未列条件，严格正文检查不通过。
- `conflict-121-production`：核心原文答案正确，但给旧主张安上不同的条件，并出现“互斥或可选”的无依据表述，严格正文检查不通过。
- `conflict-122-full_control`：原文纠错及旧主张转述均通过。
- `conflict-122-production`：原文版本、OR 和完整条件正确，但错误地说旧主张缺失三项条件，严格正文检查不通过。
- `history_error-122-production`：来源列表重复，属于格式问题；未改变绑定或原文条件，不据此判为语义失败。

这些检查由本助手阅读已保存正文、原文、调用轨迹及数据库完成，不是被测模型自评，也不是盲评。两个 seed 不能证明总体正确率稳定不变。

### 修订与首次积累

真正修订两组仍各 **0/4**：明确修订题反复使用错误的 `expected_revision` 等参数；部分核查后修订题虽然保存了正确答案，却新建了候选，没有修改指定旧对象。两组的旧对象和历史版本均未被改坏。

新版四个编辑任务都能看到原来完整的提交工具，参数定义与对照相同。**“能展开工具”与“模型能正确修订”分开计分。**

首次积累两组各 **2/2**：答案核心条件正确，恰好新增一条匹配指定事实的 candidate claim，引用原始证据。没有把候选保存成功当成独立语义验证。

## 5. 遇到测试失败后具体修了什么

之前“1,786 通过、旧回放有一项失败”的结果只是中间结果，不能当作已完成验证。

| 失败 | 原因 | 修复与保留的检查 |
|---|---|---|
| 历史 parity 脚本耗尽 | 旧规划/Finding 合同回放误用新的整篇默认入口 | 明确旧回放的合同；固定历史基线和失败即拒绝规则不改；另用当前整篇入口验证成功发布 |
| parity 成功用例 | 仍发送旧计划、保存和完成格式 | 改走实际搜索、读取、整篇提交；检查真实引用正文、起止位置、来源 revision 1 和保存元数据 |
| 已删除模块清单 | 仍指向退役支线或漏记迁出的模块 | 根据已实施清理补充处置和当前路径，不恢复死代码来迁就旧测试 |
| 文件长度门禁 | 新工具定义使 tool_spec 超限；evidence_ledger 原来多一行 | 工具定义移到专属模块；删除冗余中间变量；不提高上限 |
| PDF 离线回放 | 脚本仍发旧版指令，且未记录原内核的实际工具事件 | 改为定位第 9 页、实际读取、引用 e6、原整篇提交；评分读取真实事件和 accepted evidence，继续检查精确原文 |
| 不支持的参数规则测试 | 把目前已支持的 pattern 当成不支持，失败后留下临时工具 | 改测仍不支持的 format，另测 pattern 实际生效；finally 清理临时注册，解决后续合同及 Zen 只读测试污染 |
| provider 无关快照测试 | 不完整的假会话缺 task_text 等必要字段 | 使用真实 TaskSession，继续检查共享快照没有 API 专属消息封装 |
| Zen 工具名测试 | 假 runtime 的旧签名不接收当前请求选项 | 更新假接口并断言观察、历史轮数、输出限制原样转发，继续检查权限、工具名映射和精确 call ID |
| PDF 命令行自检 | 仍要求 open_url(result_id) 旧别名，假域名没有隔离解析 | 明确拒绝过时参数；固定假文档 DNS 并保留生产公网地址检查；脚本耗尽明确报错，不制造完成；实际 CLI 自检通过 |

第二轮扩大检查为 **3,254 通过、8 失败、622 subtests 通过**。其中四项为直接失败，另外四项来自临时工具遗留的连带污染。修复后相关六个文件 **53 项通过**；同一整组选集再次执行，最终结果见下一节。
