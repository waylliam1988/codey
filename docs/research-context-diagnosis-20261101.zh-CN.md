# Research 纠错上下文与分层实机诊断（2026-11-01）

本轮修正工作视图的证据展示顺序，并用真实 12B 模型区分原文理解、候选选证和完整研究。
**服务已能连续生成；完整 WAL Research 仍未通过内容验收，不能以发布或测试通过代替。**
没有新增内容拦截规则、必填关系表、同模型自审、第二套运行时或知识双写，也没有放宽完成条件。

## 生产修改

`codey/research/context_view.py` 原先按 `f1..fN` 取前面的详情。默认预算下，20 条长记录会让
后面新保存的纠错 finding 只剩编号，正文和证据反而不可见。

现在先按问题分组，再轮流分配详情位置；组内优先最近成功保存或明确读取涉及的引用、
最新 finding、最近完成提案选择的引用，最后才是其他记录。当前操作的问题先获得位置，
不会让同一问题的许多旧记录占满全部位置。

最近引用取自真实执行回执的 `knowledge_notes.created/updated`，或 `knowledge_read` 的精确
引用、对象、note identity；不解析展示文字中貌似 `fN` 的字符串。失败写入不能制造引用。
显式读取 revision 时只优先匹配该版本；短 fN 只匹配自身。一次回执关联多个历史绑定时，
先显示新的绑定，避免又把旧版本排在新版本前面。
这只改变可见性，不判定最新记录正确，也不撤销旧 finding。

完整问题索引继续保留所有 fN/aN。预算不足时显式标出哪些详情未显示，已有截断标记和
`knowledge_read` 读取精确版本的路径保留。没有扩大 14,000 字符默认预算或改变知识版本。

## 服务诊断与重启干扰

服务为 KoboldCpp 1.117.1，模型
`Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，JSON 工具格式，thinking=false，
temperature=0.3。Research 单请求 deadline 为 120 秒，全部模型请求串行提交。

第一次健康探测依次完成短请求、约 13,526 字符提示的普通生成和同规模 JSON 约束请求。
其中普通生成在 512 token 上限结束，只有 reasoning_content，没有最终正文；这里只能证明
服务完成了生成和响应，不能算研究回答成功。随后第四次短请求等了 120 秒超时。
**用户明确说明当时关闭并重启了 KoboldCpp；这次超时按重启干扰保留，不能作为服务自行卡死的证据。**

重启后重新串行验证：

| 请求 | 请求体 | 耗时 | 结果 |
| --- | ---: | ---: | --- |
| 短请求 1 | 268 bytes | 0.656 秒 | SSE 正常结束 |
| 短请求 2 | 268 bytes | 0.657 秒 | SSE 正常结束 |
| 生产规模 JSON | 17,994 bytes | 4.594 秒 | 有效 research_plan JSON |
| 大请求后的短请求 | 268 bytes | 0.672 秒 | SSE 正常结束 |

JSON 非流式响应完成瞬间曾出现 `idle=0`，随后很快回到 `idle=1, queue=0`。最初诊断脚本
误把这个瞬间当成异常退出，已修正为有限轮询排空；原始记录保留。
后续 19 次固定证据实验及一次完整研究共 75 个真实模型请求均返回，未出现请求超时；
各轮结束检查均空闲且队列为零，当时 `total_gens=79`（含上述 4 次健康请求）。
提交前精确版本优先级修正后，另复跑单写者和只读条件各一次，共 4 个请求，
两项仍正确；最终 `idle=1, queue=0, total_gens=83`。这些补测不混入原五题统计。
此后数字排序的收口只跑离线验证；本轮实机没有恢复同对象多版本的实验场景。

保存了两次启动的进程信息、命令行、perf、wire 和新进程空闲堆栈。GUI 启动命令没有显式
stdout/stderr 重定向路径；无法据此证明旧进程输出管道被持续读取。旧进程已经退出，
无法取得其超时堆栈。**本轮没有定位 stdout 阻塞，也没有修改 KoboldCpp 服务端解析器。**
JSON 路径可用不等于原生工具解析卡死根因已修好；本轮没有调用原生工具模式。
perf 和客户端时点也不是服务端排队、prefill、decode 各阶段的精确追踪。

## 固定证据的真实模型实验

新增手工实验入口 `tests/manual/research_evidence_local.py`，复用
`tests.manual.persistent_research_local.stage`。来源是本轮下载并冻结的完整官方
<https://www.sqlite.org/wal.html>，校验 SHA256 后按稳定定位选取完整段落；保留删除文本标记。

fixture 的规划和阅读通过原 `ExecutionDelegate` 产生回执，明确标为 `fixture_setup`，
不能算模型自行规划或检索。模型实际生成局部 finding、选择引用和完成状态，走原 kernel、
save_finding、知识事务及发布路径；模型可调用 save_finding、done、knowledge_read 和
read_tool_result。没有 scripted provider 代写回答，也没有旁路写知识或伪造发布凭证。
每次实验使用独立 state 和 knowledge 目录，不向用户现有知识库写入实验主张。
完整网页未读部分仍保留在来源快照，片段缺失不等于整页不存在。

这是一项控制实验，预置了问题和证据，不能代替自主检索、恢复或浏览器实验。
任务没有泄露正确版本号。下列结果是本助手逐项对照完整引用的诊断记录，非模型正面自评，
也不是用户或独立专家已签收的内容验收。没有修改提示重试到满意后丢弃失败记录。

### 原五题：15 次实验，44 个请求

给定证据层每题 seed=74；候选层每题 seed=74、75，候选顺序随 seed 固定洗牌。
因此跨 seed 的差异同时包含采样与段落次序变化，不能单独归因为其中一项。

| 题目 | 完成/运行数 | 原文对照结果 |
| --- | ---: | --- |
| 只有并发概述，没有单写者限制 | 2/3 | 2 次发布“同主机/共享内存”作为答案，答非所问；另 1 次无进展停止。没有合理保留该缺口 |
| 有直接单写者限制及相邻段落 | 3/3 | 3 次均正确回答只有一个 WAL 文件、一次只有一个 writer |
| 引入版本、只读版本及条件 | 3/3 | 版本号均对应正确；3 次全漏只读条件且未标 partial；给定层另把 2010-07-21 写成 2010-01-21 |
| writer 回绕条件是否为 checkpoint 必要条件 | 3/3 | 回绕条件有记录，但 3 次都漏 checkpoint 的读者边界/恢复说明和所问比较；候选 seed=74 另加强成“当且仅当” |
| 本机性能及整页未测量的推断范围 | 1/3 | 只保存文档“一般更快”，没有回答本机和整页两个证据范围；另 2 次无进展停止 |

流程完成 12/15，按整题判据充分回答 3/15；另 9 个已发布结果存在重要遗漏、答非所问
或错误陈述。这个“误完成”计数不等于 9 个全部虚假的句子：引用真实且句子局部为真，
仍可能没有回答问题。不能拿 12/15 作为内容正确率，更不能外推成通用模型基准成绩。

实质信息也应分别保留：3 次单写者回答正确；3 次版本对应正确，但只读的三个替代条件
全部遗漏；3 次回绕条件有用，但 checkpoint 及比较部分全部遗漏。候选段落中并非没有
相应原文。没有一次妥善回答缺证据的整题，也没有因全部保留未知取得虚假的“改善”。

明确的事实错误为发布日期 1 处；另有 1 处“当且仅当”强化，所选段落没有建立其必要性，
需额外核查。3 次只读条件遗漏单独计入覆盖不足，不与明确假事实混算。
性能题没有生成本机测量数据，本轮不应虚报它编造了本机实验；
实际问题是用通用文档优势替代所问证据范围，并在一轮标成完整回答。

3 次 no_progress 中包含把 passage_ref 当知识 id 读取、重复保存或重复完成；
候选性能 seed=74 则反复提交未满足中文格式的 finding。没有超时或超出轮数。
原五题各 2..6 请求，生成请求跨度约 9.8..24.4 秒；含进程初始化约 12..27 秒。

### 再缩小问题：4 次实验，8 个请求

另将“只读条件”和“checkpoint 停止/继续”分别单独提问，每题两个 seed，给定正确段落。

| 更窄的问题 | 原文对照结果 |
| --- | --- |
| 只读媒体或缺写权限时仍可读取的条件 | 2/2 完整列出已存在可读 -shm/-wal、目录可写、immutable 三种替代条件，并正确给出版本边界 |
| checkpoint 与读事务并行时何时停止、之后如何继续 | 2/2 正确提取 reader end mark 停止边界；均标 partial，但仍遗漏 wal-index 记录进度、下次恢复转移 |

这与复合题漏条件形成可操作的线索：减少同时需要回答的区别，确实能改变本轮输出。
它不是严格的单变量 A/B，也不能证明原复合题只要拆分就一定成功。
checkpoint 的恢复信息已经在完整给定段落里，遗漏仍需计入实质覆盖缺口。
这两轮 partial 的状态比复合题的“已完整回答”诚实，不能把它们当作整题通过。

## 下一步建议

先沿已有 kernel/问题计划缩小一次生成的实际范围：一个具体行为、一组完整前提和少量
已读证据。引入版本、只读条件、checkpoint 的暂停/恢复分别处理；跨动作条件比较要在
两个局部事实均明确后再判断，不能靠句号强行拆散完整条件关系。

优先验证“单题工作上下文”是否减少遗漏和错选，而非再加整套关系表或关键词拦截。
本轮只修正详情展示顺序，尚未把完整任务历史变成严格的单题生成上下文。
本轮真实错误还包括回答与问题对应失效、选入多个近似旧 finding 和格式返工空转。
可以先用程序给出既有选择的逐项字数和具体重复引用，让修复对象更清楚；不要自动替模型
认定任务已覆盖、自动删除非完全相同的主张，或恢复整篇自由改写。

固定相同反例继续统计错误肯定、合理缺口、有证据却漏答和请求成本。当前证据支持
“更小的局部判断值得验证”，不支持“12B 智商必然不够”或“架构已经保证研究正确”。
