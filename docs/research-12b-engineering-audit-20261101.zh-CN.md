**3. 当前最有证据的工程负担。**

**3.1 有界状态视图没有使实际输入有界。**

最新完整运行的实际发送消息如下；字符统计不含单独的 response_format schema，token 为提供方报告值。

| 请求 | 消息数 | 消息正文字符 | 输入 token |
| --- | ---: | ---: | ---: |
| 1 | 4 | 13,644 | 3,499 |
| 4，第一次保存前 | 10 | 34,172 | 9,627 |
| 16，第一次 done 前 | 34 | 93,071 | 25,939 |
| 23，最后一次 done 前 | 48 | 105,984 | 29,977 |

23 次报告的输入 token 合计 443,128；这是请求规模累计，不是排除缓存后的实际 prefill 计算量。最后的工具契约约 10,967 字符，response_format 的 JSON 表示约 8,422 字符，暴露 14 个工具。这些格式和候选选择成本存在，但目前没有实验能给它们分配准确的语义错误占比。

代码路径很明确：`context_view.py:110` 的 14,000 字符只限制状态投影；`kernel_context.py:335` 给评审设置 `tool_call_history_groups=2`，普通严格 research 只设置输出上限 4096；`api_provider.py:735` 只有请求显式指定 history_groups 才投影最近完整协议组。服务容量准入主要防超窗，没有提供当前问题所需的认知工作预算。

因此只调整“最近 finding 先显示”不足以隔离旧错误。也不能直接把 research 的 history_groups 改为 2 就宣布解决：当前 `ResearchContextView` 主要包含已保存 finding，**没有完整重建保存前全部候选 passage、搜索命中及其可用定位**。直接删历史可能把下一步必须读的材料一起删掉。

**3.2 逐题工作仍主要是一条提示。**

`completion_guidance.py:31` 要求先完成一个具体问题，但 `kernel_protocol.py:72` 主要按“有没有搜索、打开、证据”来筛工具，没有冻结一个当前问题的工作范围。模型每次仍可重规划、在 qN 间跳转、选择全局 finding、重交整份 coverage。

最新记录里，模型先为 q2 再次打开相同结果，接着却为 q1 保存近似 finding。最后 q1 选择了 f1/f2/f7 三条近似内容；新近显示不代表新近内容正确，也不代表旧条目已被替代。

同一轮模型同时处理：检索策略、证据相关性、英文条件理解、中文局部表达、qN/pN/fN 引用、全局 rN 登记、状态选择及总字数。减掉最终重写已经少了一项工作，但其他职责仍堆在一个连续会话里。

另一个可见歧义是 rN 同时用于搜索结果和原任务片段：本次 `open_result.result_id=r5` 与 `coverage.task_refs=[r5]` 指不同对象。字段足以让程序区分，模型却仍要维护这两个命名空间。更优先的办法是减少它必须抄写的全局编号，而不是再写一段编号说明。

**3.3 选证与主张范围失配，比 JSON 语法更接近当前核心失败。**

完整运行 q1 的精确 965 字符依据讲 COMMIT 追加和多个事务可以追加到一个 WAL；finding 增加了“同时提交”。审计扫描全部实际载荷，未发现官方直接单写者原句。完整来源确实包含该句，但下载过完整页面、读过相邻窗口，不代表模型已经得到这条直接证据。

checkpoint 的 f4 用 481 字符 excerpt 支持了约 420 字符中文复合说明，增加该段没有包含的 checkpoint 并发边界及默认 1000 页。程序确认来源、片段和版本真实，却不判断整条中文主张的每个关系都由所选材料支持。

`findings.py:15` 的保存语义是候选知识，`interpretation_review` 明确仍为 unreviewed；这是合理边界。真正需要改的是保存前的工作范围与材料选择。将 save 成功当成答案通过，或者把 `evidence_complete` 当成主张完整获支持，都会误用这些字段。

**3.4 负向关键词检查没有一般的答题判断能力。**

本次用当前 `answer_focus.py:31` 的纯函数离线重放，确认两个盲区：

- 原实际问题“多个写入者是否可以同时提交？”配合错误的同时提交 finding，没有被此 helper 拒绝；该问法未命中当前数量问题表达式。
- 明确问“为什么仍存在单写者限制”，配合“所有进程必须位于同主机、共享内存”的答非所问 finding，也没有被此 helper 拒绝。

第二种错误在固定证据实机中确实发布过；第一种在完整任务最终先被长度挡住，本次 helper 重放不代表绕过全部检查已经发布。不能混淆两种证据层级。

这不是要求将表达式加到能认出所有中文问法。词语共现检查不能证明主体、比较对象、条件、否定、充分必要关系或是否真正回答问题。可以保留已知反例的有限检查，但不应再把主要资源投入到给每个语义错误新增规则。

**3.5 字数约束被放在很难修的位置。**

`report_proposal.py:93` 逐字采用选中 finding；`finding_report.py:199` 绑定后才执行报告格式检查。于是一个已经保存的长局部结论，同时承担知识存储文本和最终约 800 字篇幅的义务。模型只能重新选，或另存有依据的短版；done 不允许直接修改答案。

**4. 建议收敛到什么执行形态。**

目标是同一条现有执行链，每次模型只负责一个明确的语义工作；全局进度和格式组装由程序处理。

```text
原始任务 + 一次冻结的 research_plan / 要求归属
    ↓
从计划和已提交回执推导当前问题、当前工作
    ↓
同一个 run_task_kernel：检索 / 阅读 / 小范围 finding
    ↓
提交本题的 finding 选择与完整/部分/缺口状态
    ↓
有未处理项则仍在同一 kernel 进入下一工作
    ↓
程序从全部精确选择编译 FindingReport
    ↓
原 completion gate → 原 publication effect → 原 KnowledgeStore 事务
```

这是建议的目标，不是已经实现或经过实机证明的流程。局部状态依然由模型明确判断，程序不因为“保存了一个 finding”就自动认为问题完整回答。

**4.1 第一批：先把实际请求缩成当前问题的工作视图。**

主要改 `research/context_view.py`、`operations/task_guidance.py`、`kernel_context.py` 和冻结请求/快照契约。

1. 将当前明确操作的问题冻结为本次 TurnSnapshot/请求 artifact 的 scope。至少包含问题身份、必要的原任务范围、允许采用的精确引用和本次目标；没有单独可写的 current_question 数据库。第一批可先依据实际调用和精确回执改善输入投影；完整的“程序选择下一题”依赖后面的局部提交契约，不能仅从最近活动推断某题已经完成。
2. 视图包含当前问题的少量完整候选 passage、必要相邻上下文、来源版本、已保存候选、当前选择和最近一次具体错误。其他问题只显示简短进度索引；跨问题比较时显式带入所需的两个局部事实。
3. 活跃证据不能沿用“最多显示 500 字符，剩下让模型自行补读”的预览作为完整依据。保留完整条件段；超预算时拆候选工作包或明确要求继续阅读，不能静默剪掉列表尾部、否定或例外。
4. 补齐上述可恢复投影以后，再复用现有 `tool_call_history_groups`、完整 codec group 投影与请求准入。原任务锚点必须显式保留；`bounded_history()` 自身不会帮你保留已被切掉的 user 任务。
5. 新请求只呈现当前范围与最近少量完整协议组；全部原始 history、调用与结果留在现有 durable artifacts。原生调用和返回 ID、Responses reasoning 关联继续由 codec 处理，不能直接切 messages 数组。
6. 先实验总输入约 4K～8K token 的工作预算，必要时显式分包或扩大到确实所需范围。这是待验证起点，包含工具和固定指令的预算，不是以证据截断换取达标，也不要求修改服务容量。

只设置“不要跳题”不能替代这批工作。一个新 view class 可以是纯函数结果，但不能拥有独立生命周期和事实写入。

**4.2 第二批：收窄本轮工具和引用，减少模型搬运身份。**

主要改 `kernel_protocol.py`、`research/tool_contract.py`、`operations/task_execution.py` 及原回执投影。

- 规划时只暴露规划所需动作；阅读时暴露检索、打开与必要恢复动作；形成局部发现时暴露 save_finding 和补读路径；本题提交时只允许当前候选与状态。控制范围来自冻结 scope，并与 schema、解析、执行保持一致。
- `question_ref` 在单题 scope 内可由 host 从冻结输入绑定；若模型仍显式传入另一个 qN，拒绝，不能偷偷纠正。原始参数、有效绑定参数与绑定依据必须可审计、可重放。
- 当前可用 passage/finding 采用适度大小的 enum，减少 pN/fN 写错与跨题选择。合法集合仍不能证明语义支持，不将 schema 约束当内容验收。
- 去掉纯 research 窗口中不适用的工作区编辑/测试、shell/CodeMode 说明；领域指导也按当前需要提供。普通编码任务的规则继续由其任务契约负责。

不要为了工具减负增加一套模型专属 ResearchTools 或另一个 provider adapter。当前简单 save_finding 的写入实现继续唯一。

**4.3 第三批：把全局登记移到计划阶段，本题只交本题。**

主要改 `questions.py`、`task_requirements.py`、`tool_contract.py`、`research/tools.py`、`ledger_receipts.py`、`kernel_facts.py` 和完成组合。

`rN` 目前只是保留原文的文本片段，不是天然研究问题。完整任务里既有事实问题，也有背景、实际搜索、保存和回到官方原文的方法要求。不能简单把全部 rN 自动塞进某条回答，假装完成了原义务。

建议在**原 research_plan 唯一契约**中一次记录问题与实质 rN 的归属。格式仍从原文投影；可明确执行验证的要求由真实 tool/effect receipt 检查。背景及方法约束在计划中明确保留作用范围，不能静默丢弃；混合或不能识别的要求仍需交代。计划归属是模型解释，保留不确定性，不宣称程序能自动理解任意自然语言。

随后模型提交一条本题选择，例如“本题 partial、采用 f3”。需要落盘的只有这一条选择事实，而不是每回重交七行 coverage 与几十个 rN。

一种具体实施方式是在现有 kernel 里增加普通领域提交动作 `submit_research_answer`，仅记录当前问题的状态和精确选择，不写新的知识正文、不发布。它**替换当前严格研究让模型反复写全局 coverage 的完成输入**；普通任务的 done 不变。全局 coverage 从原计划和已提交选择回执派生。

这不是另建答案存储：候选事实正文仍只在 KnowledgeStore，选择事实只在该 submit 的 settled effect receipt；`ResearchLedger` 和 `TaskSession` 只是恢复投影。下一工作由 `next_work(plan, settled_receipts, current_failure)` 纯推导，不另存 cursor/status/retries 表。

最后一条局部提交后，程序形成全局候选，进入现有完成与发布路径。可复用 `KernelContext.deliver_results` 已有“领域提交触发程序完成检查”的机制，提炼其通用的受校验提交边界；不能直接信任模型返回的 complete=true。任一缺项、错版本、错归属或未通过格式检查，仍不得发布。

此时需要同步修改 gate 的准备输入：明确区分原始模型提案和程序从局部回执组装的提案，不能把后者塞进 `last_done_args` 后谎称模型提交过一个全局 done。组装结果进入原 managed artifact，记录计划身份、全部采用的提交回执与精确知识版本；`proposal_digest` 绑定这份冻结输入。成功后恢复读取原 compilation，不按今天的知识重新组装另一份报告。

所有局部工作可以留在**一个 research invocation 的普通工具轮次**里，不必每题另开 continuation attempt，也不用先重写整套 `ResearchInvocation` 编号。这与已有 review batch 的回执派生方式一致，但不恢复同模型审查权限。

**4.4 第四批：在保存、选择时就反馈篇幅，失败只修局部。**

主要改 `report_proposal.py`、`task_requirements.py`、`finding_report.py`、`research/issues.py`、`kernel_control.py`、`kernel_prompt.py`、`kernel_progress.py`。

1. 采用同一计数函数，从全局要求、程序缺口与当前选择计算剩余字符；显示每题、每条 finding 的贡献。规划/局部生成前就能看到篇幅目标，不能只在最后要求 1443 字缩到 960。
2. 保留程序逐字采用精确 finding 的原则。需要短版时，在原问题及完整证据上生成一个有依据的替代 finding，更新选择；不恢复整篇自由改写，不静默裁断完整条件。
3. 对完全相同的知识版本可确定性识别重复；对 f1/f2/f7 这种相似但不相同的内容，只提示共同来源与文字重叠，由局部选择决定取舍，不让程序凭相似度合并或宣判哪条正确。旧知识仍保留，更新的是明确选择。
4. 错误应携带结构化 code、scope、path、合法引用、当前值和所需动作。登记错误修登记，字数错误修选择或指定局部 finding，证据错误补读相应材料；删除统一要求“保留所有答案、只修 coverage”的尾句。
5. 在前置引用都合法后，一次给出可独立计算的全部机械错误，减少逐层返工；解析失败时仍先处理依赖，不对无效对象继续推断。
6. 在现有 KernelProgress 中保留重复与预算限制，并将“同一 scope 的未解决错误、选择和有效证据是否变化”纳入进展反馈。新保存了近义文字不等于消除了已知问题。程序不因此自称能判定新旧文字语义相同。

不应以放宽字数、自动给所有 rN 打勾、同一请求换 seed 重试到满意来宣称跑通。若真实且完整的信息无法符合篇幅，明确交代冲突，不能删掉关键条件后把流程成功当内容成功。

**4.5 局部生成本身也要改变粒度。**

围绕一个动作或一个明确区别工作；版本引入、只读权限的完整替代条件、checkpoint 的停止、进度恢复分别形成工作，再按需要比较。一个完整条件关系可以跨多句，不能用句号机械拆成失去前提的碎片。三种替代条件属于同一个完整规则，应一起保留。

对有清楚原文的题，优先忠实抽取/翻译，不要求每条都追加适用性、性能推断和新局限。跨来源归纳确有需要时，沿已有 save_inference，明确前提和未验证边界。原始任务没问的额外主题不要自动扩大成必做研究。

没有直接证据时，允许明确的局部缺口；有证据却遗漏不能算缺口处理成功。全部未知也不能作为“错误肯定减少”的唯一成绩。

**5. 单一事实来源的边界应怎样守住。**

| 事实 | 唯一权威 | 允许的派生内容 |
| --- | --- | --- |
| 原始任务和冻结问题计划 | 原 durable 输入、research_plan 的原调用及回执 | rN、当前 scope、待工作索引 |
| 实际发生的搜索/阅读/采用 | 原 settled tool/effect receipts | aN、已读 passage 索引、当前材料视图 |
| 原始证据与候选主张版本 | 现有快照及 KnowledgeStore 精确版本 | 预览、定位、fN、只读证据包 |
| 某题明确选择与声明状态 | 原局部提交的 settled receipt | 全局 coverage、下一题、修复工作 |
| 执行位置、总预算与取消 | 原 operation/checkpoint/counters | UI 进度、范围投影 |
| 最终报告内容 | 唯一冻结 FindingReport compilation | Markdown、UI、历史 ledger、知识发布内容 |
| 发布是否成功 | 原 publication effect 与知识事务 | 发布索引和完成证明 |

同一数据库事务里的正文与索引投影、不同事实之间的引用，不自动等于有问题的“双写”。关键是每种事实谁有权修改、恢复时以谁为准。不能出现另一张可编辑 EvidenceCard/QuestionAnswer 表与原知识/回执相互覆盖。

局部提交记录选择身份，编译 artifact 冻结一次报告采用结果，知识发布记录发布效果；三者是不同事实阶段，不能各自重新创作同一答案正文。任何缓存都要能由权威 artifact 重建，不能反向裁定历史发布结果。

迁移时同一新任务只冻结一个契约版本、使用一条写路径。旧已发布 artifact 只读；旧执行中的请求按原冻结语义恢复，若实现不兼容则明确拒绝恢复。不要同时保留“旧严格研究”和“12B 新研究”的可写运行模式。

**6. 建议按这个次序实施与验收。**

| 顺序 | 交付 | 本批应回答的问题 |
| --- | --- | --- |
| P0 | 完整活跃证据的单题视图 + 实际载荷预算 + 按错误类型修复提示 | 长历史与纠错污染是否下降，完整条件是否仍可见 |
| P1 | 冻结 scope、按工作收窄工具、question_ref 绑定 | 是否减少错题保存、错误引用及来回跳题 |
| P2 | 计划阶段一次归属 + 局部选择回执 + 程序全局编译 | 是否减少 rN/coverage 重交，并保持完整义务和唯一发布 |
| P3 | 早期篇幅反馈、明确替代选择、现有进展机制收口 | 是否真正修掉字数/重复，不以缺口或丢条件换完成 |

不必先大改浏览器、换 provider、重做知识数据库或重写 continuation。每批先删除被替代的请求/写入入口，再验证下一批；不要先堆一个新 orchestration 外壳。

模型验收建议固定同一模型文件、模板、量化、采样、thinking 和来源快照，分开控制候选顺序与 seed。先做单因素对照，再测整体组合：

- 固定证据：直接数量限制、共存但无数量证据、完整只读条件、checkpoint 停止与恢复、版本关系、缺少本机测量。
- 对照多问题任务：同一材料单问与复合问；不能给新流程预选正确答案，旧流程却要自行找证据。
- 跨领域保留比较对象、非随机试验及摘录/整页范围反例，防止只对 WAL 过拟合。
- 每题至少 3 次独立状态作为初步检查，再增加样本；把原失败保留下来，不修改提示直到成功后只保留最后一次。
- 分别计错误肯定、有证据却漏答、答非所问、合理缺口、实质回答率、完整任务率、调用和输入输出规模、重复保存与修复次数。与正确正例一起统计，避免全部拒绝得到虚假好结果。

机械验收包括：两个协议实际载荷的范围一致；无证据截断伪装成完整；错 scope 拒绝；漏题不发布；局部修复不重查已 settled 资料；旧选择不批准新版本；进程退出恢复不重复知识修订；发布前后中断均只提交一次；取消与结果未知边界不被后续阶段绕过。

最后按“固定证据 → 单问题真实检索 → 多问题 → 原完整 WAL”逐层复测。12B 正例通过后再核对将实际使用的 27B 部署；这属于验证同一架构，不是依赖换模型解决。

**7. 本轮做了哪些验证，哪些尚未做。**

已离线读取 22 个最新运行目录（原五题、窄题、补测和完整任务），复算实际载荷规模及字数，重放上述两种 focus helper 盲区，核对 Qwen 短材料原始输出。统计 JSON 不具备自动语义评分权限。

初始快照的 9 份现有测试文件共 **105 passed in 7.06s**，覆盖答案编译、答题焦点、纠错上下文、格式、问题归属、缺口、finding 选择、页内检索和报告快照。工作区出现上述 gate 重构后，增加 `test_research_gate_preparation.py`、`test_research_reference_coverage.py`，11 份测试最终为 **120 passed in 11.96s**。两轮有重叠，数量不相加；独立离线 runner 拦截 socket 连接，两轮记录的尝试数均为 **0**。本轮未改写这些测试，也没有运行全仓测试。

本次尚未实现上述 P0～P3，更未进行新模型 A/B。因此结论是“已定位仍存在的工程负担，并给出可实施的收敛路径”，不能声称已经证明 12B 端到端内容通过。优先实施单题完整证据视图与实际请求投影，是现有证据最支持的下一步；继续追加提示、字段或同模型正面自审，收益依据都更弱。
