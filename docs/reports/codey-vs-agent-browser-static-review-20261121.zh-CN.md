# Codey 对照 agent-browser 的静态设计复审

日期：2026-11-21。对照 agent-browser 提交 `4b0e9f0` 与当前 Codey 源码。本轮仅阅读源码和修订方案，没有运行浏览器、模型或性能测试，没有修改生产实现。

## 1. 判断

上一版六批方案是 Codey 能力融合与缺陷修复方案，还不能据此判断浏览器执行层超过 agent-browser。它没有充分覆盖后者已经具备的引用生命周期、frame 身份、原生输入中断、增量观察、传输与会话细节。

需要分别评估两件事：

- 浏览器执行层，在双方共同支持的本地 Chromium 场景中对照观察、定位、输入、等待、会话与恢复。
- 整体任务层，评估浏览器如何与项目文件、研究来源、用户协助和可恢复执行共同工作。Codey 有额外基础，但它们不能直接证明浏览器驱动更好。

“静态上更好”应落实为可检查的模块依赖、明确的状态和身份合同、覆盖所有出口的协议定义，以及纯逻辑合同验证。功能名称更多、语言换成 Rust、类更多或文件更少都不是充分证据。

## 2. 对照中实际确认的 agent-browser 能力

| 维度 | 已阅读的实现 | 上一版 Codey 方案还缺什么 |
| --- | --- | --- |
| 元素观察 | AX 树结合 DOM 可交互补充；支持 selector、交互项、深度等观察范围 | 明确观察主模型与不同观察之间的关系，不能只补 CSS selector |
| 引用身份 | session/frame/document loader/backend node 共同约束，同文档节点可延续引用 | 跨 frame 身份与引用失效规则；避免每次动作清空所有引用 |
| 增量反馈 | 按页面保存快照 revision，返回移除 ref 和 delta；观察选项变化可返回全量 | 有基准身份的增量协议、截断后的再观察入口与输出预算 |
| 视觉观察 | 区域截图、编号与 ref/box 映射，条件截图比较解码后像素 | 图像、DOM ref、视口和坐标变换的一致性合同 |
| 原生输入 | 按键、选择、悬停、frame 坐标偏移，点击会记录中途弹窗和未释放鼠标状态 | 不只是工具名，还需完整的中断和部分执行语义 |
| 会话绑定 | pinned target 跨 daemon 重启，绑定文件原子写、严格丢失反馈 | TaskResources 中资源所有权、目标绑定和恢复语义的完整设计 |
| 等待 | selector 状态、文本、函数及 frame 范围等等待 | 新文档和同文档变化的等待规则、统一预算和可中断性 |
| 传输事件 | CDP command ID、事件订阅、需要应答事件的无损 tap，与可丢帧消费区分 | 阻塞故障域、取消与迟到结果的处理，不能只写“有 timeout” |

## 3. 对原重构方案必须增加的设计

### A. 把浏览器从研究 provider 中真正解耦

当前 BrowserSession 直接导入多个 research 模块，`_base_provider` 必须从 WebSourceProvider/ConnectorAwareSearchProvider 解包得到具体 BrowserSearchProvider，并访问其私有页面与 worker。这不仅是命名问题，而是资源所有权和依赖方向仍受研究采集实现约束。

修改目标：任务资源创建并持有浏览器会话；浏览器交互和网页来源采集都使用它。BrowserSession 接收明确的驱动/会话资源和执行通道，不再依赖研究 provider 的具体类。

浏览器层返回真实观察与原始页面捕获；来源模块负责选择、抽取、版本和引用入账。保留 HTTP 快速读取，但不得因为来源正文校验失败而失去当前页面的观察与操作能力。

验收应包含依赖检查：浏览器执行核心不导入 research 或 operations；来源与任务层可以依赖浏览器能力。保留 Playwright 作为引擎，不需要为此重写一套 CDP，也无需先造多个可替换后端。

### B. 明确身份与新鲜度，不用一个 generation 承担全部语义

分别定义：浏览器实例/context/target/frame/document 身份、观察 revision、节点身份与语义约束。

- 同文档中节点仍存在且目标语义未变时，可以继续使用对应引用。
- DOM 节点被替换、frame 文档或执行 session 改变，旧引用失效。
- 虚拟列表复用同一个 DOM 节点时，还需重新检查名称、所属记录或其他已观察目标语义。
- 身份未知时不得凭同名或同域悄悄换目标。
- 观察来自历史还是当前、覆盖哪个区域、哪些部分不完整，都有明确数据字段。

Codey 已有角色、名称和区域复核，可保留；需要补跨 frame 身份及精确失效，而非简单放宽 `_resolve_ref` 或删除校验。

### C. 把观察做成有范围、有基准的协议

采用 AX 与 DOM 互补，截图补充 DOM 无法充分表达的信息。所有观察都绑定同一套目标与文档身份。

局部快照的 complete 应表示该声明区域完整，不能暗示整页完整。长页面应支持进一步观察指定区域；增量结果需包含基准 revision、变化和失效引用；基准丢失或范围变化时返回明确全量观察。

编号截图必须绑定图片 artifact、区域、视口、滚动与缩放变换、观察 revision。坐标是对那次观察的解释，不是永久元素身份。页面变化后重新核对，不能拿旧截图位置点击新页面。

不把“页面有变化”当作“查询成功”；DOM/视觉差异是观察事实，业务正确性仍需对照用户目标。

### D. 完整定义动作生命周期和错误结果

上一版只提出拆分 delivered/uncertain，仍不足以覆盖真实输入。

每个动作至少区分目标检查、输入派发、浏览器反馈和业务验证。失败出口说明已确认执行到哪一步，以及下一步可以观察什么。点击过程中可能已按下鼠标、已导航、已打开原生 dialog，不能用一个 success=False 概括。

以实际可知事实定义有约束的结果分支：确认未派发、确认已派发、派发状态未知；同时保留后续观察与业务验证状态。未知不等同未执行，派发不等同业务成功。组合动作记录每个已有组件结果，不要求重放已完成部分。

所有失败出口具有机器可读 reason 和必要身份，不依赖解析 Playwright 英文报错或任意字符串前缀。错误显示文字由结构化结果生成。中断后的 release、dialog 处理和目标变化必须进入同一生命周期。

### E. 等待、调度、取消和故障隔离形成同一预算合同

当前采集与交互链路调用全局 `_SEARCH_WORKER`。BrowserWorker 有有界队列、取消信号、迟到结果丢弃和健康观察，这些是应保留的基础；但同步作业未返回时，调用方退出不表示底层操作已经停止，也不能让清理工作越过该阻塞作业。

仓库已有其他 session_worker 通道，不能说整个 Codey 都没有会话隔离；应让真正的任务浏览器使用相应所有权和执行通道。

设计要求：同一目标写操作有序；独立目标不受单个卡页的全局队列牵连；排队、动作和后续等待消耗同一绝对 deadline。执行状态区分排队、已开始、取消请求、结果未知及已结束。

硬卡死的处置要明确。可以保留 Playwright，但受影响 worker 的失效与重连必须有可隔离的控制边界；不能把同步线程标为 cancelled 后继续假定没有迟到效果。必要的进程隔离按故障边界引入，而不是一开始重写全部引擎。

等待需支持新文档、同文档区域变化、可见/消失、可操作性及必要的 popup/download/dialog 事件，并明确绑定范围。避免把固定 2.5 秒或 network idle 当作所有网站的完成定义。

### F. 区分本地回执恢复与网站效果恢复

网站已执行动作、本地尚未提交回执时崩溃，是必须设计的边界。本地 durable 写入不等于网站效果 exactly-once。

记录执行意图与派发阶段，恢复时优先取回已提交结果；若效果未知则观察并核对当前状态，不自动重放原点击。无法核实则保留未知并请求必要协助。不得凭原请求 ID 就认定网站做了去重。

这能让 Codey 的浏览器动作与代码修改、测试和报告共同拥有一致的恢复语义，是整体任务层可能形成明确优势的地方。

### G. 单一工具定义要覆盖成功、失败与前提执行

Codey 已有 ToolSpec、冻结快照和部分输出 schema 校验，应继续利用。但现有 browser 输出中 delivery/observation 多为宽泛字符串，不能仅凭“有 JSON schema”就称动作状态严格。

`ToolSpec.preconditions` 的直接消费主要可见于回执定义恢复，真实前提在各执行路径实现。角色与文件等检查并非不存在；缺少的是声明与执行检查的统一对应关系。

新增验收：每个声明前提有可执行检查或明确由哪个 handler 保证；每个工具的成功和失败出口都满足相应结果合同；直接/native/CodeMode/恢复路径保持相同含义。继续使用现有注册源，不建立第二套独立 DSL 或手工重复维护多份 schema。

工具目录只在用户授权和资源真实条件下变化。没有授权、未支持、尚未观察目标、执行失败须分别说明，不能统一归为 unavailable。

## 4. 哪些维度可以提出超出对照项目的目标

| 目标 | 可以在静态审查中核对的内容 | 当前状态 |
| --- | --- | --- |
| 统一机器可读动作结果 | 所有命令的派发阶段、观察、失败原因与恢复身份有一致合同 | 需要补充，不能只沿用字符串状态 |
| 跨工具可追溯性 | 浏览器观察、来源版本、文件修改和测试结果共同来自任务回执 | Codey 有基础，端到端关系仍需完成 |
| 效果未知时的恢复 | 明确崩溃窗口、已完成组件复用、禁止未知动作自动重放 | 有基础，本轮已发现常规恢复缺口 |
| 能力与交付解耦 | 相同授权下研究/编码共享能力，报告成功不提前结束整体目标 | 已有明确修改位置，尚未实施 |
| 清晰的依赖和所有权 | 浏览器不依赖研究 provider；任务持有资源，页面和观察身份各司其职 | 当前依赖方向仍需修改 |
| 可验证的协议一致性 | 一份工具主定义覆盖展示、验证、执行与恢复；每个声明前提有对应检查 | 已部分具备，需要补全 |

这里不声称 agent-browser 没有恢复、策略或状态管理。它已有相关机制。比较点是 Codey 能否在上述端到端合同上更一致、更可审查，而不是拿一个完整任务系统与一个浏览器工具按功能总数比较。

## 5. 静态验收门槛

实现后逐项给出源码位置和纯逻辑合同验证；未满足时不能宣布静态设计已超过对照目标。

1. 浏览器核心依赖方向正确，来源采集不再拥有唯一浏览器入口。
2. 同授权、同资源条件的核心工具能力不因活动类型而消失，显式限制仍执行。
3. 引用包含 frame/document 语义；文档未知、节点替换和虚拟记录变更均有明确处理。
4. 无关变化不强制清空所有仍有效引用；失效引用不静默同名重绑定。
5. 局部观察与增量协议具有范围、完整性和基准 revision，基准缺失可恢复。
6. 图像/ref/坐标转换可追溯到同一次观察，缺少视觉能力时有准确降级。
7. 每个动作成功与失败出口有结构化阶段与原因，部分输入状态可恢复。
8. 等待谓词、事件范围和绝对 deadline 有一致定义，取消不伪装成效果未发生。
9. 任务资源所有权、同目标排序和独立目标故障隔离明确；卡死不依靠同一阻塞队列自救。
10. 崩溃恢复复用已提交结果，效果未知不自动重放，不对网站承诺不可证明的 exactly-once。
11. 工具定义、前提检查、结果 schema、模型协议和恢复含义保持闭合，支持能力有真实 handler。
12. 报告、代码、测试和网页验证按用户整体目标组合完成，不靠模式切换或一条固定流程。

依赖和 schema 一致性可做静态/合同检查；引用与恢复状态可做不启动浏览器的纯逻辑状态迁移验证。这些比口头设计更可审查，但不替代浏览器行为与模型效果验收。

## 6. 对实施顺序的修订

先在原第一、二批完成能力与交付解耦；同时把单一任务浏览器资源接口、身份/观察/动作合同定下来。再让原第三至六批围绕这些合同实现恢复、所有权、观察与输入，而不是各自增加局部字段。

引用和恢复状态的纯逻辑验证应先于大规模修改。首个浏览器增量必须同时交付其身份、输出和取消语义，不能先加十个工具名再补正确性。

不要求首轮复制 agent-browser 的所有移动端、远程 provider、录制和 flow 功能。应先在共同的 Chromium 支持范围追平核心执行能力，再以统一回执、恢复与可组合任务合同建立可审查的优势。
