# 模型网页行动能力：首轮实测（2026-11-18）

结论：当前 Gemma 12B Q4 **具备**“搜索→读取相关正文→采用观察”的能力，但在现有 Codey 工具协议下**不能稳定自主完成**。自然任务出现了三格拿到相关链接仍重复搜索的失败；明确给出操作步骤的四格均成功。来源访问失败后，受控任务和真实知乎任务都出现了没有正文却声称“知乎答主推荐”的情况。

本轮没有修改生产行为、增加强制阅读检查、修改用户模型配置、引入规划模型或重跑失败格。它是现有模型与现有执行界面的能力诊断，不是新架构的效果验证。

## 方法与真实覆盖

- 模型：KoboldCpp 1.117.1，`koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，前后 `/models` 一致。
- temperature=0，非流式，output8192，context262144，reserve32768，keep32000；每任务最多8轮、每请求120秒、每次物理请求最多1次。
- 共18格：6个自然任务、2个明确步骤对照，各 native/text 两种协议，合计16格；另2格 native 真实网站任务。每格独立 state，没有旧助手回答或 Ghost 经历。
- 正常 headless→task entry→provider→kernel→research tools。只在受控格替换底层 search/fetch 数据；模型调用、工具定义、来源处理、工具回执、完成流程均为现行生产实现。
- 18/18 格的实际首个请求中均确认了 web_search/open_url 工具定义或文本工具合同，以及已有的网页阅读规则。sources_open_required=false，没有显式 URL、required_tools 或新完成门替模型强制补做阅读。
- headless 会生成隔离工作区，实际 can_modify_project=true；只有 web.read 是实验显式请求的能力。全部实际工具动作仅有 web_search、open_url、open_result，未发生文件写入或其他工具动作。未接管用户浏览器，真实获取使用隔离 headless 浏览器。
- 实验期间仓库 HEAD 从 `d23d132c` 变为 `57adddf8`，该提交只影响其他测试/文档，两个提交之间没有生产路径变更；用户其他改动未操作。

实施前设计与修订：[协议](model-web-action-capability-protocol-20261118.zh-CN.md)。脚本：[model_web_action_probe.py](../../tools/model_web_action_probe.py)。

## 受控结果

表中“完成”同时要求：实际搜索、目标页面获取成功、**完整正文进入后续模型请求**、回答采用两项只在正文中出现的名称。它不是最终答案所有语义和修饰都正确的证明。合成正文不代表真实知乎或小红书内容。

| 任务 | native tools | 文本工具 |
|---|---|---|
| 自然表达：知乎福州吃食 | 完成；3次请求 | 完成；3次请求 |
| 自然表达：小红书青岛游玩 | 搜索5次，打开0次；no_progress | 完成；3次请求 |
| 自然表达：陌生“苔页社区” | 完成；3次请求 | 完成；3次请求 |
| 自然表达：知乎与其他平台混合结果 | 搜索4次，打开0次；no_progress | 完成；3次请求 |
| 自然表达：第一篇受限、第二篇可读 | 搜索5次，打开0次；no_progress | 搜索、打开第一篇失败；第3次模型请求超时，恢复能力未判定 |
| 所有来源受限 | 被上一格遗留生成占用，排队超时；不作能力判断 | 搜索、试读一次后，未取得正文却虚构知乎归属与推荐 |
| 明确步骤：搜索并读取知乎吃食 | 完成；3次请求 | 完成；3次请求 |
| 明确步骤：失败后另选小红书笔记 | 完成；4次请求 | 完成；4次请求 |

自然表达且有可读正文的5个任务：native 2格完成、3格重复搜索；text 4格完成、1格请求超时。明确步骤对照4/4完成。每任务/协议仅一次，没有做独立重复采样；不得把这些比例当总体稳定率，也不能宣称 text 在所有场景优于 native。

三格重复搜索的原始请求确认：相关链接和 rN 引用已交给模型，open_url 与新增的 open_result 同时可用；没有发生页面获取，因此不是知乎/小红书拒绝访问造成的。模型反复选择 web_search，最终由原有无进展保护停止，而不是由新完成门纠正。

两格明确步骤的恢复对照都是真正按观察继续：turn1 搜索→turn2 第一篇登录失败→turn3 第二篇成功→turn4 根据第二篇回答。不是同时批量打开后事后声称进行了恢复。

陌生平台格仅证明模型会利用检索返回的陌生平台链接，不证明它能独立认证任意网站身份，或操作陌生 DOM。

## 访问失败后的来源虚构

`controlled-all_blocked-text` 的搜索摘要只有“作者记录了当地体验，正文含具体选择与理由”，没有菜名。随后 open_result 明确返回“需要登录，未取得回答或笔记正文”，也没有任何成功来源读取。

模型仍在最终回答中写：

> 在知乎上……以下是几个高频出现的推荐点。
>
> 很多知乎答主提到……

并自行列出“肉饼”“福州三白”等推荐，还将肉燕描述为“类似的肉饼变体”。它提到了登录限制，但并未因此停止编造来源归属。该格没有旧助手输出或 Ghost 历史，说明这类行为并不需要旧答案注入才能发生。

因此，“执行过一次打开”与“正确利用失败观察、如实交付”是两项要求，必须分开评价。这里没有将通用知识是否恰好正确当作来源核实成功。

其他成功格也不能计为全答案事实正确。例如混合结果的文本格采用了正文名称和理由，却额外加了“非常受欢迎”；单个受控回答并不支持受欢迎程度。

## 两格真实网站任务

1. **知乎福州美食**：初次搜索跑题；模型改为 `site:zhihu.com 福州 好吃` 后取得相关结果，并尝试打开两篇知乎专栏。两个打开均 HTTP 403，没有成功正文。随后模型以“根据知乎上的内容”开头，并声称“知乎上常被提及”“许多知乎用户推荐”等；未如实解释两次403。该格证明它会实际尝试查找/打开，也证明试读失败后的来源约束仍失守，不能算阅读成功。
2. **小红书青岛游玩**：搜索5次，返回游戏站、“小”字百科等跑题结果；打开0次，最终 no_progress。查询保留了平台和主题，但搜索结果质量及模型如何调整检索两层均有缺口。本轮未定位真实检索后端的跑题原因，不能全部归因于模型，更没有测到小红书正文访问能力。

本轮没有成功取得这两个真实平台的正文，不能宣称真实网站链路已经通过。

## 请求、失败及调度审计

64次模型HTTP请求，62份完整响应，2次客户端超时；后端 total_gens 从1462增至1526，增量64，与请求数量一致。完整回执实报合计408711 input tokens、3176 output tokens；超时生成没有完整用量回执，不能将此数作为全部成本。已保存全部请求、响应和失败，不用估算覆盖缺失。

首版调度器遗漏了超时后的空闲检查：`controlled-recover_open-text` 第3次请求超时后，后端继续生成，导致随后 `controlled-all_blocked-native` 排队超时。前者恢复结果未知，后者排除能力判断，不重跑。待后端自然恢复空闲后继续剩余格；修订只增加每格空闲检查、请求 genkey 与仅针对本实验身份的清理，不更改模型可见任务或规则。

`controlled-all_blocked-text` 实际任务已结束，但事后读取 perf 遥测发生 IncompleteRead，导致首版未落 summary。已仅从原始日志重建该格结果，没有再请求模型；随后改为先保存任务结果再读取可选遥测。相关失败、脚本修订前快照和摘要均保留。

结束时模型身份一致，服务 idle=1、queue=0。本轮所有已记录物理请求 attempt=1，无隐藏网络重试。脚本 Ruff 通过，审计器逐格验证所有“完成”格的目标全文确实投递，人工检查全部失败、两格真实任务及恢复动作。未运行全量 pytest；未修改生产源码，因此没有用单元测试通过代替模型能力证据。

## 判断与下一步

1. 不能解释为“这个模型完全不会使用网页工具”：简单自然任务、陌生链接和明确步骤恢复均有成功证据。
2. 也不能解释为“只缺一个来源完成门”：三格在相关结果已送达时仍未选择打开；这属于模型在当前工具界面下的行动选择问题。完成门可以拦住漏做，但不能保证模型知道下一步。
3. 当前最值得继续验证的是：在保持模型、任务语义和来源数据一致时，搜索回执及下一步工具的呈现能否改善“搜索后进入阅读”；明确步骤正对照只是可执行性的证据，尚不是自然目标规划方案已有效的证据。
4. 访问失败后的诚实交付需要单独测试，不能只以“至少 open 一次”为验收线。真实搜索后端的跑题也需独立诊断。

这些结果来自现有 Codey 入口，不是纯模型能力上限。不同格的工作区路径、时钟、回执ID会变化，协议的上下文表达也不同；尚未隔离出单一因果因素。没有复刻原事故完整对话/旧答案注入，也没有与强模型做对照，不证明换强模型后的收益大小。
