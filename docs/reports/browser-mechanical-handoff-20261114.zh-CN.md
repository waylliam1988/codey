# 浏览器操作机械减负与回执交接验收

基于 `816728ee`，直接修改当前工作区，没有创建或复制 worktree。使用现有本地 KoboldCpp Gemma4 12B Q4、seed `123456789`、真实 Chromium、生产注册表、kernel、CodeMode 和回执链。没有运行全量 pytest。

## 修改边界

1. 普通 Chat / Hybrid 明确要求正式导航、原任务只有一个已授权 URL、尚无浏览器操作回执时，在原有首轮来源批次中补正式导航。原有 URL 绑定和冻结参数校验仍然生效；要求 `via=codemode` 就生成普通 CodeMode 调用。已经操作过页面时不自动刷新。显式页面顺序合同继续管理自己的导航，不再额外附加入口。已经预取过来源，也不能使独立导航要求被提前返回跳过。
2. 直接和嵌套 `browser_click` 使用同一输入定义及可执行 `purpose` 集合。固定后续计划由冻结要求和原叶工具能力生成。原 guest 在同一 RPC 链逐项发送点击、等待、快照或正式读取；每项继续取得原子动作身份和原回执。host 消费已校验的查询意图，底层点击仍只接收 `ref`。删除按整段 JavaScript 字符串相等识别查询的分支，没有引入第二套运行时。
3. 计划不可执行、参数非法或剩余子调用预算不足时，在点击前拒绝。组合参数先固定为 JSON，避免选择计划和发送点击读取到不同值。未等待组合调用仍会被原有 unawaited 检查拒绝。成功时保留点击返回类型；正文和快照仍由原子回执交付。后续读取失败不会返回一个冒充组合成功的点击结果，也不会重放点击。
4. 首轮实机再次表明“知道还欠等待”不代表模型会编写等待程序。因此，仅在明确要求且回执仍缺失时，把原 `browser_wait` 叶工具提供为直接模型入口。它使用原冻结 schema，仍要求 `condition`、`value`、`timeout_ms`，没有猜条件或放宽参数。固定包装仍走普通 CodeMode 和原 kernel，也能满足原来的父调用约束。普通单击同样经过共用包装，实际动作仍只有一次点击。
5. Chat / Hybrid 的下一步说明从原 `ToolSuccessRequirement.observe()` 和原回执投影生成，不保存另一份完成状态。查询点击已送达、读取未确认时，优先提示补读。JSON 项目写入缺失时，重新交付现有的两行 `tools.edit({read, changes})` 模板；路径、字段和值仍由模型选择，没有恢复旧 `codemode.action` / `edit_json`，也没有为多字段任务另建绑定系统。
6. 删除源码识别后，同步删除呈现层对旧 `audit.browser_followup` 的依赖。快照和查询正文直接来自已提交的原子回执；后续导航之后不再把先前快照呈现为可用引用。失败后仍保留点击和读取的各自事实，没有写入第二份组合完成状态。

没有加入通用 Chat “工具齐了就只准 done”的门禁：工具清单不能证明任意开放任务已经答完。原完成门继续判定完成；未知等待条件、额外必要交互和任务含义仍需模型判断。`purpose=action` 也不会被程序擅自解释成查询。

## 结论边界

这批改动接手的是已声明步骤、调用转换、类型解包和执行事实交付。它没有自动理解任意网页，也不会把点击送达解释成答案已经取得。自由编写的 CodeMode 仍可能产生语法或字段错误；模板降低样板负担，不能保证模型总是选用模板。少量矩阵和重跑可以证明机制在具体轨迹中被使用，不能据此估计普遍成功概率。

因此，本轮不能声称完整自主完成率已经提升，也不能声称所有实机问题已修复。确定性修复是两层点击的 purpose 语义统一、可绑定初始导航、缺失等待的原叶工具入口和子回执交付。元数据调用选择、任意 JavaScript 的解包及重放程序构造仍需后续按真实失败频率减负。没有为这些问题放宽生产合同或添加矩阵专用分支。
