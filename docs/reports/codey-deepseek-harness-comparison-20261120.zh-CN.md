# Codey 与 DeepSeek Harness 复杂任务实机对比

日期：2026-11-20。使用本机已有 KoboldCpp 与 Gemma4 12B，分别运行同一份复杂编码任务。没有给模型追加人工救场提示，没有修改两边生产源码。

**本轮 Codey 修好的测试更多，但双方都没有完成综合任务。最值得借鉴的是 Harness 的上下文组织；双方的重复操作检测都有缺口，不能直接照搬 Harness 就认为能解决。**

## 设置与验收

| 项目 | 设置 |
|---|---|
| Codey | `9cdada0d237ae95a4bfe0563656ba6726b52ad9a`，生产 headless 入口 |
| DeepSeek Harness | `8bd073392eef6f54e921a093b95076248eb08cbb`，`0.2.2-alpha.3`，官方 CLI 的 headless profile |
| 服务 | 本机已有 KoboldCpp `1.117.1`，没有重启或停止服务 |
| 模型 | `Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M` |
| 采样 | temperature 0、seed 123456789、关闭思考、每次最多输出 4096 token |
| 上下文 | 262144；不委派，不创建 worktree |
| 预算 | 每边最多 36 次实际任务生成、1200 秒；串行执行，Harness 在先 |
| 输入 | 完全相同的任务正文、七个夹具文件、空 Git 索引；初始 SHA256 已保存 |
| 独立验收 | 固定 `test_checkout.py` 与 `test_health.py`，共 12 项；检查受保护文件哈希 |

复杂任务要求：先后台测试并读三个项目文件、检查实际失败，再修复 SQLite 下单服务；修复通过后启动并停止 partner 诊断，确认清理；最后运行健康检查并如实收尾。只允许修改 `checkout.py`。

两边的原始请求、转发请求、原始响应、工具参数与结果都保留。代理只统一采样控制，不修改消息、工具定义或工具返回。正式实验没有重跑挑最好成绩。

这不是严格隔离单一变量的 A/B：Harness 使用原生工具，Codey 按现有兼容策略使用文本工具；Harness 是 danger-full-access，Codey 保留自己的编码权限合同；Codey 另有逻辑步数、进展判断及正式完成检查。Harness 第 37 次请求在代理处被预算限制拒绝，没有发生第 37 次生成。Codey 在 36 步上限结束。服务生成计数分别增加 36，元数据与分词请求没有计入生成预算。

## 实际结果

| 指标 | Codey | DeepSeek Harness |
|---|---:|---:|
| 实际模型生成 | 36 | 36 |
| 独立验收通过 | **10 / 12** | **6 / 12** |
| 独立验收失败 | 2 | 6 |
| 编辑调用 | 11 | 16 |
| 实际改变文件的编辑 | 2 | 1 |
| 新旧内容相同的空编辑 | 9，返回没有改动 | 7，明确拒绝 |
| 旧文本找不到 | 0 | 7 |
| 后台执行并读取最终结果 | 11 次 | 0 次；12 次测试实际在前台完成 |
| 修改受保护文件 | 无 | 无 |
| 完成诊断停止与后续健康检查阶段 | 否 | 否 |
| 综合任务成功 | **否** | **否** |
| 运行阶段耗时 | 771.11 秒 | 543.53 秒 |

耗时不表示同等工作量下的速度：双方动作、工具协议、输出长度、等待方式不同。独立评分额外运行健康检查，所以“独立健康项通过”不代表模型自己完成了任务第四阶段。

Codey 的后台子任务有 11 个，最终全部结束，主任务为 failed，停止原因 max_turns。测试失败收据没有被当成测试通过。Python 实验 worker 进程正常退出不代表用户任务成功；正式 headless 结果的退出码是 1。

### Codey 的剩余错误

两个失败项是：`True` 被当成合法整数数量；并发相同订单触发唯一键冲突。候选代码仍使用 `isinstance(quantity, int)` 而没有排除 bool；并发请求在事务开始前检查旧订单，多个连接可能同时认定订单不存在。

这是模型生成的业务修复不完整。本轮库存耗尽后的同单重试、连接关闭等项通过。不能因“编辑成功”或“开启事务”就认定并发逻辑修好。

实际改动出现在第 6、9 步。第 10、11 步验证第 9 步的修改后，仍然失败；第 12～36 步共 25 次模型调用继续空编辑、重跑相同测试、读取结果，没有再改变文件。这个数字是本轮观察到的停滞成本，不是已证明能全部省掉的回合数。

Codey 首次显式请求后台执行；后续 10 次 run 没有填写后台参数，均通过现有有界等待自动转后台，11 次最终结果全部读到。**这是已确认的程序代劳收益，模型漏填参数没有阻断执行。** 两次实际编辑均没有缩进修复审计标记，本轮不能把成绩归因于自动缩进处理。

### Harness 的剩余错误

模型第一次成功编辑后使用 `with closing(self.connect()) as db:`，没有保留事务提交上下文或显式提交。因此订单和库存更新没有可靠提交；同时仍没有排除 bool。独立评分六项失败涉及库存、重试、bool、冲突及并发。

完整 16 次编辑中：1 次成功、1 次因审批参数组合不完整被拒绝、7 次新旧内容完全相同、7 次旧文本不存在。另外有 1 次把 `run_in_background` 当成工具名而被拒绝。

7 次不存在的旧片段完全相同，且确实出自最初的 `checkout.py`。模型已经改过文件，却一直拿修改前的原始片段做后续替换。这不是整段缩进偏移。Harness 正确拒绝，不能靠自动补空格或偷偷替换成当前片段解决。

双方编辑工具收到的参数都与原始模型回复一致；没有发现框架改变参数、丢失缩进或漏执行已接纳编辑的证据。

## 确定能借鉴什么

### 1. 精简上下文，保留一份任务正文

首轮原始请求中，Harness 的任务正文出现一次；Codey 出现三次，分别位于工作观察中的 `user_task`、`User task (verbatim)`、初始项目提示中的 `User task`。编码请求没有再次暴露不适用的 `source_gaps`，该字段出现次数为 0。

对消息、工具定义及 response_format 做相同的紧凑 JSON 序列化，再用本机模型分词接口统计：

| 首轮请求 | Codey | Harness |
|---|---:|---:|
| 序列化字符 | 46,518 | 22,043 |
| 统一文本分词 | 11,745 | 4,844 |
| 任务正文出现次数 | 3 | 1 |
| 可见工具 | 20，文本合同 | 18，原生合同 |

这是**统一文本分词量，不包含后端 chat template，不是实际输入 token 的精确计费统计**。工具协议与工具范围不同，不能把 2.42 倍全部归因于任务重复。任务正文自身为 1543 字符，仅去掉两份正文约省三千字符；工具说明、示例和文本工具响应 schema 仍占较大体积。

可以学习 Harness 的组织方式：任务正文保留一次；后续工作观察只传当前文件、已有结果、剩余要求；从现有工具定义生成必要的调用说明，减少重复示例和重复解释。权限、证据与完成检查仍由原生产合同约束，不需要让模型填写新字段。

末次有效生成请求的统一文本分词量分别为 Codey 54,941、Harness 45,431。双方都因重复编辑和测试日志积累了长上下文。没有发现本轮触发 Harness 的 spill 或工具结果裁剪的证据，不能把其静态具备的功能当成本次实测收益。

### 2. 借鉴“带来源的提醒”，但要覆盖交替循环

Harness 的 repeat-tool-reminder 在连续相同工具与参数达到 3、5、8 次时追加提醒，不篡改原回执。但本轮模型交替编辑、测试，因此提醒没有触发。

Codey 已有进展检测与重复提醒，不应再建立一套。当前通用比较直接使用 model_text；新的后台 task_ref、execution_ref 和测试输出中的变化，会产生新的信息指纹。结合本轮九次空编辑后的重复后台测试，这说明既有检测需要更准确地区分“新执行身份”和“对修复有帮助的新进展”。这属于减负机会，不是本轮证实的命令执行或收据一致性错误。

建议在既有检测内，结合可靠的工作区版本、命令身份、实际改动记录与正式失败结果，识别“没有改文件 → 同一命令仍失败 → 又做相同空编辑”。在当前回执或下一次上下文中给出具体提醒，指出没有发生新修改，并列出仍失败的项。优先提醒，不禁止有正当理由的重跑，也不抹掉原始结果。

本轮证明这种循环发生了，尚未证明增加提醒就能让模型修好 bool 和并发。

### 3. 重新核查原生工具兼容条件

Harness 的 36 次原生工具生成均正常，没有发生解析卡住；Codey 因 `safe_native_tools()` 对当前 KoboldCpp 1.117.1 与 Gemma4 的已知问题，自动走文本工具。

值得针对**两边不同的原始请求和工具 schema**做最小复现，确认缺陷究竟由何种请求触发，再考虑缩小禁用条件。仅凭 Harness 本轮正常，不能判定 Codey 当时的解析卡住不存在，也不能直接删除兼容保护。

## 不值得直接照搬的部分

Harness 的 edit 同样要求模型复制 old_string；底层主要统一换行后做字面匹配，没有自动处理整体缩进偏移。本轮它的编辑匹配错误更多，没有证据表明换成这套编辑合同能给 Codey 减负。

Harness 允许重复继续，本轮仍耗尽生成预算。Codey 也到达步数上限。单纯放宽轮数不能解决没有实际修复的循环。

Harness 的 jobs 具有统一观察/停止、完成通知、闲时唤醒与大输出读取指引；Codey 已有对应的任务执行、观察、取消和通知链，不能另建一套。此次 Harness 没真正启动后台工作，双方也没走到诊断停止阶段，所以这轮没有得出谁的取消或恢复更可靠的结论。

## 可追溯材料与限制

全部实验材料位于 `.e2e-artifacts/codey-deepseek-harness-20261120/`：

- `pair-first/context.json`：双方 commit、统一任务和夹具初始哈希。
- `pair-first/{harness,codey}/http-*`：原始请求、转发请求、响应和传输状态。
- `pair-first/{harness,codey}/events.jsonl`：工具过程；Codey 另有正式 tasks、effects、calls 与 headless 结果。
- `pair-first/{harness,codey}/independent-check.json`、`file-assessment.json`：独立验收和保护文件检查。
- `pair-first/analysis.json`：调用统计、错误及原始编辑参数一致性。
- `prompt-measurements/`：统一分词输入与回复；分词前后服务生成总数相同，没有重新生成模型答案。

Harness 首次预检工作目录错误，且参考项目缺少声明的 rrule 依赖和生成的 web 元数据；这次预检无效，原始材料保留在 `smoke-first/`。随后修正工作目录，在 ignored 实验目录安装已声明依赖并链接到 node_modules，通过官方生成入口补齐 ignored 元数据。第二次预检与环境日志也保留。没有修改参考项目源码或 lockfile；正式实验启动时插件加载正常，最终 stderr 只记录预设预算拒绝。

本轮没有修改生产源码。没有运行全量 pytest，也没有把上轮生产 Ruff/mypy/pyrefly/ty 的通过结果冒充本轮新检查。实验脚本 Ruff 首轮发现 8 项导入布局问题，整理导入后通过，首次与重跑日志均保留；执行实验时的脚本副本保存为 `*.executed.py`，没有为整理脚本重新生成实验结果。

这只是一次固定采样的小模型实机，不证明整体成功率或项目总体优劣。可以确定的是：Codey 本轮业务测试通过更多；Harness 的上下文更简洁；双方都需要更有效地帮助模型摆脱重复操作。后续应先做无需新工具、新参数的上下文去重和具体循环反馈，再用冻结任务与独立验收验证局部收益。
