# 第二批第三部分：先诊断引用范围，再决定是否改来源链

本次遵循用户的前提：先检查“选对控件、读到目标内容后，是否仍用隔壁字段作答”；只有观察到这类问题才扩大到 passage 范围贯通。没有创建 worktree。

## 实机方法

新增 `tools/browser_query_scope_probe.py`，复用现有本地模型连接、生产 headless/kernel/CodeMode、浏览器和持久回执读取。没有替换执行器或修改工具合同。

两种布局：

- 结果在目标订单内部，相邻订单有不同的送达时间和回执号。
- 目标按钮与结果面板分离，目标结果面板位于另一订单后方；关联由唯一 aria-controls 声明。

每种布局分开运行：

- 自主组：模型自行观察、选控件、点击、读取和回答。
- 固定首步组：第一步固定从实际快照选择 A-173，并调用生产 purpose=result，后续回答交给真实 12B。该组验证读回及交付机制，不计为自主选择成功。

审计从原已提交回执读取 query_region、正式来源正文、实际 read_passages 的范围和最终答复，分别记录：是否进入定向读回、目标内容是否正确、邻居是否出现在实际交付 passage、最终是否出现邻居字段。完整来源包含邻居与实际 passage 包含邻居分开计算。邻居字段标记还需结合原始答复判断，不能把否定引用也自动算成错答。

## 本提交的决定和限制

两轮实验均未复现用户指定的“选对、读对后仍串字段”。因此本提交交付可复用诊断与审计测试，**没有新增区域来源对象、正文范围状态或修改 passage 生成**。这不是证据隔离能力已经完成：每轮两次定向读回的实际 passage 都含邻居记录，范围混入风险客观存在；相同四个单元的两轮结果也不足以证明开放网页不会串值。

`fitting_full_read()` 的默认扩展行为继续保留。若以后依据真实失败实施边界，必须同时约束初次窗口、默认全文扩展、原回执恢复和历史来源版本；不能只改当前提示。这次没有为了满足三个提交的数量而先引入尚未证明必要的来源链复杂度。

本提交仅涉及实验脚本、审计测试和本报告，生产源码与第二部分最终版本相同。验证按实际影响选择，不额外重复全量 full-surface；第二部分最终完整矩阵覆盖当前生产版本。

三个审计回归通过，验证“完整来源含邻居”不能误算为“交付 passage 含邻居”，以及普通读取不能计为定向读回。Ruff 全树通过；采用显式包名和禁止隐式/显式 Any 的模块设置，最终 mypy 691 文件通过。首次包名解析失败、隐式 Any 检查失败及修正记录均保留在 `.e2e-artifacts/bc3/`，没有关闭检查或使用 cast/type ignore。

## 后续引用审计更正

后续复核确认旧实验计分存在缺陷：整份正文含目标事实时，答案仅引用邻居 passage 也可能被计成正确。现已改为复用生产 passage 恢复器，按原来源版本的实际引用切片检查，并离线重审上述两个保存目录。两轮仍分别为 4/4，但八个答案都只引用 s1，exact_passage_cited 均为 false；这些结果不能作为精确 passage 引用归属的通过证明。原记录保留，重算值单独写入各目录 scope-reaudit.json。详见 [复核修复报告](browser-observation-review-fixes-20261114.zh-CN.md)。
