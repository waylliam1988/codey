# Gemma4 12B 综合研究续测：Codey 与 OpenScience

日期：2026-11-01。**12 次正式综合测试、4 次单独登记的预算补测已完成。另一次追加试验遭服务停滞，排除计分。**

**在本次封闭官方材料、普通研究入口的测试中，OpenScience 的综合交付明显优于当前 Codey strict research：正式测试有效交付 5/6，Codey 为 0/6。** 这已经足以定位当前使用体验上的差距；尚不足以建立科学研究全领域的深度排名。

这也改变了首轮只能说“证据不足以排名”的状态。首轮的 [30 次固定材料诊断](research-codey-openscience-comparison-20261101.zh-CN.md)仍然有效，但它给 Codey 预填计划与阅读，不能替代这次普通入口的结果。

完整逐次评阅、正文、候选内容、引用问题和成本见 [综合测试 JSON](reports/research-framework-synthesis-20261101.json)。原始请求、回执、CLI 输出、冻结材料和失败记录在 [restart-1 实验目录](../.e2e-artifacts/research-comparison-20261101/restart-1/)。生产研究逻辑没有修改。

## 1. 如何比较

使用同一个本地部署：`koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，KoboldCpp `1.117.1`。Codey 生产实现仍是 `c346b9e2`；测评脚本起始提交为 `0cac0a27`。OpenScience 为官方 Windows CLI `2.0.153`，对应源码 `a08e0ad0ad3d6448123039ee4659163eb2e35d99`。

正式矩阵是两题 × 三个 seed × 两个框架：

- **SQLite WAL**：读写并发与单写者、版本与完整 OR 条件、checkpoint 停止与恢复、writer 回绕与 checkpoint 的条件差异、性能及选段外推边界。16 个必要事实、5 组关系。
- **Python 3.12.7 asyncio.gather**：异常传播与其他任务、结果顺序、父/子取消差异、done 后 cancel、TaskGroup 的取消保证与性能边界。12 个必要事实、5 组关系。

两边都走真实普通入口，没有预填计划或答案。Codey 使用原严格研究内核、来源工具、知识写入与报告编译；OpenScience 使用原生研究代理、`read` 和最终回答。两边均先通过工具读取相同冻结材料，禁止材料外检索。读取接口分别是原生来源工具与本地文件，呈现形式不同。

公共参数为 seed 74/75/76、temperature 0.3、top_p 0.9、关闭 thinking、每次最多输出 4096 token、配置窗口 32768。**本轮核对了 Codey 实际 connection_budget 为 32768/4096**，不再沿用首轮跟随服务 262144 窗口的配置。完整正文和条件没有为缩短输入而删减。

Codey 继续使用固定请求时钟，OpenScience 保留原生系统中的当日日期，没有做到系统提示时钟逐字相同；这两题不含相对日期。相同 seed 也不代表不同提示、工具或新目录下具有相同采样轨迹。

正式预算为 12 轮/最多 12 次推理、累计输入 180000 token 软门槛、单请求 150 秒、进程 360 秒；OpenScience deadline 为 300 秒。双方均关闭子代理。透明记录代理只统一采样、输出和预算，不翻译或修复工具调用，不替模型选证。

评分按测试前冻结的必要事实和关系逐项人工对照，没有用被测 12B 评分，也不声称独立盲评。不按篇幅给分；**没有完整回答时，语义分记为不可评，不记成模型“全部事实答错”**，交付失败单独统计。

正式 protocol SHA256：`e44346988b92acbc70bb6fd6f95a0d3e6986904abf46806f467bf57c661a953d`。

### OpenScience 并非稳定全对

WAL / 75 写：

> SQLite 版本 3.22.0（2018-07-22）

同一材料第 68 行实际是 `2018-01-22`。版本号正确，因此必要版本事实有分；额外日期错误仍使整份回答不能通过严格内容验收。

这一份回答还把只读条件引用到 70～79 行，遗漏实际位于 80～81 行的 immutable 条件；把 wal-index 的记录位置引用到第 35 行，而名称在第 34 行。来源存在，精确引用范围却不完整，不能把“有行号”自动视为引用支持充分。

三个 WAL 回答都曾把“保留或的关系”的独立小节误解成其他事项。不过其实际条件列表明确写“任一条件/满足其一”，因此 OR 关系仍然成立。这里区分无关扩写与真正改变逻辑条件。

asyncio / 75 的最终文本只有：

```text
<|tool_call>call:read{filePath:"D:\codey\...\evidence.md"}<tool_call|>
```

没有任何 `tool_use: read` 事件，实际未读取材料。退出码为 0、SDK 计数为 0，也不代表完成研究或没有消耗推理；原始后端记录中仍有输入和输出。

## 3. 增加预算是否能解决

看到 WAL / 75 达到轮次上限后，单独登记了 **24 轮、24 次推理、进程 660 秒、OpenScience deadline 600 秒**的探索性补测。先固定两个主题各 seed 75，双方使用同一档预算，问题、材料、评分、上下文、每次输出和累计输入软门槛不变。

| 补测 | Codey | OpenScience |
| --- | --- | --- |
| WAL / 75 | `no_progress`，13 次调用；没有完整报告 | 只输出未执行的工具标记 |
| asyncio / 75 | `no_progress`，10 次调用；没有完整报告 | 完整回答；12/12 必要事实、5/5 关系 |

**增加预算没有解决这两个 Codey 样本的重复检索问题。** 但这些是全新运行，不能说成前 12 步完全相同的反事实重放；路径、提示里的步数、实际时间与执行轨迹也可能变化。补测不替换正式结果，不合并提升总通过率。

为覆盖正式矩阵中另一次 `max_turns`，随后还登记了 asyncio / 74 的双方 24 轮对照。Codey 完成第一次模型响应后，第二次请求遭服务停滞/超时；服务空闲检查在 OpenScience 请求前将其拦住。**这一追加对照排除语义和成本计分。** 因此，尚不能断言正式 asyncio / 74 增加预算也一定无效。

## 4. Codey 的主要负担具体在哪里

### 4.1 任务分段和计划登记仍要求模型维护大量无关对应关系

本次已经把原文从用户任务正文中移出，避免先导实验的 117/151 条要求膨胀。但 Codey 仍为五个实质问题建立了 **28/29 条 coverage requirements**：其中包括编号、说明性引导及材料接口操作要求。

模型必须同时生成 `questions`、同序 `question_details`、rN 归属，还可能生成 work_units 与 submission_mode。错误修复又要求保持这些对象一致。

asyncio / 75 的真实错误包含：

```text
question_details must assign every substantive original requirement; missing: r1, r13, r17, r2, ...
question_details needs one task_refs record per question, in the same order
```

WAL / 76 修复时则连续遗漏 `questions`，最终因重复五次不合法请求停止。它没有进入资料阅读，不能把这次算成“12B 不懂 WAL”。

代码入口：[任务分段](../codey/research/task_requirements.py)、[计划归属验证](../codey/research/local_scope.py:24)。

### 4.2 切题后，已读材料需要模型再找回

WAL / 74 已读完整来源并正确采用 q1。切到 q2 时，冻结视图里 `read_evidence=[]`，同时保留此前 q1 阅读的回执索引和 passage IDs。材料没有从权威存储消失，也有恢复动作，但模型需要自行选用回执恢复、来源定位、知识读取等路径。

实际模型连续六次选择 `knowledge_search`。返回的来源预览只展示开头一部分，候选主张仍主要是刚保存的 q1，并不直接给出只读条件。模型没有稳定转向正确的恢复/阅读操作。

asyncio / 76 出现同类停滞。24 轮补测也重复了这个现象。**这不是来源不存在，而是跨问题复用已读原文仍依赖一次额外的工具选择。**

代码入口：[局部证据投影和回执索引](../codey/research/context_view.py:87)。

### 4.3 知识检索回执重新带回全局结束指令

在上述局部 q2 请求中，`knowledge_search` 的实际返回文本仍包含：

```text
When using saved versions, include knowledge_refs:[{id:...,revision:...}] in done ...
```

同一请求后面的局部工作指导却明确说不需要 global done，应使用 `submit_research_answer`。来源是 [render_recall](../codey/knowledge/recall.py:153) 的 `include_answer_refs` 指导。

这是已经进入模型输入的合同冲突，应该修。实验不能给它分配准确的失败贡献，不能声称移除这句话就能解决所有循环。

### 4.4 正确理解之后，仍可能在保存和采用上耗尽轮次

WAL / 75 先正确采用 q1，随后出现：

- 调用并不存在的 `save_research_answer`。
- 一次提交过多 passage IDs，或把主 passage 再放入 additional 列表。
- 使用只包含 3.7.0 的片段支持同时包含 3.22.0 的结论，遭版本检查拒绝。
- 一度把 OR 条件写成 AND，之后再修成任一条件。
- 保存后尚需明确采用，再切换下一题。

本轮成功登记的计划实际沿用 select 合同，没有自动获得 inline 提交的动作合并收益。提供了可选 `submission_mode=inline`，不等于日常入口的小模型一定会主动选择它。

这组轨迹同时包含语义错误与协议成本，不能全部归为其中一种。

### 4.5 引用版本正确，仍可能只支持结论的一部分

asyncio / 74 保存的 q3 finding 正确描述了单个 Task/Future 取消、CancelledError，以及 gather 取消传播不受 return_exceptions 影响。但它唯一附着的证据窗口在介绍“gather 本身取消”后结束，不含后面的子取消条件，也不含 3.7 的相关说明。

完整来源确实有这些事实，主张并非全部虚构；**附着的精确 passage 却不足以支持整条主张。** 该运行没有发布最终报告，缺陷已在候选保存阶段形成。

这再次说明不能把保存、引用版本或编译通过视为独立语义核验，也不能用 WAL 的专项版本检查推导跨主题的支持范围检查已经可靠。

## 5. OpenScience 的工具失败还有工程线索

两次只输出工具标记的样本，都生成了带未转义反斜杠的 Windows 绝对路径。离线提取上游 KoboldCpp `1.117.1` 的两个已审阅 Python 函数，保留原实现重放：

| 输入变体 | Python 规范化结果能否解析为 JSON |
| --- | --- |
| 实际失败输出 | 否 |
| 等价相对路径 `evidence.md` | 是 |
| 转义后的同一绝对路径 | 是 |

这解释了一个可复现的解析失败路径；此前真实 `read` 烟测使用相对路径也成功。但完整服务还先经过原生 C++ parser，本次没有执行其完整离线路径，因此不声称已穷尽根因或证明修改后稳定通过。

测评代理没有偷偷改写路径、补工具调用或重发成功样本。后续应在明确的原生协议/服务边界处理错误，并保留原始输出；不能靠“completed”或看起来像工具调用的文本推进研究状态。

## 7. 对“到底哪个好”的回答

**当前同一 12B 部署下，若目标是在给定官方材料上产出多问题综合回答，OpenScience 在本轮更好用，也展示了更多可评阅的关系分析。** Codey 的严格研究流程尚未把这些能力稳定转成完整报告。

但不能得出以下结论：

- OpenScience 已经解决缺证据、精确引用和工具可靠性。首轮缺证据题三次都给了不受支持的原因，本轮也有错误日期和未执行工具。
- Codey 六次未交付等于六次都完全理解错误。局部正确发现和已采用答案清楚存在，失败大量发生在计划、选证引用、切题与动作选择。
- 更多轮次对 Codey 永远无效。本轮两例没有改善，另一次干净进展样本的预算扩展因服务故障未完成。
- 两个资料主题已经代表自主检索、文献创新或实验研究。那些仍未测。

**这组结果支持继续减少 Codey 要模型维护的协议决定，而不是继续假设 12B 无法组织任何复合回答。** 同样，也不支持为追求顺畅而取消原有出处、缺口和唯一发布边界。

## 8. 下一轮最值得做的修改

优先在原内核内收敛四件事，再沿原第 6 步内容验收，不能因为比较中相对胜出就降低绝对标准。

1. **清理所有模式相关回执。** 从同一冻结 scope 决定局部指导，知识 recall 不再重新引入全局 done。核对实际发送请求，不能只改提示模板。
2. **计划登记只维护一份对应结构。** 原问题、requirement 归属与可选局部目标成组记录；其他视图单向派生。明确的格式和执行要求继续由原验证器处理，保留原始任务与出处；不要要求模型把编号、材料接口说明再研究一遍。
3. **已读原文按原版本直接复用，减少恢复选择。** 新目标的冻结视图能从原回执/知识版本获得必要的完整原文；保留条件和例外，避免只给陌生 passage IDs，再让模型在多种检索动作中试错。不另建可写证据副本。
4. **把省动作的合同落实到入口。** 内容验收后，由冻结入口明确采用 inline 局部提交，让模型一次明确声明正文、依据和 state。正文仍只写原 KnowledgeStore，选择仍记原结算回执，最终仍编译唯一 FindingReport；保存成功不自动升级成 answered。

不需要第二个研究循环、另一份答案表或最终整篇自由重写。OpenScience 这次最有启发的部分，是用较少协议决定就能从材料走到回答；Codey 应在保留事实归属的前提下减少多余决定。
