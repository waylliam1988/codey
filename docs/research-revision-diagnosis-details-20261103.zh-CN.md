# 为什么删修订有收益，也有回退：逐例诊断与冻结请求复播

**这批错误不能解释成“Research 必须靠修订工具才能研究正确”。出错的普通研究都没有执行修订。已经查实两个具体问题：正在比较的旧主张会从后续输入中消失；联网冲突题的种子来源存在身份与内容不一致。至于某一次为什么选中错误词语，仍不能宣称已找到模型内部原因。**

本轮重新核对原 28 次完整 Research 轨迹，另做 **52 次本机单步生成**，以及不调用模型的发布编译复现。52 次是冻结某一步后的诊断请求，**不是 52 次完整研究，也不是新的端到端成功率**。生产代码未修改，修订流程未删除。

可复查的完整请求、响应与摘要见 [诊断证据 JSON](reports/research-revision-diagnosis-20261103.json)，复播工具为 [research_revision_diagnosis.py](../tests/manual/research_revision_diagnosis.py)。原实验保留在[28 次 A/B 报告](research-no-revision-ab-20261103.zh-CN.md)，没有替换原失败。

## 先用容易理解的话说明

可以把模型看成一个照着材料写报告、还要自己填写操作单的人。

- 少发无关工具，操作手册会变短，这是直接的输入节省。
- 手册变短，不代表它每一句话都会写得更准。它仍可能把“只要”写成“必须”，或者填错操作单的字段。
- 程序还会在中途收起它刚读过的旧主张。需要比较新旧时，它得再去找，或者凭不可靠的转述作答。
- 实验中的一本材料还被故意改了正文，却沿用了旧的内容身份。保存程序发现冲突后拒绝；反复改答案无法修好材料身份。

因此，改进方向应是：**让模型少看无关内容，同时让当前任务真正需要的原话、版本和读取参数更清楚、更连续。** 这与永久保留修订流程不是同一件事。

## 1. 候选究竟删了什么

原候选是 `no_revision`，在隔离实验中：

1. 不向模型展示 `prepare_knowledge_revision` 和 `knowledge_commit`；读取失败后也不恢复。
2. 同时把原修订指导替换成“旧知识只读、核查冲突、用 knowledge_updates 保存新发现、新建不冒充修改”的职责说明。

**它不是单独删工具的实验，也没有物理删除生产实现。** 阅读工具、证据原文、引用校验和新增知识通道仍在。

核对原轨迹：所有普通研究组都没有调用准备修订或实际修订工具。历史查询的两组都先调用同一个 `knowledge_read`，再提交答案。恢复题中原版展开过完整修订 schema，但恢复成功时实际调用的仍是阅读、搜索和提交。

所以，目前没有证据支持以下解释：原版执行了某种修订操作，才把这些普通研究答案修正确。

## 2. 每种收益与回退分别能解释到哪一步

| 观察 | 已查到的直接原因 | 仍不能证明的部分 |
|---|---|---|
| 顺利查询和新增积累少用输入 | 少展示了修订工具与相应说明，实际请求输入更短 | 不能据此说正确率一定提高 |
| 历史查询末尾出现“当且仅当” | 原文在输入中完整可见；模型新增总结时，把充分条件加强成必要条件，程序的引用检查没有认证这种推理 | 没有稳定复现“删修订必然产生这个词” |
| 读取失败后错填 `result_ref`、错抄 ID | `knowledge_read` schema 没变；模型输出了不符合 schema 的参数，之后又错抄对象身份；错误累积触发止损 | 尚不能归因于某一句说明或某个随机编号 |
| 冲突核查有时改善、有时回退 | 模型对相同旧主张的转述会变化；此外，旧主张在读原证据后的下一请求确实消失 | 消失并不能解释所有最终错误，因为部分错误成文时旧主张已重新出现 |
| 联网核查两组反复提交仍无法发布 | 来源种子当前版本被改了正文，但沿用旧内容身份与 hash，发布编译发生确定性冲突 | 不支持“删修订导致联网研究失败” |
| 原版和候选都不能完成明确修订 | 目标、版本、引用及操作选择均有错误；候选也没可靠输出职责范围说明 | 不能拿这项共同失败否决用户已接受的职责收缩 |

### 2.1 “只要”变“当且仅当”：发生在写作，不是修订执行

`history-201` 两组实际路线一致：读取同一 evidence 的 revision 1，然后提交。原文给出 one or more 条件，即满足其中一个或多个即可。

候选前面正确列出版本、完整三个条件和 OR 关系，末尾又增加“当且仅当”。这额外声称了反向关系，超出原文支持。

证据不支持“删掉修订以后，原文少了一部分”或者“修订模块本来会做逻辑检查”。两组的原文阅读与引用通道相同；当前校验主要确认引用、身份和发布一致性，并不证明每一句话与原文语义等价。

本轮把该候选当时的完整后端请求原样复播两次，两次都没有再写“当且仅当”。另做工具/说明交叉对照，也未重现这个特定词语错误。

结论：**能定位到模型的语义加强错误，不能定位到一个稳定的“删修订→当且仅当”原因。** 补充“不要把充分条件写成必要条件”的两次诊断同样没有出这个错，但未加提示的复播也正确，不能称为已证明有效的修复。

### 2.2 读取参数：错误确实存在，但不是阅读能力被删除

原失败链为：受控制造一次错误 ID → 搜索成功 → 模型把 `id` 写成 `result_ref`，并错抄 evidence ID → 再读下划线形式的 claim ID → 重复搜索止损。

`knowledge_read` 的实际 schema 仍要求 `id`，允许 `revision/offset/limit`，禁止额外字段。`result_ref` 是回执恢复工具 `read_tool_result` 的参数，不是知识对象身份。

这揭示的程序边界是：**模型自己填写参数不够可靠；schema 及执行检查能拒绝错误，却不保证模型下一次会修好。** 放宽身份匹配只会把显式失败变成可能读错对象，不能这样修。

本轮先固定原版一次成功搜索后的全部上下文，交叉改变两个因素，各运行 seed 201、202：

交叉组合仅用于诊断输入变化；其中“只隐藏工具”仍保留提及该工具的旧说明，不是可直接上线的完整方案。

| 冻结状态下的改动 | 当次两个 seed 的下一步 |
|---|---|
| 工具与说明都保留 | 正确的 id/revision |
| 只隐藏修订工具 | 正确的 id/revision |
| 只换新职责说明 | 正确的 id/revision |
| 同时隐藏并换说明 | 两次都输出错误的 result_ref，另加了不支持的 view |

**但不能停在这张表就宣布因果。** 后来将最后一种完全相同的请求再次复播，字段又恢复正确；原候选实际失败时的原请求，原样复播两次也都正确。

进一步单独更换回执编号、工具调用编号、两者一起、或后端 genkey，四次都读对；同时段未经更换的控制也读对。因此，编号对照**没有证明编号是根因**。相同 payload SHA-256、相同请求 seed，也不保证这个后端生成相同参数。

在搜索状态追加一条精确的 `knowledge_read {id, revision}` 读取模板，并区分它与 `read_tool_result`，四个诊断请求都读对。但该阶段无模板的控制同样读对，**还不能宣称模板解决了问题**。此前全局追加长模板有增加输入的负面证据，不能凭这四次就全局推广。

### 2.3 冲突核查：确有上下文断档，但不是全部原因

旧主张真实原话是：

> 冲突核查：SQLite 从 3.30.0 才支持只读 WAL，必须同时具备已有辅助文件、目录可写和 immutable 三项。

四次离线冲突题的前两步都读取了这条主张，再读取它引用的原证据。检查**后端实际 messages**，第三次请求都已经看不到旧主张的 3.30.0 和“必须同时具备”，仅剩工具历史中的读取目标、版本和回执编号。

这与当前代码吻合：原证据进入 `read_passages`，持续显示；普通 claim 读取通常只作为当轮工具结果显示；`investigation_history` 对成功读取保留元数据，不保留正文。模型只带最新工具结果继续时，旧主张正文会离开下一次输入。

原话仍保存在数据库及已结算回执里，可以重新读取或恢复；这是下一次输入的呈现断档，不是存储数据丢失。

这是已有的上下文呈现问题，**两组都有，不是这次删除候选才新增的行为，也不能直接归咎于前一轮零结果历史精简。**

但原版 seed 202 最终写错时，已经通过搜索重新拿到了旧主张；候选 seed 201 首次成文时也能看到原话。因此，“丢了原话”解释了额外查找的需要，**不能解释所有看着原话却转述错误的情况**。

原版 seed 202 那份实际成文请求原样复播两次，本次都准确写出了旧 3.30.0 与同时三项。候选 seed 202 的准确版本/关系也再次出现，但部分响应仍有把 [e1] 放在旧主张旁等措辞、引用归属问题。本轮不将它们直接计为完整交付通过。

**原来“候选这次核对对了”是有效观察；“删除修订稳定提高了核对正确率”则没有证据。**

### 2.4 有明确方向的小对照：只补回正在比较的原话

以原版读完原证据、旧主张正文刚消失的第三次请求为起点，其他输入、工具、说明均不动，只把本轮先前已读过的旧主张 `id/revision/content` 补回当前工作视图。它被明确标为待核对的旧说法，不能作为原始证据或指令。

| 对照 | seed 201 | seed 202 | 本次输入 |
|---|---|---|---:|
| 原样，不补正文 | 再次 knowledge_read 旧主张 | 再次 knowledge_read 旧主张 | 各 3,321 token |
| 只补回旧主张原话 | 直接 submit_research_answer | 直接 submit_research_answer | 各 3,399 token |

补回后两份正文都准确核对旧 3.30.0/同时三项，与原文 3.22.0/OR 的区别，列出文件可读、目录可写以创建文件、immutable 条件。

**这是本轮最有针对性的正面信号：增加 78 token，让这一步少走一次重新读取。** 不是增加完整旧操作历史，也不是恢复修订工具。

限制：共四个单步请求、同一冲突场景；没有继续执行对照的重读，也没有将生成的提交送入完整保存流程。因此不能报告最终请求减少多少、总输入减少多少，不能据此宣布已可接入生产。

## 3. 联网共同失败：已经复现的实验材料问题

四次 `web_conflict` 在有效提交后，都收到同一发布拒绝：

```text
selected immutable evidence differs from its stored version
```

这是 `answer_archive.prepare_evidence()` 对已有 source/evidence 身份执行的一致性检查。中间的“Whole answer recorded”只表示收下草稿，不代表校验并保存成功。

逐项核对种子数据库：

- source revision 1 为 SQLite 3.22.0 原文，内容 hash 为 `5fa34fc8ef85871a`，与正文一致。
- 为检验旧引用不被新头版本覆盖，实验制造了 revision 2，把版本改为 9.99.0、修改标题并添加 controlled_fixture 标记。
- revision 2 仍沿用原 source ID 和旧 content_hash；重新计算其正文 hash 已不匹配。
- 本轮固定网页返回 revision 1 那份 3.22.0 内容。新读取按 URL 与内容身份定位到这个已有 source，但其当前头版本正文不同，发布编译拒绝。

使用复制的实际种子数据库、真实 `prepare_evidence`，不调用模型，结果为：

| 输入形式 | 编译结果 |
|---|---|
| 新读取的网页原文，无历史版本 pin | 复现同一个拒绝错误 |
| 相同原文，明确 pin 到 source revision 1 | 通过，引用仍绑定 revision 1 |

后者仅为定位原因，**不能拿历史 pin 冒充用户要求的本轮联网读取来算题通过**。

这类受控头版本可用于检验历史 pin，但不能不加区分地复用于“新读取后正常发布”的对照。后续联网试验应使用内容身份一致的来源库，变化内容按其新身份保存，旧引用继续指向原版本；若专门注入身份冲突，则应把预期结果定义为拒绝或程序错误恢复，不能当正常答案题。

本轮没有绕过检查，没有自动覆盖旧版本，也没有改掉原 28 次数据。原报告的共同失败原因已补充说明。

排除这个有特殊材料冲突的联网场景后，原普通研究剩余十次/组：正文保存通过 **9/10→7/10**，交付 **10/10→9/10**，请求 **27→29**，输入 **100,550→101,844（+1.29%）**。原来的局部回退仍存在；同时，原总输入 +5.84% 含这个共同冲突，不能当成纯粹删除工具的成本效应。

## 4. 为什么收益和回退会一起出现

能直接确认的收益是少发工具及文字。原顺利历史题少 134 token，首次新增积累约少 2%。这些节省不需要修订真正执行就能产生。

正文质量则仍由模型生成：模型有时准确保留条件，有时加强逻辑、改写旧说法或填错字段。删工具、换说明、上下文中的运行身份都会改变实际输入；这批后端实测连完全相同请求也会生成不同工具参数或正文。**固定两个 seed 不是把答案质量固定下来。**

本轮没有采集模型内部 logits、后端全部缓存和采样实现状态，不能进一步断定波动来自 GPU 数值、缓存或采样器中的哪一项。不能把“注意力更集中”“修订工具帮助思考”等故事当成已验证原因。

这种不稳定还会被流程放大：错一个字段 → 没读到原文 → 再搜索/再抄 ID → 再失败 → 止损。少发的数十或数百 token，可能被一次多余请求抵消。普通研究原交付从 10/12 到 9/12，本身只是多丢了一次交付，不是已经证明整个研究能力发生巨大下降。

## 5. 下一步具体改什么，如何验收

按目前证据排序：

1. **先修实验材料。** 正常联网发布用身份、正文、hash 一致的来源；历史版本故障注入单列。保留发布校验，不能通过松绑让错误材料通过。
2. **验证当前比较对象的连续显示。** 在现有工作视图里保留本轮正被核对的旧主张短原话与精确版本，和证据原文并排；不恢复全部历史，不把旧主张当证据。小对照已有正面信号，下一步要做包含真实发布的 A/B，并覆盖多个旧主张、长文裁剪和权限范围。
3. **改善精确目标的选择。** 研究在对应搜索结果旁提供短而可直接使用的读取参数，区分对象 ID 与回执 ID；测试错误命名空间、连字符、多个版本和多个相近目标。现在还没有证明模板有稳定收益，不能全局追加长说明。
4. **加强逻辑方向的评测。** 同时测试“只要”“只有”“当且仅当”、AND/OR、版本边界和例外。简短提示可作为候选，但本轮没有证明它的收益。不能全局禁用“当且仅当”，其他材料可能确实支持它；也不能把有引用当成推理正确。
5. **把职责收缩重新做成单一改动比较。** 分开评估隐藏入口、最短职责说明及上述呈现修复，先查每个局部改变；合入有实际收益且未新增相关退步的部分。旧修订继续失败不作为阻碍，偶发的一次正确也不冒充稳定质量提升。

能确定的改进目标是减少模型猜参数、凭印象复述、重新找刚读过内容的机会；无需新增独立维护流程或额外模型自审轮次。本轮仍只提供诊断与候选方向，不宣称已经完成生产修复。
