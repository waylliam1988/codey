# Codey / Pi 本地 Agent 稳定性实测（2026-10-09）

本轮 10 个场景、每场景 2 次配对，共 40 次原生 Agent 运行：**Codey 通过
11/20，Pi 通过 10/20**。Codey 在普通修复、无需修改和多文件任务中较好；Pi
在 503 自动恢复、编辑后续接和停止速度上较好。这个样本不能证明全面领先。

本轮修改的是比较脚本与评分，不是产品算法。`codey/` 生产代码未修改。
全量 pytest 已按用户最新要求停止，没有完整回归结果，也没有发布。

## 场景结果

“通过”要求满足场景的全部条件；正确补丁不等于任务完成。修复任务需要原生
正常终态、独立验收通过、Agent 实际执行过针对最终文件的测试、修改范围合法。
停止任务要求控制信号确实触发、原生停止确认、进程退出且无需看门狗补救。

| 场景 | Codey | Pi | 实际观察 |
|---|---:|---:|---|
| 普通修复 | 2/2 | 2/2 | Codey 32.97 / 48.16 秒；Pi 87.20 / 83.78 秒 |
| 先测红，再修复 | 1/2 | 0/2 | Codey 两次补丁和实际验证都正确，一次以 `no_progress` 结束 |
| 已正确，无需修改 | 2/2 | 0/2 | Codey 保持文件；Pi 两次重写了禁止修改的测试文件 |
| 只诊断、禁止修改 | 0/2 | 0/2 | Codey 两次修改了源文件；Pi 保持文件但未正常给出 blocked 终态 |
| 多文件修复 | 2/2 | 0/2 | Codey 修复两个文件并验证；Pi 的 adapter 补丁错误且未完成有效验证 |
| 保存的长输出中段恢复 | 0/2 | 0/2 | Codey 分页读取超时；Pi 修好代码但没有读取要求的中段结果 |
| 首请求收到 503 | 0/2 | 2/2 | Codey 明确失败后结束；Pi 自动重试并完成 |
| 停止正在运行的测试 | 2/2 | 2/2 | 都停止了测试进程；Pi 的停止确认和退出更快 |
| 编辑后进程中断，再续接 | 0/2 | 2/2 | Codey 最终补丁和实际验证正确，却两次以 `no_progress` 结束；Pi 正常完成 |
| 停止后用户改变需求 | 2/2 | 2/2 | 都改用下划线并验证；Codey 33.25 / 33.40 秒，Pi 15.76 / 17.23 秒 |

20 对中：双方通过 6 对、仅 Codey 通过 5 对、仅 Pi 通过 4 对、双方未通过
5 对。没有因缺失配对或隔离失败而剔除的正式配对。

只对双方通过的同场景比较速度：普通修复中 Codey 分别少用 **62.19% / 42.51%**
时间；用户改口场景则多用 **111.03% / 93.85%** 时间。不同场景的时间不混成
一个“整体更快”的结论，失败得快也不算速度优势。

停止延迟单独从控制器发送停止请求算到 Agent 进程退出：Codey 两次均约
**1.797 秒**，Pi 为 **0.282 / 0.250 秒**；双方均没有残留夹具测试进程，也没有
借用看门狗强杀来获得停止成功。这是端到端关闭时间，包含各自收尾工作。

## Codey 的优势与需要加强的地方

Codey 本轮的优势是能在已有正确实现上停止修改、完成多文件修复，以及普通
修复的端到端速度。它的正常完成仍包含真实 Local review，没有为跑分关闭审核。
“先测再改”也好于本轮 Pi，但 Codey 仍有一次未正确收尾。

Pi 多个失败记录中，模型忽略了任务指定的 `python -m unittest discover -v`，
反复调用 Windows 上不可用的 `python3`，返回退出码 49。普通修复等成功场景
证明其 `python` 路径可用；这属于本环境中命令选择和错误恢复的表现，不能推广
成 Pi 在其他系统上也较差。无需修改场景还直接重写了 `test_app.py`，不能仅用
解释器问题解释这个失败。

Codey 的改进优先级建议如下，每项都应另行以确定性测试锁定后改生产代码：

1. **用户限制与执行权限一致。** “只诊断、不得修改”的两次任务都实际改了
   `app.py`。应在有明确只读任务契约时落实到工具权限，并测试 read/run 可用、
   edit/write 被拒绝、终态准确为 blocked。不要只依赖模型遵守一句提示，也不要
   把所有自然语言限制猜测成权限规则。本轮两次模型输出是稳定观察，不等于已经
   证明某个函数存在确定性的实现 bug。
2. **支持在任务所属的已保存输出中检索。** 长输出记录显示 Codey 从 offset 0
   开始按 4000 字符递增读取，直到超时。现有 `read_tool_result` 支持有界分页与
   身份/digest 验证，却没有关键词定位能力。建议在同一只读工具上增加有界查找，
   返回匹配位置与邻近片段；保留任务范围、完整性校验和“读取失败不授权重跑”。
   不开放任意文件路径，也不为此暴露整份输出给模型。
3. **明确失败可安全重试，结果未知不重发。** 注入的 503 是完整拒绝响应；
   Codey 的 transport 将其作为 `GenerationRejectedError` 上抛，Agent 直接结束。
   可以为可重试且明确未执行的失败增加有限重试，测试取消、次数上限、物理请求
   用量归属及 `Retry-After`。网络断开后的结果未知仍应保持不自动重发。这不能
   简化成“所有 API 错误都重试”。
4. **验证成功后的收尾与恢复连续性。** 先测再改的一次运行、编辑后续接的两次
   运行，最终补丁和真实测试都通过，之后仍出现重复/无效工具调用并以
   `no_progress` 结束。下一步应回放这些调用序列，检查有效验证证据、恢复指令、
   completion 契约与无进展保护如何交互；保留必要审核，不能把看到 `OK` 就直接
   宣布完成作为优化。停止和用户改口的收尾耗时也值得分阶段测量。

长输出失败直接暴露的是结果检索能力，当前证据不足以断定是上下文压缩算法
造成。此报告与此前压缩函数比较分开，不把函数级压缩收益当成完整 Agent 胜率。

## 计量与公平性

- 同一已加载模型：`koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`。
  KoboldCpp **1.117.1**，Jinja 启用；Windows、Python **3.12.8**、Node **24.19.0**。
- 采样 temperature 0、seeds 41/42；串行运行、每对交替顺序。每侧总时限
  180 秒、物理生成请求最多 24 次，输出上限 2048、声明上下文窗口 32768、
  最近上下文目标 12000。模型后端实际窗口较大；本实验使用相同声明预算，
  并不声称两家的内部裁剪策略完全一样。
- Codey 只启用 Local，writer 和 reviewer 使用同一模型。两者保留原生提示、
  工具、循环与完成条件；薄控制器只设置采样、记录事实、请求停止/中断。
  HTTP 代理不修改已准入请求。额外审核调用计入 Codey 的时间和用量。
- 每次先等待 KoboldCpp `idle=1, queue=0`，结束后再次确认。超时进程由隔离
  看门狗清理；看门狗行为不能算成产品成功。
- 独立验收有 7 项保留输入检查；外部测试不能替代 Agent 自己的验证。测试记录
  保留源码哈希，文件后来改变就不再算新鲜验证。
- 长输出场景明确要求读取保存的中段记录。测试源码及失败断言可能透露答案，
  所以仅补丁/测试通过不算恢复证据。Pi 两次因此未通过这个完整场景。
- **不能比较总 token 成本。** Pi 的工具流式响应即使请求 stream usage，
  KoboldCpp 仍未返回 usage；全部 20 次 Pi 运行总用量均不完整。Codey 16/20
  完整，其余是未发生实际生成或超时缺失。未知保持 `null`，已有部分单独记载。
  不把 Pi SDK 填写的 0 当服务端实际用量，也不以不完整数据声称谁更省 token。
- 工具事件的可观测性也不同：Codey 有 101 个调用的有界事件缺少完整参数。
  因此已知参数下的重复调用只是下界，不能用其少于 Pi 的数值直接证明全面更稳。

## 版本身份、诊断轮次与重算

Codey 生产版本为 `699b83ace686bd4520f0775a01bc267e7d0cf12a`，包源码摘要为
`d0bfa32e9ddbf48c48a130245f8f347585bffcf3594f596d88d46750743414d9`。
Pi 源码 checkout 为 `a276dabe57911253350bffb93cb7d7aff6a73261`，但本轮实际
执行的是用户目录里已有的 **dist 构建**：
`189b8f8868f437c28ebbbd6be6fa9e357b7047fd2aab484ff1e31abb34020eb3`。
构建对应的源码 commit 未知；CLI 显示 1.0.0 不能证明它对应当前源码。
因此结论是与本地已有 Pi 构建比较，不能称为与最新 Pi 源码比较。

源码入口缺少生成目录，离线预检不能启动。脚本没有在线补依赖或自动换版本，
正式运行显式选择 `--pi-entry dist`，使用与构建配套的资源，记录两种身份。

前面的 pilot、v1、v2 均保留为诊断，不进入上表：曾发现 stdin 未关闭、构建与
源码主题资源不匹配、超时后后端仍忙，以及 Codey 隔离配置中 Local 未启用导致
review 探测网页来源。配置修正经红→绿后才运行 v3；早期多约 73 秒的 review
探测等待不能归因于 Codey 压缩算法，也不能拿来与正式结果混合。

`truncated-call` 场景脚本仍支持，但未进入这轮正式 10 场景。此前诊断中其后
KoboldCpp 长时间 busy/queue，用户重启后恢复；根因尚未证明，不能将其算作
任一 Agent 的缺陷，也没有给它补造配对分数。

实测后还通过 TDD 修正了评分器：Pi 在取消工具期间可能给 assistant `error`，
随后返回成功的 typed RPC abort 确认和 settled 事件。旧评分器只认 `aborted`。
对所有 40 次已保存事件、请求和验证事实按同一规则重算，**仅两次 Pi 停止由
失败改成成功**，未重跑模型。新增规则同时要求触发停止、无残留进程、无强制
补救且无越界修改；旧 abort 不能影响下一次任务。普通任务也不能借用看门狗
清理遗留子进程后被算为完整成功。

正式执行脚本摘要与重算器摘要分别保留在
[可携带的数值证据](reports/codey-vs-pi-agent-stability-2026-10-09.json)；原始记录留在
`artifacts/pi-agent-stability-20261009-v3/`，包括 `result.json`、`result.rescored.json`、
执行脚本快照、HTTP journal、原生事件、stdout/stderr 和验证回执。

## 脚本与验证

脚本已从 `tests/manual/real_local_ab.py` 重命名为
[`codey_vs_pi_agent_stability_ab.py`](../tests/manual/codey_vs_pi_agent_stability_ab.py)。
任务夹具、HTTP 观察、指标与 Local 控制器分开；无旧文件转发或第二套 Agent 循环。
默认支持 11 个场景；此轮使用以下显式选择：

```powershell
python -B tests/manual/codey_vs_pi_agent_stability_ab.py `
  --run-dir artifacts/pi-agent-stability-new-run `
  --pi-entry dist --seeds 41,42 --timeout 180 `
  --cases normalize-name,test-first,no-op,scope-blocked,multi-file,long-output,http-503,cancel-running-test,resume-after-edit,correction-after-stop
```

已有目录不能覆盖；只接受 loopback HTTP 后端。实验未全部成功时脚本返回非零，
这不等于评分工具自身报错。源码入口与已有构建必须显式选择。

新测试按内容命名为 `test_codey_vs_pi_agent_stability_metrics.py`、`_paired_summary.py`、
`_proxy.py`、`_runner.py`、`_verification.py`、`_local_isolation.py`；原 helper 测试同步
重命名。红→绿锁定了假完成、陈旧验证、范围修改、缺失/零用量、HTTP/SSE 保真、
请求归属、stdin EOF、子进程清理、继续与新需求的区别、后台隔离和停止判定。
原有消费者的请求输出配置与不完整 usage 汇总也先补测试后修正。

最终定向回归 **68 passed in 7.45s**。Ruff 全树通过；mypy Windows/Linux 各
**402 files** 无问题；直接 Pyrefly **0 errors**（47 suppressed / 838 warnings not shown）；
compileall 和 staged/working diff 检查通过。此前必跑机器契约 **798 passed in 171.38s**。
全量 pytest 启动后收到用户“不需要全量 pytest”的新指令，已停止，不记录为完成。

仍未测量跨模型切换、运行中 steering 与队列差异、含歧义编辑注入、专门并行负载
和大型真实仓库任务。仅两次回放、一个本地模型与当前 Windows 环境，不能给出
统计显著性或全面优于 Pi 的结论。
