# Research 12B 实施清单：每一步做什么，什么条件下继续

这是前两份诊断之后的实施顺序，不是新流程已经完成的声明。起点为 `4d54b126`。本轮只写清单，没有修改生产逻辑或调用模型。

目标：让固定 12B 在同一生产 kernel 中，以局部证据处理一个关系，允许有依据地回答或明确留下缺口；所有选择可恢复，最后只产生一份冻结报告。

## 如何执行这份清单

每一步都留下：变更说明、相关测试结果、失败记录、原始回执或实际请求、继续/停止结论。生产代码每批提交一次；改代码和跑跨进程恢复测试分开进行，恢复测试期间冻结生产源码。

离线测试可以证明合同和恢复边界；真实模型实验才检验内容收益。两者不互相替代。以下内容标准是建议的有限样本验收门槛，不是通用能力保证。

先执行 0～2，解决实验可比性和基础输入/反馈。第 3 步做一条最小完整流程，第 4 步才拆关系，第 5 步才裁剪历史。第 3～5 步可以分提交，但应在同一开发分支完成闭环后再作为新的生产 strict research 流程交付。

| 步骤 | 本步交付 | 进入下一步所需证据 |
| --- | --- | --- |
| 0 | 固定试题、原文、评分和基线 | 同一输入可复现，评分点没有歧义 |
| 1 | 同源字数与明确修复反馈 | 计数一致，修复指令不冲突 |
| 2 | 保存前完整证据可恢复投影 | 截掉旧消息仍能重建已读证据与继续定位 |
| 3 | 每 qN 一个 unit 的局部提交完整链 | 有答案/空证据都能结束，父报告/恢复正确 |
| 4 | 原计划内的关系拆分和缺口汇总 | 拆小后原问题没有遗漏，混合结果正确汇总 |
| 5 | 局部工具合同与实际历史投影 | 实际输入隔离、协议完整、恢复沿原请求 |
| 6 | 固定证据、候选及两因素对照 | 内容达标且不是靠过度 unknown，成本可接受 |
| 7 | 完整 WAL 与故障恢复验收 | 原要求、字数、语义和唯一发布同时通过 |

## 第 0 步：先固定“什么叫成功”

### 做什么

建立五个最小案例，用已经保存的官方来源快照，保留精确哈希和原文范围：

| 案例 | 给模型什么 | 人工判分必须检查什么 |
| --- | --- | --- |
| S1 单写者 | 完整直接限制段落 | 一个 writer；不混成读写并发 |
| S2 只读条件 | 完整版本与条件段落 | 版本、适用范围、三个替代条件、“或”的关系 |
| S3 checkpoint 停止 | 完整相关段落 | reader end mark 与停止边界 |
| S4 checkpoint 恢复 | 完整相关段落 | wal-index 保存进度、下次调用继续转移 |
| S5 缺证据 | 只有读写并发的邻近片段 | unresolved；不声称整页不存在限制，不以邻近事实冒充回答 |

另保留两个完整复合题：“引入版本及只读完整条件”“checkpoint 停止及恢复”，后面用来检查拆分后合起来是否完整。原完整 WAL 任务作为最终验收题，不在每改一行后反复跑。

每个案例先规定三个采样 seed，例如 74、75、76。候选材料的顺序独立固定，不能跟采样 seed 一起改变。

每次记录模型 id、已有 generation settings、部署参数、源码身份、来源哈希、候选顺序、实际请求、usage、工具回执、最终选择、是否发布、人工逐点判断。使用独立实验 state/knowledge 目录，不写入用户日常知识库。

### 改哪里

优先扩展已有 `tests/manual/research_evidence_local.py` 和现有 stage/生产 kernel 入口：将候选排序 seed 与模型采样 seed 分开。不得为实验实现另一个研究执行器。

评分表是实验资料，不导入生产代码，不成为运行时第二份正确答案。fixture 提前提供的规划和阅读必须继续标明 setup，不能算模型自主检索。

先记录当前基线 R0。历史失败用于挑案例，只有源快照、参数和代码身份明确的运行才可用于受控比较。新增 S3/S4 等窄题可以沿用脚本扩展，但不能把历史复合题结果冒充其基线。

### 进入第 1 步的标准

- 五个案例有冻结原文、明确必答点和禁止扩大范围。
- 同一配置能从归档资料还原其输入、选证和结论。
- 能分开记录“正确完整”“正确但不完整”“答非所问/不受支持”“合理缺口”“有证据却未回答”。
- 基线允许失败；本步是把失败测清楚，不要求先把基线跑成功。

若分不清一次运行是服务超时、协议失败还是内容失败，先修实验记录，暂停生产逻辑改动。

## 第 1 步：先让修复反馈说清楚

### 做什么

1. 提取唯一的结论计数函数：非空白字符，排除引用，口径沿用原合同。过程反馈与最终检查都调用它。
2. 保存回执显示本条字数；最终拒绝列出当前总数、上下限和选中条目的贡献。中途不因为未达到整篇下限而拒绝局部成果。
3. 清理“保留原答案、修 coverage”对所有错误统一追加的提示。
4. 让领域错误保留 code/path/允许动作。至少区分：重选、读取精确引用、依原文另存、补读。
5. 修复 `ResearchIssue` 默认“无需写入”与“保存简短替代 finding”相互冲突的问题。

### 改哪里

`task_requirements.py`、`findings.py`、`report_proposal.py`/`finding_report.py`、`issues.py`、`research_completion_checks.py`、`completion_gate.py`、`kernel_prompt.py`。

本步不增加新完成循环、不改接受标准、不扩大语义关键词规则。反馈里的预算和贡献直接从原精确选择计算，不持久化另一份计数状态。

### 验证什么

- 640 和 960 接受，639 和 961 拒绝；引用、空白、partial 和缺口通知计数口径一致。
- coverage 错误只要求修归属/选择；字数错误允许依原文另存，不能同时禁止写入；缺直接证据允许补读/留缺口。
- 中文约束仍有效，不能通过加无依据文字来凑字数。
- 原报告快照、原要求偏移和引用恢复测试不退步。

### 进入第 2 步的标准

正式计数与过程预估对同一完整选择完全相等；每类已知错误都有不矛盾的下一动作；相关既有回归和新增边界全部通过。暂不要求真实模型已学会修复。

失败时留在本步修计数/错误传播；不要靠加重试次数掩盖反馈问题。

## 第 2 步：让保存前的原文不再依赖长历史

### 做什么

新增纯投影能力，从已有事实重建：

- 已读 passage 的精确原文、source 版本、范围和 pN。
- 可以继续使用的 source/result/hit 定位及读取入口。
- 当前候选 finding 的精确版本和原文依据。
- 哪些只是预览，哪些内容没有提供，下一步如何补读。

先完成这个能力，不立即开启历史裁剪。不要新增一个可写“候选证据库”。

### 改哪里

主要是 `context_view.py`；输入取自原 `ledger.read_passages`、调查回执、`search_results/hit_targets/source_ids` 及精确知识版本。核对 `passages.py`、`source_rendering.py` 的现有边界，复用而非复制其定位算法。

活跃判断证据必须完整；目录可以缩略并显式标记。完整条件跨两个 passage 时共同提供，不能按句号或 1000 字符上限把“语义完整”当作已证明。

### 验证什么

1. 完成规划和阅读，还没有 save_finding；移除内存中的旧消息后，仅凭原回执仍能重建同样的候选原文和定位。
2. 修改网页最新内容，重建仍返回原版本。
3. OR 列表末尾和跨句恢复机制没有静默丢失；放不下则显式继续，不强行给出完整标记。
4. 可提供未读章节/命中的定位，但不凭 view 自动生成新的已读 pN。
5. 跨题采用已读 passage 仍无需重新采集；知识对象不因此复制。

### 进入第 3 步的标准

没有旧消息也能恢复保存前的已读候选和继续入口；重建不联网、不写知识；原文/版本/范围一致；相关测试全部通过。

失败时继续补回执投影，暂时保留完整历史。不要通过裁短历史来提前制造“输入变小”的结果。

## 第 3 步：先做每题一个 unit 的最小完整流程

### 本步的范围

**暂不拆复杂问题、暂不裁历史。** 每个原 qN 派生一个 unit，目标等于原问题。这样先验证局部提交和父报告接线，不把拆题收益混进来。

### 按这个顺序实现

1. 在原 research_plan 中一次登记 qN 与实质 rN 的归属。原格式和实际执行要求继续由原检查负责。
2. 从原计划和 settled receipts 纯推导当前 unit，不保存独立 cursor。
3. 在原 TurnSnapshot 冻结 research_scope：计划身份、qN、unit、合法引用、待替换的选择。快照保存/恢复同步版本化。
4. question_ref 先保留，冻结成当前 qN 的单值 enum；执行也按原请求的 scope 检查，不能只改提示。
5. 新增普通领域动作 submit_research_answer，只接收 state 和 findings。answered/partial 需要非空 finding；unresolved 允许空列表。即使还没有保存过 finding，也能提交 unresolved。
6. 选择只写入原 effect 的 settled receipt；正文继续只在原 KnowledgeStore。live 和 recovery 共用原 projector。
7. 提交后仍由原 kernel 决定下一动作，进入下一 qN。提交独占工具批次，原生调用返回保持配对。
8. 所有 qN 提交后，从原计划和有效选择回执组装父 coverage，进入原 gate/compiler。不得要求模型再重抄全局 coverage，不得把组装输入塞入 last_done_args 冒充模型 done。
9. 接受后仍冻结唯一 FindingReport，经原 publication effect 发布；全缺口时按真实未完成原因关闭，不授予成功发布，也不逼模型保存占位事实。
10. 拒绝修复只重开对应选择。替换绑定被修回执身份，新回执成功后替代旧选择；旧事实保留，不覆写答案表。

### 改哪里

计划：`questions.py`、`tool_contract.py`、`tools.py`、`ledger_receipts.py`。

合同/执行：`kernel_protocol.py`、`provider_receipts.py`、工具注册、`task_execution.py`。

投影/完成：`kernel_facts.py`、`kernel_context.py::deliver_results`、`kernel_control.py`、`research_completion_checks.py`、`report_proposal.py`、`finding_report.py`。

这些修改是一条纵向功能，不是要求一次提交全部文件。可以先提交数据合同、再提交原 kernel 接线、再提交编译与修复，但不要在只加了局部工具却没有下一步/完成接线时宣称可交付。

### 必须通过的场景

| 输入/故障 | 期望结果 |
| --- | --- |
| q1 有答案，q2 缺证据，q3 有答案 | q2 空提交后能到 q3；报告保留 q2 缺口 |
| 所有 qN 都缺证据 | 所有局部可结束；不造 finding、不成功发布、不无限完成重试 |
| 错 qN、范围外引用、过期替换基准 | 拒绝；没有错误写入/推进 |
| 同一提交回执重复恢复 | 不重复推进、不增加知识版本、不再次执行已结算动作 |
| 选择 f1 后局部修复改选 f2 | 有效选择只有 f2；原 f1 仍可审计 |
| gate 已接受后知识发生变化 | 恢复原 compilation，正文与 digest 完全相同 |
| 原生和 JSON 协议 | 得到相同领域选择和父 coverage；调用/返回完整配对 |

### 进入第 4 步的标准

以上场景全部通过，并至少覆盖一次真实持久化后冷启动恢复；有成功报告和全缺口未完成两条完整链。生产只走原 kernel、原 gate、原发布入口，没有新的循环、可写进度表或答案正文。

本步可先用 scripted provider 验证控制流程；它不能证明真实模型的语义收益。若控制流程失败，先修本步，不调模型提示。

## 第 4 步：在同一计划中加入关系目标

### 做什么

把第 3 步默认“一个 unit”扩展成原问题下的少量 work_units；没有必要拆的问题仍然一个。qN/rN 的权威仍是原计划回执。

首轮人工固定两种拆分：

- 版本复合题：WAL 引入；只读支持版本及完整条件。
- checkpoint 复合题：停止边界；继续机制。

只读三个替代条件不拆成三个 unit；writer 回绕与 checkpoint 条件比较后续再增加独立目标，比较时两边完整依据同时提供。

编号由程序生成。先保持有序列表，不做通用 DAG、关系语言或自由任务重规划。

### 改哪里

原 `research_plan` schema、计划校验/回执投影、scope 推导、父 coverage 汇总、缺口渲染。

父状态规则：全部必要 unit 声明 answered 才可汇总 evidence_found；有采用事实但目标未完整则 partial；全无事实时，根据真实调查回执区分未调查与调查后未回答。answered 仍是模型声明。

### 验证什么

- 引入 answered、只读 unresolved：父问题必须 partial，缺口明确指向“只读支持版本及完整条件”。
- checkpoint 停止 answered、继续 unresolved：不得显示整题已完成。
- 同一精确 finding 可以复用，不重复写知识；不同条件的近似 finding 不自动合并。
- 父问题文本、原 rN、全局禁止测量等限制未丢失。
- 未开始的局部目标不会因为另一个 unit 读过网页就被伪造一条新搜索回执。

### 进入第 5 步的标准

全部混合状态用例正确；原完整问题每个必答点都有局部目标或明确原义务，缺口不被隐藏；规划回执冷启动后派生出相同 unit 和下一工作。

失败时修计划归属和汇总。不要增加一套最终自由改写来“补齐遗漏”。

## 第 5 步：这时才开启实际请求减负

### 做什么

1. 将第 2 步证据投影按冻结 scope 渲染：当前目标、完整父问题、必要原要求、完整原文、局部候选、最近错误。
2. 其他问题只显示进度索引；跨问题比较显式带两边所需证据。
3. 收窄当前工具和引用集合，但始终保持补读、恢复、unresolved 提交路径可达。避免只能 save、无法补证的死路。
4. 为 strict research 复用最近 1～2 个完整协议组历史投影。保留任务锚点；不直接切 messages 数组。
5. 去掉不适用的编码/shell 指导。模型看到的合同与解析执行合同同源。
6. 冻结 scope、证据清单、请求 options；恢复已冻结请求时沿用原记录，不重新选择当前材料。

### 改哪里

`context_view.py`、`task_guidance.py`、`kernel_prompt.py`、`kernel_context.py::freeze`、`kernel_protocol.py`。复用 `api_request_view.py` 和 codec 的完整组逻辑；没有证据时不先改 provider 的底层压缩机制。

### 验证什么

- 查看实际 admitted_payload，而非只看 view 文本长度。
- 加入许多其他 qN 的历史，当前独立目标的详细证据/旧错误不随之重新灌入。进度索引增长可以解释，完整无关正文不能持续增长。
- 1/5/10 个已完成目标下，同一个当前工作包的实际输入规模基本由本工作包决定；差异应能归因到必要索引/完整协议组。
- 原生工具配对、Responses reasoning 关联、任务锚点、必要硬约束保持完整。
- 预算不够时显式分包/继续/扩大必要范围；OR 列表和恢复句子不能裁掉。

### 进入第 6 步的标准

输入隔离、准确重放和协议配对用例全部通过；每轮实际 token、工具数和证据范围可审计。4K～8K 是普通局部包的试验目标，不是删条件的硬上限；大包必须记录具体必要性。

失败时检查请求拼装的哪一层仍带入全任务/全历史，或投影缺了什么材料，不继续靠“请专注当前问题”补提示。

## 第 6 步：用真实 12B 检验工程收益

### 6A：先跑五个最小案例

S1～S5，每题三个预先固定 seed，共 15 次。单题固定证据必须走生产 kernel 和新局部提交；不要让测试脚本替模型写答案。

建议进入候选层的门槛：S1～S4 各 3/3 完整正确，S5 3/3 合理 unresolved；无不受支持肯定、主体/否定偷换、明有证据却回避作答。

这是有限反例集上的严格回归门槛，不表示统计上证明可靠。失败一次就保留记录，定位、修复后以新版本重跑整套；不能补跑一次成功就删掉失败。若同一案例多次修复仍失败，先做只改变输入范围/输出要求的诊断，暂停扩大完整任务。

### 6B：再放入邻近干扰材料

先固定一种候选顺序，再用单独预定的第二种顺序复核；每种顺序沿用三个采样 seed。

门槛：上述已知直接依据仍选得对，条件完整；缺证据仍合理结束，不拿邻近事实冒充回答。若 6A 通过而 6B 失败，重点修候选定位和呈现，不修改发布机制。

### 6C：两种复合题做 A/B/C/D

四组都使用同一个局部提交合同，只改变“目标拆不拆”“实际上下文限不限”。两个题、三个 seed、四组，共 24 次。

| 配置 | 拆关系目标 | 限制实际上下文 |
| --- | --- | --- |
| A | 否 | 否 |
| B | 是 | 否 |
| C | 否 | 是 |
| D | 是 | 是 |

R0 比较整体流程；A～D 区分两个设计因素。测试参数只调同一原 kernel 的计划和请求配置，不成为四套生产执行器或长期兼容模式。

建议进入自主检索的门槛：D 对两个原完整题均 3/3 完整回答，不靠增加 unknown；没有新增错误肯定；与其他配置逐题比较后有清楚收益，例如遗漏减少或输入负担下降。调用增加、耗时和 token 的取舍必须明确记录，在预先冻结的预算内完成。

若 D 没有内容或成本收益，先暂停推广，依据 A/B/C 的差异决定保留哪些变化。若纯关系在完整材料上仍稳定出错，承认这套部署的能力限制，不无限堆字段、自审和关键词。

## 第 7 步：最后才验收自主研究、整篇报告和恢复

### 7A 自主定位

先跑只包含一个关系的真实研究题，不预置正确段落。至少包括单写者定位和只读条件定位，使用前面固定 seed。

门槛：请求记录能看到模型经原 source_search/open_hit 等路径把直接原文实际送入局部生成；来源版本和引用正确；内容满足前面的相同判据。fixture 给过正确原文不算自主定位通过。

### 7B 完整 WAL

使用原 `wal-full.txt`，沿生产 headless/kernel 入口。每次独立 state/knowledge；先保留原 40 轮等预算作为起点。若新工作单位决定最低调用数已超过预算，必须在实验前说明计算并冻结新旧可比预算，不能失败后随手放宽。

先跑一个固定 seed 定位集成问题，通过后再跑其余预定 seed，首轮失败原件全部保留。

进入故障验收的门槛：

- 所有原始 qN/rN 都有回答或明确缺口，执行义务看真实回执。
- 人工对照完整原文，没有原反例中的读写/写写偷换、条件遗漏、当且仅当强化或本机测量范围扩大。
- 有依据的目标充分回答；缺口不能把完整回答率“刷高”。
- 最终结论符合原 640～960 字口径，引用和版本有效，未通过自由重写生成第二份正文。
- 选择、字数等相同拒绝没有无限空转，在预算内结束。
- 若发布，decision、正式交付和知识中的采用正文与同一 compilation 一致。

### 7C 故障恢复

固定源码，分别在局部提交结算后、下一请求冻结后、gate 接受后、发布前后进行中断恢复；至少有真实子进程退出再冷启动的用例。

门槛：已结算动作不重复执行；选择不重复推进；冻结请求沿原 scope；已接受报告恢复时不重新编译、不读最新知识；多次恢复不产生第二次逻辑发布或不同正文。

再做代码边界复核：仍只有原 kernel/operation 执行循环，原 knowledge 写入入口，原 gate/compiler，原 publication effect；新局部选择只有 settled receipt 可写，其他视图可重建。

全部通过后，才把新流程作为默认 strict research 交付。历史请求按版本读取；不长期保留两套可写运行流程。

## 每批如何跑检查

先跑改动直接影响的用例，再跑其依赖的已有合同/恢复选集，不必每次全仓或全 research 重跑。

现有基础测试包括：

```powershell
python -m pytest tests/test_research_question_ownership.py tests/test_research_gap_compilation.py tests/test_research_report_requirements.py tests/test_research_context_priority.py tests/test_research_report_snapshot.py -q
```

这条命令仅覆盖当前既有边界，不能代替第 2～5 步新行为的测试。新增测试应集中验证上面的实际场景；第 3 步尤其要走真实工具结算与正式冷启动入口，不能只直接调用 projector 来冒充恢复链通过。

## 现在首先做什么

先提交第 0 步的固定案例与评分记录，再提交第 1 步的计数和反馈修复；随后做第 2 步的“没有旧消息也能重建保存前证据”。

**第 3 步第一个最小演示只用三个问题：有答案 → 空证据 unresolved → 有答案。** 它必须自动形成父提案、走原 gate、保留中间缺口，冷启动后保持一致。这个演示跑通，再加入复杂目标拆分和历史裁剪。

这样每一步失败都有明确归属：实验记录 → 反馈 → 证据投影 → 提交/恢复 → 父子覆盖 → 实际输入 → 模型内容 → 自主研究与交付。
