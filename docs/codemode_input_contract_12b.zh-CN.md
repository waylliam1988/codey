## 根因与所有权

| 观察到的问题 | 根因 | 本次处理 |
| --- | --- | --- |
| 原生读取成功后继续多轮修格式 | 初始提示允许普通文字答案，完成返修没有明确 done.summary 与 JSON 正文的关系 | 初始、协议修复、完成反馈共用同一条原生交付说明；原完成门继续校验 |
| console.log 后没有程序结果 | 控制台静默丢弃、隐式 undefined 曾等同成功空值，错误直到完成门才显现 | 同一 worker 明确拒绝 console 和 undefined，保留显式 null、false、0、空串 |
| 文本整文件更新反复 JS 语法错误 | 同一正文同时经过外层 JSON 和内层 JS 字符串两次编码，模型漏掉 JS 转义 | 同一 CodeMode 工具增加只读 JSON inputs；数据直接解码进原 VM，不执行数据 |
| 正文中的引号、换行导致难以定位错误 | 外层传输与内层编译错误混在一起 | Node 编译器直接报告有界源码位置，明确无子工具执行，并引导使用 inputs |
| return result.matches 得到 undefined 后原样重试 | 原错误只要求补 return，没有解释返回不存在的属性也产生 undefined | 诊断覆盖两种原因，合同直接给出 result.value.text / result.value.matches 的完整访问方式 |
| 只声明 async function main 后不断修改其内部 | CodeMode 执行函数体，声明入口函数不会自动运行；原诊断未指出零子调用事实 | 原 worker 在零子调用的 undefined 错误中说明事实，并引导显式调用和返回 main；不自动执行函数 |
| 多文件整文件编辑不断返修引用 | 模型截掉引用前缀、引用错误工具或旧版本 | 原回执投影为包含 result_ref、tool、ok 的 JSON 元信息；错误说明实际引用的工具；原版本保护保持 |
| 原生 args 外壳纠错 | 泛化的缺字段错误未先指出参数层级 | 原冻结 schema 校验直接诊断外壳，列出必填字段；生产修复提示要求直接顶层参数 |

`inputs`、源码和预算只由原参数解析器校验；Node runtime 委托它，不保留第二套 Python
源码规则。输入先生成不可变程序快照，再在原 VM 内解码并深冻结，隔离宿主对象原型。
源码和输入共用原字节预算；严格 JSON、有限数和 JavaScript 安全整数边界均明确验证。
没有 JS 修补、剥搜索词引号、自动拆 args、补 base_result_ref 或自动切换编辑方式。

工具定义仍归 ToolDefinition/ToolSpec，原生、文本、CodeMode 声明和字段错误说明从它派生。
生产纠错走 `task_loop → kernel_prompt._repair_prompt`，没有往旧的
`agents.protocol._native_invalid_args_lines` 再加一份关键词表。实际 schema 可以合法
声明名为 args 的参数，这种工具不因字段名称被误拒绝。

工具结果仍只存原完整效果收据。模型可见的 JSON 元信息及压缩后的引用视图均是原收据
的投影；旧展示标记不参与新格式解析。父调用已提交时直接恢复原收据；未完成重放将
原 worker 源码摘要纳入原恢复指纹，运行时实现改变就阻断，不通过另一个解释器接续。

错误返修仍由原任务循环执行。提示词能够提高可操作性，不能保证 7B/12B 或任意模型
首次重试 100% 成功；脚本执行、参数合法、最终格式正确和答案内容正确是分别验证的条件。
