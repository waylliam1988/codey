# 同一 Gemma4 12B：Codey 与 OpenScience 的实机比较

> 续测更新：用户重启服务后，正式综合矩阵和预算补测已完成，见 [综合研究续测报告](research-codey-openscience-synthesis-20261101.zh-CN.md)。下文保留重启前的首轮诊断结果与当时状态；综合研究的最新判断请看续测报告。

日期：2026-11-01。状态：**30 个固定材料诊断运行已完成；普通入口的综合研究矩阵未完成，不能给出完整研究深度排名。**

这次实际运行了两个产品，没有用一份模拟代理替代它们。现有证据不支持“换成 OpenScience，12B 就会稳定研究”。两边共享一些明显的条件理解错误；Codey 能阻断部分不受支持的交付，但其计划、选择与缺口结束协议仍有负担。OpenScience 在一个综合题先导样本中顺利形成了回答，尚不能据此推广为综合研究胜出。

逐次结果、原文摘录、分类判断、运行路径及成本在 [机器可读评阅记录](reports/research-framework-comparison-20261101.json)。原始数据位于 [本地实验目录](../.e2e-artifacts/research-comparison-20261101/)。

## 1. 测的是什么

本轮先隔离资料理解，再尝试综合研究。不能把两层混合成一个分数。

| 层次 | 设计 | 当前状态 |
| --- | --- | --- |
| 固定材料诊断 | 五题 × 三个 seed × 两个框架；相同官方选段 | 30 次完成，可分析 |
| 普通入口综合题先导 | SQLite WAL 五项关系问题；材料直接放入用户输入 | OpenScience 一个完整回答；Codey 一次协议失败、一次服务超时；另有中断样本 |
| 材料读取通道综合题 | WAL、asyncio 两题，各三 seed；材料经原生工具读取 | 服务卡住，未形成有效的成对矩阵 |
| 自主检索、候选干扰、实验科学 | 需要另设任务与验收 | 未测 |

诊断层的 Codey **预先提供计划和阅读回执**，模型仍实际执行保存、选编和结束；OpenScience 得到同一份已打开材料，通过其真实研究代理回答。这层适合发现理解与协议问题，不能称为两边的自主研究对决。

综合层使用普通入口，不预填计划、finding 或答案。封闭材料设计限制外部来源，避免搜索排序、网站变化掩盖理解问题。因此即使这一层完成，也只代表技术资料综合，不能直接外推到文献发现、实验设计或科学创新。

## 2. 版本、部署与公平性

| 项目 | 实际配置 |
| --- | --- |
| Codey | 被测生产代码 `c346b9e2`，真实 headless research 入口，strict research |
| OpenScience | 官方 Windows CLI `2.0.153`；对应源码 `a08e0ad0ad3d6448123039ee4659163eb2e35d99` |
| 模型 | `koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M` |
| 服务 | 同一个 `127.0.0.1:5001`，KoboldCpp `1.117.1`，运行上下文容量 262144 |
| 采样 | seed 74/75/76，temperature 0.3，top_p 0.9，`enable_thinking=false` |
| 输出上限 | 代理将每次请求限制为最多 4096 token |
| 调用预算 | 每次运行最多 12 次推理请求，累计输入 180000 token 软门槛 |
| 时间预算 | 单次请求 150 秒；子进程 360 秒；OpenScience deadline 300 秒 |
| 子代理 | OpenScience delegation 关闭；Codey 没有引入另一套代理循环 |
| 评分 | 逐条对照冻结原文；没有让被测 12B 给自己打分，也没有独立盲评 |

透明代理保存原始请求、转发请求和响应，不翻译工具协议、不代答、不修正模型动作。公共采样与输出限制通过该代理注入。OpenScience 使用隔离配置和数据目录，没有复用用户账号、密钥、记忆或研究会话；保留其原生研究提示和可用工具。

需要明确披露以下差异：

1. **诊断层协议不同。** Codey 使用生产中的受约束 JSON 文本工具，OpenScience 使用原生工具。它比较实际部署，不能独立识别“框架本身”与协议格式各贡献多少。
2. **上下文准入配置发现了不一致。** 初始清单拟定双方 32768，但 Codey 实际跟随服务获得 262144 窗口、32768 输出预留；代理仍将实际输出封顶 4096。已完成诊断中 Codey 最大实际输入 3761，OpenScience 为 8690，未触及任一窗口上限，但不能称为严格等窗口实验。测评脚本已补真实保存配置的 32768/4096 预算；旧运行不重标为修复后运行。
3. **时间上下文不同。** Codey 使用原固定时钟；OpenScience 保留原生系统中的当日日期。这些题不含相对日期，仍需披露未做到系统提示逐字相同。
4. **相同 seed 不等于相同随机轨迹。** 两边提示、工具与调用次数不同；三个 seed 只能检查有限的重复性。
5. **耗时不是受控性能排名。** 记录包含 CLI 启动、不同准备过程，KV 缓存和全部先后效应没有隔离。

源快照、原评分表、初始 protocol 的哈希保留在清单中。初始 protocol SHA256 为 `e176c3d6e378756627177582413481e5408ebfdeea571c18e8018678b0e3afae`；随后在综合题正式输出前冻结的读取通道清单为 `45cd5e942c601209221902d31ae129cf5c4c4c1b63471f2e8f35595c1158b2cd`。更换输入通道的先导数据没有被删除，也没有并入新通道结果。

## 3. 30 次诊断运行的结果

每格为同一题的三个 seed。把“所问事实正确”“主动附加错误”“结束行为”分开评阅，不按篇幅奖励。

| 检查项 | Codey | OpenScience | 含义 |
| --- | --- | --- | --- |
| 单写者限制及一个 WAL 文件的原因 | 3/3 核心正确 | 3/3 核心正确 | OpenScience 一次额外写错 checkpoint 边界 |
| 只读支持版本、三个完整条件与 OR | 3/3 | 3/3 | 没有观察到 OpenScience 的内容优势 |
| checkpoint 停止边界与原因 | 3/3 | 3/3 | 明确问停止时，两边都能答对 |
| checkpoint 记录位置与下次继续机制 | 2/3 清楚正确；1/3 位置表述矛盾 | 3/3 核心正确 | 仍须检查额外说了什么 |
| 上一题整段回答无错误附加结论 | 0/3 | 0/3 | 两边都会自行扩展并写错条件，Codey 另有位置矛盾 |
| 只有邻近材料时，最终正确空缺口结束 | 1/3 | 0/3 | Codey 的一次正确结束经历了拒绝和修复 |
| 只有邻近材料时，直接空缺口结束 | 0/3 | 0/3 | 两边都未稳定表现出简洁、正确的缺证据行为 |
| 缺证据题中，不受支持的原因进入接受报告/最终答案 | 0/3 | 3/3 | Codey 的门槛发挥作用，但两次最终无进展 |

这里没有把 Codey seed 76 的最终正确 unresolved 判成最终失败。它与“一开始就按正确路径结束”是两个维度。也没有把 Codey `no_progress` 记为回答正确，或把 OpenScience `completed` 自动记为内容正确。

如果只统计四道有直接证据题的“核心完整且没有错误附加结论”，Codey 为 **9/12**，OpenScience 为 **8/12**。OpenScience 单写者 seed 74 另有未标注的机制推测，见下文。这个一例的差距不支持显著优劣或普遍排名；缺证据题应另外看结束与错误交付，不硬塞进同一个总分。

### 3.1 相同材料，不同问法，暴露共同的扩写问题

原文：

> The checkpoint remembers (in the wal-index) how far it got and will resume transferring content ... from where it left off on the next invocation.

问恢复时，两边基本都能保留 wal-index 与下次继续；但会主动补写并非当前所问的停止边界。

Codey seed 76：

> 当 checkpoint 操作遇到任何当前读取者（reader）正在使用的 WAL 页面时，它会暂停。

OpenScience seed 75：

> 当 Checkpoint 遇到任何当前读取器（reader）尚未到达的 WAL 页面时，必须停止。

这两句都没有保留原文的 **past the end mark of any current reader**。读者使用某个页面、尚未到达某个页面与 reader end mark 不是同一个条件。Codey seed 74 的“正在使用的 WAL 文件末尾之后”也没有准确表达每个读事务的 end mark。

Codey seed 75 则写：

> 会在 WAL 文件中记录进度（在 wal-index 中）

正确名称与错误的位置说法并列，不能只看出现了 `wal-index` 就通过。应记录为表述矛盾，而不是把整个恢复过程都评成完全不懂。

同样的模型在明确问“何时停止、为什么”时两边均 3/3 正确，说明当前失败的一部分来自**生成时主动扩大回答范围**。这不是 OpenScience 独有的解决能力，也不是引用存在就能自动避免的错误。

### 3.2 缺证据时，两边都存在邻近事实代替原因的问题

这题只提供读写并发、同主机与共享内存的材料，故意不给“一个 WAL 文件所以一个写者”的句子。

OpenScience 三次最终答案均将共享内存约束说成单写者原因。例如 seed 75：

> 由于其核心机制依赖于内存共享，导致它在处理多个并发写入时仍受限于单写者。

材料中的共享内存解释的是“为何要求同一主机”，不能移作“为何单写者”。seed 74/76 虽另加“不完全解释”的保留语句，前面的肯定因果仍然没有被撤回。

Codey 的三个轨迹不同，不能一概归为同一种幻觉：

- seed 74 保存“仍有单写者限制”的候选，却没有回答原因；提交 answered 被拒，随后读材料循环，最终 `no_progress`。
- seed 75 确实保存了共享内存作为原因的错误候选；多次 answered 被拒，最终 `no_progress`，没有形成接受报告。
- seed 76 从一开始就写明材料未直接解释原因，但把这句话保存成 finding 并提交 partial；修复后最终以空 `findings`、unresolved 结束，终态为 `research_unresolved`。

Codey 在这里体现的是**部分阻断能力**，不是模型语义能力已更强，更不是泛化的事实正确性证明。门槛挡住错误但让流程循环，同样是需要改善的产品行为。

### 3.3 区分错误事实与未标注推论

OpenScience 单写者 seed 74 写“多个写者同时操作会导致内容冲突”。这与材料方向相容，但材料没有直接展开该机制，回答也没有标注为推论。本次将其记为支持范围问题，没有仅因原文未逐字写出就判为已证实的事实错误。

这项区分适用于两边：不能把合理推测都当事实，也不能把所有非逐字转述都当错误。逐次 JSON 保留了这一备注，便于复核。

## 4. 综合题：发现了什么，尚不能断言什么

### 4.1 一个已完成的 OpenScience WAL 先导回答

该回答覆盖了读写并发/单写者、版本、三个只读条件、checkpoint 停止/继续、writer 回绕与性能边界，大体形成了用户可阅读的综合结果。这说明同一部署的 12B **有能力在一次较宽的回答中组织多组材料**，不能预先断言它只能逐句抄写。

但回答仍有瑕疵：把题目中的“保留或的关系”额外解读成 WAL 与回滚日志的替代关系；writer 回绕条件列表还加入“Checkpointer 已完成的进度”这一不完整项，虽然同一处列出了全部转移并同步、无 reader 使用 WAL 的主要条件。

该样本保留在 `runs/wal_synthesis-74-openscience/research-report.txt`。它只是一个先导样本，不与诊断层混分，也不代表三 seed 或跨主题通过。

### 4.2 Codey 普通入口的真实协议失败

WAL seed 75 有三个实际完成的模型响应，均提交 8 个 questions、5 条 question_details，违反一一对应契约；反复相同后 `no_progress`。这是协议失败，不是服务超时，必须保留。

另外，材料直接放进用户输入后，当前 Codey 的原文分段机制将来源正文也登记为 coverage requirements：

| 输入 | WAL | asyncio |
| --- | --- | --- |
| 问题与全部材料一起放入任务文本 | 117 条 | 151 条 |
| 问题留在任务，材料改由工具读取 | 28 条 | 29 条 |

编号 `1.` 自身也成为了一条 requirement。这个计数可从 `coverage_requirements(task_text(...))` 离线复现，不能解释成模型凭空添加了一百个研究要求。

**不能反过来声称 117 条要求就是 8/5 错配的唯一原因。** 实验只证明负担真实存在，以及这次计划未能通过；还没有完成改用读取通道后的稳定对照。读取通道即使减少了要求，仍含编号和元指令，也不是已经解决了任务语义分段。

### 4.3 服务故障使后续矩阵失去可比性

先导 constrained JSON 请求曾超过 150 秒；随后切到双方原生工具的读取通道，Codey 也发生等待超时。故障因此不能简单归因于 JSON 约束。

暂停时，KoboldCpp 健康、模型与 perf 接口仍响应，但多次观测到生成计数停在 537、`idle=0`、`queue=3`。最后保存的一次观测中空闲计时已达约 814 秒。OpenScience 后续请求受到排队影响，不用于语义正确率或耗时比较。

已停止本轮测评子进程并尝试取消本轮生成。根据上游 `1.117.1` 源码，空 genkey 的 abort 在存在排队时不会直接取消；实际接口返回 `success=false, done=false`。现有记录不足以确定卡住发生在生成、输出处理还是其他服务线程，不能当作已经找到框架根因。没有擅自重启或改写用户的模型服务。

测评脚本随后增加了两项保护：下一次运行前验证服务真正 idle、queue=0；为本轮请求附加仅供服务识别的 genkey，便于定位并取消自己的请求。这些是测评设施修复，没有替被测代理作研究决策，也没有改变旧样本。

## 5. 调用和输入成本

仅统计 30 个已完成诊断运行。每次都有非空响应、匹配 seed，并核对后端 generation counter 全局不重复；超时后的旧 perf 不计入成本。

| 指标 | Codey | OpenScience |
| --- | ---: | ---: |
| 运行数 | 15 | 15 |
| 实际推理调用 | 48 | 30 |
| 其中额外标题生成 | 0 | 15 |
| 累计输入 token | 148273 | 142802 |
| 其中标题输入 | 0 | 13281 |
| 累计输出 token | 2186 | 2573 |
| 最大单次实际输入 token | 3761 | 8690 |
| 端到端耗时中位数 | 12.23 秒 | 23.66 秒 |

Codey 正常有证据题通常为保存、采用两次调用；三次缺证据运行分别用 8、10、6 次，抬高总调用数。OpenScience 每题一次主要回答，另有一次同模型标题生成，即使 CLI 已指定标题仍实际发生，不能漏计。

OpenScience 的原生系统与工具输入更大，Codey 的局部投影确实使单请求更小；但 Codey 更多调用后累计输入接近。这里不支持“Codey 当前每个输入都更长”的判断，也不证明“越短就越正确”。

Codey 的计划、已读准备经过夹具，OpenScience 的 CLI 启动路径不同，缓存顺序没有受控。上述耗时只是这组运行的观测，不足以宣布 Codey 自主研究更快或 OpenScience 性能更差。

## 6. 对当前选择的建议

**目前没有充分证据选出研究深度赢家。** 可以形成更具体的部署判断：

- 固定材料的条件提取，两边接近；OpenScience 没有消除这个 12B 的关系理解和错误扩写。
- 缺证据时，Codey 更能阻断不受支持的正式报告；它仍需把拒绝后的无进展转为明确、有依据的缺口结束。
- 普通入口的综合材料组织，OpenScience 已展示一个可用先导回答；Codey 当前还存在明显的计划合同与任务/材料边界负担。不能因为存储与发布更严，就认为普通研究入口已经可用。
- 不建议据此迁移另一套研究运行时。Codey 可以继续保留原 kernel、原知识版本、原结算回执和唯一冻结报告，优先减少模型必须维护的协议对应关系。

最值得随后验证的改动是：

1. **明确任务与材料边界。** 用户提供的来源正文应保留原文和引用，但不应被通用句子分割器当成一百条研究要求。通过现有任务/来源入口表达，不增加第二份可写要求表。
2. **收敛计划表示。** 研究问题及它的 requirement 归属应尽量一次成组声明，从该权威计划派生问题列表与模型视图，减少模型同时生成两个必须逐项对应的数组。保留旧冻结合同的恢复兼容，不能静默改正错配。
3. **控制回答范围。** 当前目标只问记录位置和继续机制时，尽量不要生成整段 checkpoint 教程。内容变少不等于删证据中的完整条件；限制的是生成任务。
4. **让不足证据的结束便宜且明确。** 继续允许空 unresolved；不把“缺证据”保存成事实，不把拒绝后反复重读同一原文当作实质进展。门槛负责阻断，不能自动替模型宣布原因已经解决。

这些是本轮比较支持的优先方向，还不是新的修改已经取得内容收益。尤其不能用 Codey 的 WAL 专项 cue 检查，推导其对 asyncio 或其他主题也能阻断错误。

## 7. 继续比较的准入标准

服务恢复后，先做一个短原生工具读文件烟测，确认队列归零、调用完成、后端 generation counter 推进；不能只看 `/models` 返回成功。之前原生 `read` 烟测曾成功，这次失败不代表永久不支持原生工具。

随后使用**新目录与新的冻结清单**，继续既定两题 × 三 seed × 两框架的完整读取通道矩阵：

1. 核对 Codey 实际 connection_budget 为 32768/4096，以及双方转发的真实采样参数。
2. 相同来源内容和既定评分不改；记录工具通道不同、完整任务提示和顺序。
3. 每轮开始必须服务空闲；故障后停止矩阵，不让另一个框架在队列污染下继续计分。
4. WAL 的 16 条必要事实、asyncio 的 12 条事实及各自五组关系分别评分。wrong extra、支持范围、状态、缺口、交付与成本分开。
