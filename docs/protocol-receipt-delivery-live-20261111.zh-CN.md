# 浏览器文件回执交付 A/B

## 候选改动

候选只在实验 worker 中启用。A 沿用共享流式接线下的生产逻辑。B 复用 B2 的正文绑定和证据优先反馈，以及 B4 的已结算子回执回放，再增加普通文本任务的文件事实交付。两组的任务文字、浏览器工具、权限、任务声明和外部验收相同。B 的文件事实交付还要求成功父调用。

- `upload_bound` 沿用正式 JSON 组装器。文件名、SHA256 取自上传回执，正文取自 `research_observation.text`。候选检查回执身份、参数摘要、来源正文哈希、截断标志和已读段落覆盖范围。缺动作、缺成功父调用或证据无效时，先给出对应反馈。
- `upload` 和 `download` 沿用普通文本输出。在模型说明后附上来自成功父调用的真实文件事实。上传补文件名、字节数、SHA256、页面正文及 `effect_verified`，`false` 表示服务器接收未核验。下载补管理路径、文件名、字节数和 SHA256。模型原文保留，事实区单独提供机器可读的值。
- `return_failure` 两侧均由同一脚本执行真实下载、读页并制造父返回编码失败。B 只对生产签发修复凭证的既有合格失败进行自动回放。回放保留原工具顺序、参数、回执引用和截断标记，按既有大小预算交付。

## 验证方式

定向测试使用真实 Chromium 和脚本化 HTTP。普通上传与下载的模型说明故意漏掉文件事实，检查两侧最终文本及真实动作次数。另核对 JSON 正文与源观察完全一致、缺动作和缺父回执时的完成反馈、不完整正文的拒绝，以及修复后的下一次请求确实包含原下载值和原始浏览器读取结果。

```powershell
python -m pytest -q tests/test_protocol_surface.py -k 'receipt_delivery or installs_only'
python -u -m tools.protocol_surface_ab --config receipt-delivery --run-dir .e2e-artifacts/protocol-receipt-delivery-live-20261111-01 --repeats 2 --timeout 90 --budget 300 --max-turns 10 --seed 123456789 --kobold-base-url http://127.0.0.1:5001/v1
```

实机使用本地 KoboldCpp Gemma4 12B，temperature 0。四个场景各运行两对，交替 AB/BA，失败单元保留原结果。普通场景为 `upload`、`download`，`upload_bound`、`return_failure` 为诊断。逐单元对比正式完成、最终事实、真实文件动作次数及实际模型请求。

## 16 单元主矩阵

| 场景 | 第 1 轮 A | 第 1 轮 B | 第 2 轮 A | 第 2 轮 B |
| --- | --- | --- | --- | --- |
| `upload_bound` | no_progress（6） | 通过（3） | no_progress（6） | 通过（3） |
| `upload` | 通过（2） | 通过（3） | no_progress（4） | 通过（6） |
| `download` | 通过（3） | no_progress（6） | 通过（4） | 通过（3） |
| `return_failure` | 通过（2） | 通过（1） | 通过（2） | 通过（1） |

括号内为实际模型调用次数。A 通过 **5/8**，B 通过 **7/8**，常规场景均为 **3/4**。配对中仅 A 通过 1 对、仅 B 通过 3 对、两侧均通过 4 对。模型调用 A **29**、B **26**。8 对任务文本一致，生产源码及 12 个冻结脚本和测试文件的摘要一致。16 个单元全部结算，无服务失败或预算中止。实机退出码 1 来自场景未通过。

- **正文绑定有直接收益。** 两个 A 都已执行一次附件选择，随后父返回失败，完成反馈优先要求修答案格式。两个 B 都用一次附件选择完成，最终 JSON 的三项绑定值与成功父调用下的原始回执逐项一致。第 1 轮 B 还用一次合格回放恢复了读取正文和上传结果，随后实际请求含这两份原始数据。第 2 轮 B 自行完成，未触发回放。
- **普通上传和下载有确定性补漏证据。** 脚本化回答漏报文件名和 SHA256 时，A 的原文没有这些字段，B 从原始回执补全。实机中，普通上传和下载的三个 B 通过单元，模型原提案已含真实 SHA256，候选交付的值也都回溯到原始回执。因此本批实机没有观察到普通任务靠机械补 SHA256 由失败转为通过。第 2 轮普通上传 A 在缺 return 后反复返回编码失败，B 未触发自动回放，不能用这一对单独归因。
- **第 1 轮普通下载 B 有明确退步。** 模型前两次直接访问 `snapshot.elements`，第三次下载成功后直接访问 `download.path`。三次都触发 Result 契约错误，原父调用没有生产签发的回放凭证。文件字节正确，模型也报告了真实哈希，但候选按证据要求拒绝缺成功父调用的结果，最终 `no_progress`。该单元实际只下载一次。候选维持现有回放边界。
- **指定的返回编码故障减少模型调用。** 两组各通过 2/2，所有单元都只下载一次。B 每单元自动回放一次，且下一次实际请求中的下载数据和读页返回值均逐项匹配原始回执，模型调用合计从 4 降到 2。整个矩阵没有重复的成功上传选择或下载。

逐单元记录见 [主矩阵原始摘要](../.e2e-artifacts/protocol-receipt-delivery-live-20261111-01/summary.json) 和 [只读交付审计](../.e2e-artifacts/protocol-receipt-delivery-live-20261111-01/delivery-audit.json)。审计核对了全部 55 次实际请求的 stream、seed 和 temperature，以及 B 的最终字段和实际请求中出现的完整回放值。流式用量记录不完整，本报告只比较模型调用次数。

## 附件接收状态复核

主矩阵的一条 B 说明把已选择附件写成“完成上传”。主矩阵冻结结束后，在最终候选的 `upload_bound.explanation` 中根据成功上传回执的 `effect_verified=false` 补上“文件输入框已选择附件。服务器是否接收尚未核验。”普通上传的事实区使用同一句话。保留模型说明和原输出字段，范围说明来自回执。

最终候选独立跑了一对 `upload_bound`。A 用 4 次模型调用，最后因格式检查停在 `no_progress`。B 用 3 次模型调用通过。B 的模型原说明漏报 SHA256，最终 JSON 仍绑定了实际 SHA256、文件名和完整正文。只读审计核对了唯一一次附件选择的 `effect_verified=false`，确认范围说明进入最终 JSON。这一对不计入主矩阵。 [复核原始摘要](../.e2e-artifacts/protocol-receipt-delivery-upload-scope-live-20261111-01/summary.json)

## 检查与结论

主矩阵版本的 178 项相关回归通过，退出时有 RAM disk 清理告警。补上附件接收范围说明后，17 项定向测试重新通过。Ruff、strict mypy 和 `git diff --check` 均通过。生产源码和生产提示模板未改。

这一批确认了真实正文绑定、确定性文件事实补齐，以及合格父返回失败的无重复回放。普通上传和下载合计完成率持平。下一个已复现的阻断是普通下载的 `Result` 访问错误导致成功子回执缺少成功父调用，同时该错误不在现有回放凭证的适用范围内。
