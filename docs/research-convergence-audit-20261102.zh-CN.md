# 固定本地模型的 Research 收敛审计与修改建议

日期：2026-11-02。源码基线：`de3edcb1`。本轮检查生产代码、此前 Qwen 27B / Gemma 12B 报告、整篇入口原始 payload / 响应，以及直接作答诊断。未调用模型、未修改模型配置或生产源码，未启动或停止 KoboldCpp。本文是修改建议，不是新实现的实机验收。

后续补充：[OpenScience 源码与真实请求交叉审计](openscience-codey-source-audit-20261102.zh-CN.md)。新增证据包括：成功短题实际只用 read→正文；Codey 曾在协议修复中丢掉首次正文已答出的条件；双方长文默认读取范围不同。直接 Markdown 诊断没有隔离完整请求布局，不能据此把剩余差距主要归结为模型能力。应优先验证角色分层、稳定保留原任务与不损坏正文的修复路径，而不是继续追加写作提示。

具体实施见 [Research 函数级收敛方案](research-function-level-plan-20261102.zh-CN.md)。方案按当前工作区另行采样，区分已在修改的部分与待补缺口，分为确定性修复、请求投影、修复/阅读、知识批次四组。普通研究的知识积累建议最终收敛到原 submit 的可选显式更新，由原发布事务一次提交；这属于后续合同设计，尚未实现或验收，不应与第一批输入投影修改混测。

可复核的离线统计及探针见 [审计 JSON](reports/research-convergence-audit-20261102.json)。生成脚本为 `.e2e-artifacts/research-convergence-audit-20261102/audit.py`；仅读取历史材料和调用无 I/O 的生产投影/校验函数，禁止网络，不写知识库。已有定点回归 **32 passed、7 deselected，31.11 秒**。没有运行全量测试或本轮冷启动恢复矩阵。

## 1. 判断：仍有工程空间，但主要问题已发生变化

早期失败中，Codey 的协议负担是重大原因。当前普通整篇入口已经显著减掉这部分负担。接下来的投入应集中于 **稳定传输、准确显示材料可见范围、减少一次写作要同时处理的关系，以及独立验证内容**。不应重新要求小模型维护计划、逐题状态、finding、采用和全局 coverage；也不应再靠修改末尾几句提示作为主要推进方式。

当前有四种不同的失败，分别需要不同处理：

| 失败 | 现有证据 | 工程判断 |
| --- | --- | --- |
| 协议执行失败 | 第十批 native 连续输出正文；`tool_choice=required` 已发送 | 传输/工具调用链必须先稳定，内容改善不能补救未执行的提交 |
| 找不到或看不到必要材料 | 旧目录隐藏第 44 节；整窗按最近顺序选入有限字符预算 | 仍有可直接修改的材料组织问题 |
| 条件遗漏、对象或范围混淆 | 完整 gather 材料已显示仍漏取消边界；多数场景更快被当成本机证明 | 属于当前部署的内容判断问题，工程可以尝试减少，不存在结构校验必然消除的保证 |
| 研究交付被当作内容认证 | 当前提交主要验证引用、读取和版本，不验证所有事实/关系 | 应保持现有 unreviewed 边界，不能把发布成功提升成语义正确 |

12B 可以作为减负压力目标。**12B 通过不能逻辑推出 27B 必然通过**：不同模型部署的指令遵循、模板、量化和微调会改变表现。最终使用的部署仍需跑相同验收，不必换模型才能开始改工程。

## 2. 这次核查补充了什么

### 2.1 严格整篇通过率掩盖了失败的具体形状

重新汇总 `research-whole-batch3-20261101.json` 中已有人工评分：

| 同一第三批 | 必要事实覆盖 | 严格整篇通过 |
| --- | ---: | ---: |
| Codey `ff6cba12` | 80/84 | 1/6 |
| OpenScience | 84/84 | 6/6 |

80/84 **不是“研究准确率 95%”**。该计数不能抵消错误附加、错误逻辑关系或引用范围不全。但它说明下一步需要定位有限且影响很大的缺陷，而非把小模型当作几乎不能读懂材料。

第三批 Codey 的 WAL/74 必要事实 16/16，仍因错误扩写、制造已有答案的缺口和引用错位失败。asyncio/76 为 11/12，主要遗漏父 gather 取消传播不受 `return_exceptions` 影响。把这些都归为“没跑通”，很容易继续修改已经正常工作的发布内核。

后续版本不能借用第三批成绩。第七、八批六例整份内容仍均未通过；最新 `de3edcb1` 没有完成实机验收。

九例扩展的已有成绩为 Codey 5/9、OpenScience 6/9，而且只有一个 seed。它显示双方都有内容失败，不能把 OpenScience 当作正确答案生成器，也不能用这九例建立通用能力排名。跨来源 24 小时 TTL 的评分局限继续保留，后续新题应在出题时把必要要求写清楚，不能事后给某一方豁免。

### 2.2 当前 Codey 不是简单地比 OpenScience 输入更长

原始第三批 asyncio/74：

| 请求 | 后端报告输入 token |
| --- | ---: |
| Codey：读取后首次写答案 | 4,137 |
| Codey：协议修复后提交 | 2,869 |
| OpenScience：读取后最终作答 | 10,301 |

OpenScience 此例仍覆盖了 12/12 必要事实。不同提示、工具、角色和呈现形式未被隔离，因此不能据此归因于某一种提示；但足以反对“继续压 token，质量就会自动追上”的单一解释。认知负担包括需要做哪些决定、材料怎样组织、输出怎样形成，不能只看字数。

### 2.3 第十批的修复请求真的发生了无信息变化的重发

`batch10-native/wire/wal_synthesis-74-codey.jsonl` 中，第 3、4、5、6 次 **完整转发 payload 的 SHA256 相同**，都使用 seed 74。第 4～6 次普通正文响应也相同。

第 3、4 次相同输入仍产生了不同正文，所以不能声称该后端完全确定性；也不能凭此证明缓存 bug。能确认的是，后续修复没有给模型新的、针对上一失败输出的可观察信息。

代码对应：

- `kernel_context.py`：strict research 设置 `tool_call_history_groups=1`，协议错误转入原重试控制。
- `api_request_view.py:bounded_history`：按完整协议组裁剪。
- `kernel_prompt.py:_repair_prompt`：返回通用修复要求。
- `api_provider.py:_payload`：重新插入同一工作视图、修复提示和冻结时钟。

有界历史是必要改造，但失败响应的必要诊断也应进入当前修复视图。不能依赖已被裁掉的历史让模型知道“这一次到底错了什么”。

### 2.4 18,000 字符视图不是任务相关的证据选择

`answer_contract.py:answer_scope` 从原阅读回执派生稳定标签，整窗按最近顺序加入 `READ_BUDGET=18000`。这是安全且简单的引用准入算法；它没有检查被淘汰材料是否仍是早先问题的必要前提。

本轮用四个各 6,000 字符的合成阅读回执调用生产函数：已读为 e1/e2/e3/e4，当前可见仅 e2/e3/e4。此探针证明选择规则，**没有证明第三批短材料失败由这项规则造成**。

`answer_context.py` 提供最近 8 个阅读回执 ID、最近 12 个定位，但没有把全部被省略窗口的标签、来源版本、范围及恢复动作清楚列出。长研究中，小模型可能记得某个事实，却不知道相应 eN 已退出准入集合，或者认为需要重新检索。

### 2.5 最远读取位置不能表示连续已读进度

`context_view.py:read_evidence_projection` 以 `max(ends)` 生成 `next_offset`。生产函数合成探针：

```text
已经读过：[0,1000)、[9000,10000)
next_offset：10000
实际未读：[1000,9000)、[10000,12000)
```

这不是内核已经把中间内容授权为已读；引用准入仍按真实 passage。问题是导航对小模型过于含糊。长文修复不能只把目录从前 16 个改成首尾 32 个；中间章节仍可能不可见，阅读范围也仍需明确。

### 2.6 当前语义边界是有意放开的，不能假设仍有旧 finding 闸门

`submit_answer` 校验字段、状态、正文长度、至少一次调查以及引用标签；`compile_answer_report` 校验原回执、精确版本和归档关系；发布沿原 effect/事务保存唯一 answer。

它们没有验证每个用户子句已回答，也没有验证引文蕴含每句话。本轮调用 `submit_answer`，含错误肯定及省略其余问题的示例仍可结构通过；**没有执行、编译或发布该示例**。这说明的是检查边界，不是新发现了原设计承诺之外的语义校验 bug。

旧 q8 的缺口正文替换属于旧逐题合同，不能当成当前自由整篇正文的内容保护。当前 `state=partial` 也不表示正文中的每个肯定句可信；rlock-adjacent 已有真实反例。

### 2.7 直接 Markdown 诊断排除了部分解释，没有测出模型能力上限

已归档的 `answer-ablation` 确实去掉了工具 schema、历史和时钟，仍复现同类错误。它同时保留了 Codey 的 evidence view 和整篇任务组织；`direct_method` 还增加了一段检查指导。

所以现有诊断支持“JSON 转义不是全部原因”，不能推成“所有上下文组织和作答方式都不可能改善”。此前所谓 method 实验主要要求模型自己检查，尚未验证下面建议的显式依据先行输出结构。

更早 Qwen 原始短材料只有 254 输入 token，仍从并发机制推成整体吞吐优于回滚日志；785 token 的比较对象探针也有错误放行。对于那个具体部署，不能把所有语义错误归于 Codey 长上下文。

## 3. 建议保留的架构

```text
原任务 / 原策略
  → 原 TurnSnapshot 冻结工具、证据可见范围、请求
  → 原 run_task_kernel 阅读 / 搜索 / 提交
  → 原 submit_research_answer(markdown, state) effect
  → 原 completion gate 编译同一提交
  → 原 publication effect / KnowledgeStore 原子事务
  → 一个 answer 精确版本
  → 报告、note、图和 handoff 只做派生展示
```

原始提交 artifact 是命令/审计事实，KnowledgeStore answer 是发布后的正文权威；二者不是两个可编辑正文源。展示投影可以保留，但不能独立写正文来改变 answer。

目前 `pipeline.py:_followup_block_reason` 已对 strict research 返回 `strict_writer_owns_followup`。应保留这条边界；不要为了补内容再启动外层 ResearchPipeline 补查、另一个 writer 或后台 reviewer 循环。

普通新 research 统一走整篇入口。历史冻结的 compact/select/inline/finding 合同按原版本恢复。读旧合同不等于第二套新任务运行时；不应在还有历史记录或待结算效果时直接删掉解码能力，也不应把它们重新作为模型可选的并行默认模式。

## 4. 具体怎么修改

### P0：先固定可执行传输，停止同样错误反复烧轮次

涉及 `kernel_context.py`、`kernel_control.py`、`kernel_prompt.py`、`api_provider.py` 及已有 provider 配置/请求冻结机制。

1. 对当前连接独立检查 native 和既有 `text_tool_format=json_schema`：schema 是否实际传到后端、后端是否约束 tool/enum/必填字段、返回是否可被原 normalize 执行。不能只看参数被接受或 HTTP 200。
2. 若当前 KoboldCpp 的约束 JSON 经验收更稳定，将其设为这个连接的新任务传输选择；任务启动时冻结，恢复沿原选择。它已经通向同一个 ToolPlan/kernel/effect，不需要新 research runtime。两个 JSON 内容失败样本只证明初步可执行，尚不足以宣布可靠。
3. native 普通正文继续按当前合同拒绝。不要把任何普通文本偷偷包装为 submitted answer，也不要自动猜 `state`。
4. 修复视图从原 response artifact 派生上一错误类型、实际收到的是正文还是工具、上一失败参数的必要部分，以及原冻结 spec 的最小有效样例。成功的原文仍只呈现一次。无关的超长正文不必整份重放。
5. 在原 progress/counters 内识别同一快照、同一错误和相同请求的循环。相同诊断只做有限次有针对性的修复；没有新信息则明确 protocol 停止。不要新增 retry 数据库、独立修复 agent，或靠随机换 seed 假装解决。

同时按原授权与实际目标收窄工具选择。对明确只允许固定材料的任务，开放外部检索不应成为“材料不足”的默认动作；封闭评测应在测试前冻结双方的来源范围。对正常开放研究继续保留检索。不要用模型的自我判断改变权限，也不要只从提示中删名字却让 schema/执行器仍接受调用。

这一批的收益目标是合法执行率和无效请求数，不是研究正确率。`de3edcb1` 恢复末尾指令值得作为基线复测，不能继续只凭一句提示在一个样本中成功就修改默认。

### P1：把当前证据视图改成可解释的工作材料

涉及 `answer_contract.py:answer_scope`、`answer_context.py:answer_context`、`context_view.py:read_evidence_projection`、`source_rendering.py`、`passages.py`。

**先做材料清单，不先做新的语义 planner：**

- 按 URL + 原内容 hash / 存储 revision 分组，区分已抓取总长、真正读过的区间、本轮显示的区间。
- 给未显示但已读窗口提供 eN、简短章节名、原阅读回执及可执行恢复定位。清单受预算限制时要有总数和可继续读取的出口，不能静默删除全部旧来源。
- 区间做并集，显示 `first_unread_offset` 和未读洞；已有 `next_offset` 若为最远位置，应明确叫“最远读到”，不暗示此前全读完。
- 明确来源采集是否截断，以及“已到所存快照末尾”和“真实全文已完整获取”的区别。
- 目录显示总章节数及被省略的范围；`source_search` 必须检索完整已存原文与标题，返回原版本定位。首尾标题是快捷方式，不能代替完整章节访问。

**再调整预算：**

- 18,000 字符和最终 token 上限需要协调。中文、英文、代码不能用同一字符数代表认知/服务成本；为任务、工具和输出保留预算，最后仍以实际完整 payload 准入为准。
- 最近请求明确读到的整窗应优先保证完整显示，避免刚读完就没有可引用标签。已读窗口只允许按原范围分组；不能为了填满预算把一组 OR、例外或版本说明拆成看似完整的孤句。
- 其余材料的淘汰要可观察。可以先比较按来源保留窗口与单纯最近顺序的效果，但不能用程序猜“哪个片段已足以回答”、自动补引用或把压缩摘要冒充原文。
- 如果所有必要材料超预算，允许通过现有读取工具明确重取窗口。不要暗中加入跨轮可写答案摘要或另一份证据缓存来遮掩这个边界。

所有字段从原来源/阅读回执单向派生，放进同一次冻结请求。不能维护一个与原回执独立更新的 `research_memory` / `read_cursor` 权威表。新增冻结载荷字段时显式处理版本与旧记录，不改旧请求含义。

短材料没有被预算淘汰时，这一批不应被宣称能够解决 gather 条件遗漏。它首先修复多来源和长文的可见性。

### P2：验证“依据先行的局部写作、一次整篇提交”

保持同一个提交工具的 `markdown + state`，只改变模型要形成的可见答案结构。普通任务仍一次提交完整报告，不恢复每题保存、采用和切换。

候选格式是每个原问题在同一篇 Markdown 中使用：

```text
原问题的小节
依据：最短但足以表达相关关系的原文短句 [eN]
回答：根据这句及其他明确引用材料，对所问对象作出解释。
边界：确实不能确定的部分；没有缺口时不强制制造。
```

完整条件常需要数句或一个列表，不能为了“短引文”截掉 if、unless、OR 或尾部版本说明。跨来源推导可列出多个前提再说明推导，不要求每句结论都逐字存在于原文。依据与回答都属于同一份正式 Markdown，不增加可独立编辑的 quote/claim 表。

这项改变把“回想英文前提、翻译、推断、保持条件、引用”的一部分工作转为模型刚刚写出的可见依据。它可能减少漏条件和范围偷换，也可能只是把错误解释包在真引文后面。Qwen 旧比较对象探针已经证明后者确实可能发生。因此应先做对照，**不能先加成强制生产步骤或宣称形成语义证明**。

明确编号问题可以复用 `plan_contract.py:task_layout` 的纯结构定位生成轻量小节清单，不调用 `research_plan`，不让模型再填 rN/qN/task_refs。每条原题和全局限制仍完整存在；解析不确定就保留原文，不把任意换行、编号或接口说明变成研究问题。`task_layout` 当前只保守处理 2～8 条顺序编号及缩进续行，不能直接当作通用自然语言任务分解器。

若采用机械小节检查，只能声明“这些编号小节出现/非空”，不能声明每个子句已回答。当前失败常发生在同一小节内部，检查五个标题显然不足以覆盖。

P2 与此前 `direct_method` 的区别是要求形成可见的依据→解释输出，而非仅增加“提交前检查每个条件”的指导。要用新材料验证这个差异是否真有收益。

### P3：历史知识复用接到同一材料通道

当前 `ANSWER_TOOLS` 没有 `knowledge_search` / `knowledge_read`，而 `knowledge_background` 仍可能返回背景召回。整篇引用又只接受原阅读 passage 派生的 eN。用户看到历史知识提示，不代表当前入口具备完整的“定位→读取→引用”链。

不能只把两个工具名字加回清单：现有 `knowledge_read` 主要返回对象/旧 finding 绑定，不会自动产生整篇提交所用的已读 passage 与归档关系。

建议沿现有工具、回执和 store 做一个统一读取适配：

1. 搜索命中输出结构化 ID / 精确 revision，并只把实际展示的命中算作可见定位；它们仍不是已读证据。
2. 显式读取已存 source/evidence 时检查访问范围和版本，从那个不可变版本派生与网页相同的可见窗口/eN。不得为了方便引用重新联网读取“今天的 URL”并声称是原版本。
3. 原阅读 canonical 记录精确存储引用和范围；恢复从原回执重建，不重新搜索当前库。
4. `prepare_evidence` 对已有版本复用原对象引用，不能按本轮 scope 又复制一份相同来源来制造新的权威正文。引用其他授权 scope 的原版本要保留原身份和访问检查。
5. 旧 answer / synthesis 只能作历史线索。旧 claim/inference 保留模型推论及 unreviewed 身份；要作为原始依据，需读取其实际依赖来源，不把一次旧回答自动升级成事实。

默认可见性按真实目标收窄，contract、schema 和执行允许集仍从同一 TurnSnapshot 派生。不要让背景回执继续指示模型调用一个本轮隐藏的工具。

P3 补的是产品能力，不是已有 WAL/asyncio 短材料错误的已证实根因。应在封闭材料质量基线稳定后独立接入，避免把多个变量混到同一回测里。

### P4：在行为稳定后整理新旧合同边界

普通新研究只保留一个生成合同；旧合同处理集中为明确的读取/恢复兼容。归档类型的解码可以收为显式的 accepted-report 解码入口，避免调用者以为拿到的一定是旧 `FindingReport`；当前 `FindingReport.from_payload` 已根据 schema 返回 `AnswerReport`。

这种整理有助于维护，但不是内容质量修复，不能先做大规模文件移动再解释为研究能力提高。也不要顺手修改 hybrid/coding 工具权限来强行统一所有 task kind。

## 5. 固定验证方法，避免再循环三天

### 第一步：给 `de3edcb1` 建独立基线

源码、材料、rubric、部署参数固定。不要把第七、第八、第十批结果混起来给最新版本算通过率。保留失败和服务异常，不用成功补测覆盖原记录。

先测传输：两道短题各 3 seed，加两道需要多次读取的题各 3 seed，共 12 次 run；每个连接通道单独统计。检查实际调用/归一化/effect/发布，不用完成文案或退出码代替。

### 第二步：P1 做针对性的材料边界检查

至少覆盖四源总长超预算、读取中间章节后的洞、目录中间章节、同 URL 新旧版本、PDF 页边界、末窗条件不完整、采集截断。需要证明本轮真实显示的引用恰等于冻结 scope，未读/未显示原文不因目录或存储存在而获得准入。

改变 canonical 或冻结字段后，用现有中断恢复框架检查读取结算、请求冻结和提交/发布边界。不得把本轮排除的 7 个 cold restart 测试算成已重新通过。

### 第三步：P2 用一套新正反题做有限对照

选择 3 组新问题，每组有充分材料/邻近不足材料，共 6 例；每例 seed 74/75/76，普通整篇输出与依据先行输出各一组，共 **36 次 run**。两组都走原 kernel、同一已验证传输和读取方式。先冻结独立 rubric，不把 expected、正反标签或具体正确机制送给模型。

用已有直接回答诊断入口做小规模补充：同样问题和材料，去掉工具/运行时，只改变作答组织。这是测评入口，不是生产中的第二研究运行时。若判断主要问题仍在生成组织，再扩展完整直接入口对照；不一开始把协议、提示、材料分组和 thinking 同时改掉。

正材料要检查完整条件/关系、错误附加、有证据却拒答；负材料要检查诚实地承认“当前材料不足”，以及没有把领域常识或邻近机制补成答案。长文要把“材料不可取得”和“没有读到可取得段落”分开。

报告至少分列：交付成功、必要事实覆盖、关系完整、错误附加、精确引用、正例拒答、缺口正常结束、请求数及输入/输出成本。最终内容仍按整份严格验收；诊断维度用于知道该改哪里，不用于冲淡错误。

如果新写作结构只让已知 WAL 变好、新题不改善，就撤回实验改法，不再加 WAL 专项提示。如果正常交付改善而语义仍错，保留执行收益，准确说明内容目标尚未达到。

### 第四步：再接历史知识与真实网页

先用固定旧知识版本验证不重复写来源、不把旧 answer 当原始证据，然后做全新网页端到端研究。这里涉及检索、资料可取得性和用户原题的语义范围，不能借用封闭短材料成绩代替。

最终使用 27B 时再做相同有限验收，不依据参数大小自动继承 12B 的结论。

## 6. 本轮没有建议继续做的事情

- 不回到强制计划、逐题 finding、保存后采用和全局 coverage 的普通入口。
- 不新增研究调度器、答案表、后台自审模型循环或自有写入通道。
- 不把任意正文自动当工具执行成功，不用降引用准入换完成率。
- 不把同一模型的 supported / confidence / answered 当作独立语义证明。
- 不按 SQLite / gather 专门增加大量关键词规则来替代通用研究能力。
- 不因裸模型也出错就宣布工程无空间，也不承诺任意 12B 在工程包装后都能可靠完成任意研究。

当前最值得保留的成果是：整篇明确提交、原版本证据、原 kernel/effect 和唯一发布事务。下一步优先顺序为 **P0 稳定传输与有效修复 → P1 材料范围可见 → P2 验证依据先行写作 → P3 同源历史复用**。其中 P0/P1 有明确可检查的工程行为，P2 的语义收益必须由新实机结果决定。
