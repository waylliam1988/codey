# Research：已读资料不要反复藏起、找回

**这批实机支持这个方向：资料放得下就持续展示；确实读过、准确快照仍在的资料，不因为这一轮没有重贴全文就禁止引用。**

已完成 **24 次 Gemma4 12B 实机 A/B**。复杂题从 **0/4 严格合格变为 3/4**，请求从 **29 次降到 4 次**。另外八个原版能正确完成的配对，候选也都正确完成。

**本页保留生产接入前的 24 次 A/B。该方向现已接入生产，后续实机回测、发现的问题及修正见[生产报告](research-visible-evidence-production-20261103.zh-CN.md)。** 本页中的“候选”是下面这套方案，不是此前删除修订工具的版本；本页实验期间生产代码确实未改。

## 1. 这次具体取消了什么

原来像这样：

> 程序读了资料 → 稍后把原文移出输入 → 草稿仍带着旧引用 → 程序拒绝 → 模型抄内部编号找回资料 → 重新提交。

候选改成：

> 程序读了资料 → 放得下就一直给模型看 → 模型回答 → 程序核对准确原文并保存。

| 项目 | 候选怎么处理 |
|---|---|
| 放得下的已读原文 | 全部保留，包括背景资料；不再因为固定字符额度而提前藏起。 |
| 真正超过显示预算的资料 | 不可能无限塞入窗口。保留已读范围、准确快照和稳定引用；没有重复贴全文也能引用。实机这一批全部放得下，超预算分支另做程序检查。 |
| 模型手工找回阅读回执 | 整篇回答不再展示 `read_tool_result` 工具，也不要求抄回执编号。 |
| `read_receipt_index` 旧指路 | 从候选的整篇回答提示和相关编号报错中移除。A/B 当时旧局部路径仍使用该名称；后续生产接入已改名为 `read_receipts`，保留真实在用的恢复能力，详见生产报告。 |
| 编造引用、没读过的材料 | 仍然拒绝。读过文章开头，不等于后半篇也读过。 |
| 继续阅读、搜索、准确版本、保存和重启恢复 | 保留。原始记录也保留，只是不再要求模型反复手工搬运。 |
| 修订工具、完整草稿、此前的操作记录及错误去重 | 沿用当前生产行为，不在本次删除。 |

“不用再找回才能引用”不代表“随便引用都通过”。编造的 `[e99]` 仍会报错，模型必须改成实际读过的证据。

## 2. 为什么原来放不下，现在却能放下

**旧程序限制的是 18,000 个字符，不是模型真实的 token 窗口。**

复杂题的三份原文分别为 6,476、6,490、6,489 字符，合计 19,455 字符。因此旧程序会藏掉较早的一份。找回较早资料后，又可能把另一份挤走。

但本次给模型配置的是 **32,768 token 窗口**，为输出保留 4,096 token。候选把原文工作区控制在半窗口，即 **16,384 token**，使用 KoboldCpp 的真实分词接口计算。

三份原文连同任务、导航等工作区文字，只需约 **4,600 token**。正式实验中整次模型输入最多 **7,486 token**，工具定义等也算在内。它们完全放得下，原先的丢来丢去不是这批任务的窗口容量所迫。

这里的半窗口上限针对原文工作区；整次请求仍经过原来的完整输入预算检查，没有关闭超限保护。

## 3. 实机结果

六类任务，每类两个 seed（601、602），两版各跑一次，共 24 次。下表“合格”同时要求正文完整准确、任务步骤满足、引用正确；要求保存新知识的题，还核对数据库中的候选 claim。

| 场景 | 原版合格 | 候选合格 | 请求数：原版 → 候选 | 总输入变化 |
|---|---:|---:|---:|---:|
| 多份长资料，已有完整草稿但未正式提交 | 0/2 | 2/2 | 12 → 2 | −81.41% |
| 多份长资料，先提交了编造的引用编号 | 0/2 | 1/2 | 17 → 2 | −87.66% |
| 查旧资料，先遇到一次读错编号 | 2/2 | 2/2 | 6 → 6 | −3.83% |
| 普通研究，并保存指定的新候选知识 | 2/2 | 2/2 | 4 → 4 | −4.55% |
| 简单完整草稿，补做正式提交和保存 | 2/2 | 2/2 | 2 → 2 | −4.26% |
| 连续两次读取错误后恢复 | 2/2 | 2/2 | 4 → 5 | **+21.39%** |

**目标复杂题：四次候选都一次提交并保存，三份正文严格合格。** 原版一份保存了不合格答案，另外三次止损，没有正式交付。该范围总输入为 **198,757 → 29,566 token（−85.12%）**，所有失败和重试都计入。

全部任务的合计为：

| 指标 | 原版 | 候选 |
|---|---:|---:|
| 保存了正式答案 | 9/12 | 12/12 |
| 正文和全部任务要求合格 | 8/12 | 11/12 |
| 模型请求数 | 45 | 21 |
| 总输入 token | 264,081 | 96,072（−63.62%） |

原版本来合格的八次，候选没有出现新的全文不合格。不过，连续错误题的候选 seed 601 多做了一次搜索，之后才读取给定原文，因此该场景更贵。不能承诺所有任务都省。

## 4. 成功和失败分别是什么原因

**能直接看见的改善：该核对的原文一直在，模型不用折返搬资料。** 四次复杂题的首次真实请求中，都完整包含三份原文。随后四次真实模型输出都直接调用提交工具，没有再调用回执恢复工具或重读原文。

原版复杂草稿 seed 602 的过程则是：先因 `[e1]` 被隐藏而拒绝；找回、重读后，又因背景 `[e3]` 被隐藏而拒绝。即使它只是写“背景材料 [e3] 不作为依据”，程序仍把这个编号算作引用，最后卡住。候选保留了背景原文，同样的排除说明没有再因此失败。没有为这句话添加特殊放行规则。

原版复杂草稿 seed 601 虽然保存成功，却把 C1 的 tag 和取消规则说成“没有提供”，并把 C1 的一些内容引到只有 C2 的资料上。这份不算正确。两份候选草稿答案保留了精确 tag、版本数字、父子取消边界、checkpoint 的停止/保存/恢复，以及回绕的“且”条件。

**还剩一份推论错误。** 错误引用题的候选 seed 602 写道，C1 remote “不取决于 license”。原文只说它“不继承 local 的额度”，没有证明 license 无关。其余数字、tag、取消和 checkpoint 要点正确，但整份仍按不合格计。

因此，**这次明显改善了已读资料的摆放和引用路线，没有解决模型自行添加条件的全部问题。** 也不能把整套方案的收益，分别归功于某一句提示或少了某一个工具；本轮测试的是组合方案。

## 5. 哪些保障检查过了

新增实验边界检查 **11 项**、相邻原有检查 **24 项**通过，共 **35 项不同检查**；Ruff 对新增实验和测试文件检查通过，没有留下失败。

- 强制让旧原文不再显示，仍能用原标签编译出准确旧快照；随后读到同一 URL 的不同内容，不会偷换旧引用。
- 失败读取、编造编号和未读尾部不会得到新的证据标签。即使完整网页快照在程序里，没读过的尾部也不自动成为已读证据。
- 引用正文、原文摘录被篡改仍会拒绝；原来的归档检查继续执行。
- native/text 两种工具调用路径都能正式保存，恢复同一运行不重复发布。
- 在请求准备、内核结算、发布提交三个位置中断进程，再启动仍能恢复，最终只发布一次。
- 旧局部研究路径的恢复入口没有被候选误删。

实机还核对了已保存正文与数据库一致、准确来源及证据版本、摘录属于原文、旧版本未被改写。要求新增知识的每次成功运行，都实际保存了指定的候选 claim，与答案处于同一事务，并引用准确归档证据；没有把候选提升为已验证。

12 个配对的首次真实请求，工具定义差异仅为候选移除了 `read_tool_result`，其他工具 schema 不变；完整任务均保留。实验期间 **578 个生产 Python 文件**摘要不变。

## 6. 能据此决定什么

**可以继续采用这个方向：放得下就不藏已读原文，引用资格依据本任务的真实阅读与准确快照，取消整篇回答里不必要的手工找回步骤。** 本批有直接的局部收益，不能因为尚有一份推论错误，就把这个收益说成没有。

不能据此删除所有“恢复”。真正没读的后文仍要继续读，网络失败仍需处理，重启后的原始记录及保存保障仍需保留。

这批每类只有两个 seed，复杂材料为合成规则，SQLite 为固定官方摘录。复杂题先由脚本固定执行读取、草稿或错误提交，再由真实模型接手，方便两版从同一故障状态比较；受控回应没有算作模型请求。普通研究题则由真实模型自行选择读取与提交。它证明这几个具体状态下的改善，不能外推为任意长文、任意任务都正确。

**实机候选没有遇到真正超过半窗口的资料。** “不重贴全文也允许引用”的超预算分支做了程序验证，尚未做相同压力下的模型正确性验证。历史复用实机核对的是现有 revision 1，没有额外制造一个更新的数据库 source 头版本；同 URL 内容变化时保留旧快照另有程序检查。
