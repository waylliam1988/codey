# 运行时启动第二轮页面导航

上一轮把两轮操作接进正式完成门。实机中，B 有一个单元收到“第二轮缺导航”后继续重复提交 `done`。本轮只验证把这个已明确要求的导航交给运行时。 [上次完成门实验](protocol-page-reset-gate-live-20261111.zh-CN.md)

## 对照和检查

A、B 使用相同任务、流式模型接线、真实 Chromium 和正式双轮完成门。B 在第一轮的完整读取回执落盘后、下一次模型请求前，经原 CodeMode 和浏览器工具对任务指定的同一 URL 发起一次导航。运行时以实验动作单独记账，导航结果和首轮读取凭证进入正常工具结果。第二轮的观察、填写、点击、等待和读取由模型完成。

若回执显示第一轮未完成，或者模型在第一轮之后已发起导航或切换页面，调度器不会再发起重置。重复读取和回放父调用无法形成新轮次。每个实验 worker 对同一任务最多调度一次，失败时交付原始错误。双轮完成门仍要求完整动作链。当前实验覆盖单次 worker 生命周期。

定向测试用真实 Chromium 和脚本化 HTTP 验证了以下情况。

- A 在第二轮缺导航时被完成门拒绝。B 的下一次实际请求包含已结算的第二轮导航结果和对应回执编号，随即提交 `done` 仍会因第二轮缺快照被拒绝。完成剩余动作后两组均通过。
- 已提交的重复读取、回放引用，以及已开始的第二轮不会导致额外导航。
- 在浏览器工具层注入一次失败后，原始错误进入模型请求。重复提议 `done` 时，运行时没有再次调度，任务以 `no_progress` 结束。

## 实机

```powershell
python -u -m tools.protocol_surface_ab --config page-reset-navigation --scenario page_reset --run-dir .e2e-artifacts/protocol-page-reset-navigation-live-20261111-01 --repeats 2 --timeout 90 --budget 300 --max-turns 10 --seed 123456789
```

两对按 AB、BA 串行执行。使用同一 KoboldCpp Gemma4 12B 模型及 temperature 0。分别记录首轮完成、第二轮真实导航、下一缺项、正式完成和最终事实核对。

| 配对 | A · 双轮完成门 | B · 双轮完成门与运行时导航 |
| --- | --- | --- |
| 01 | 实际完成两轮。无效的 `knowledge_refs` 反复被拒绝，最终 `no_progress`。7 次模型调用。 | 首轮读取早于等待，补等后未再读取。0 轮，调度未触发，最终 `no_progress`。6 次模型调用。 |
| 02 | 按完成反馈补做，实际完成两轮并通过。6 次模型调用。 | 运行时导航一次，模型完成第二轮后通过。4 次模型调用。 |

**A、B 均为 1/2。** 四个单元均取得完整结果，无服务失败、预算中止或不完整轮次被接受为 `done`。模型调用 A 13、B 10。运行时导航单独计数。一次触发的样本不足以证明完成率或调用数的稳定收益。

B 的触发证据在 02/B。第 3 次交互由实验运行时提交导航，持久叶回执显示同一 URL 返回 HTTP 200。该回执正是正式完成检查使用的第二轮导航。紧随其后的第 4 次交互发出了实际模型请求，请求包含“第二轮已导航”、导航结果及真实回执编号。之后模型自行完成第二轮剩余动作，正式完成证明包含 `page_reset_two_rounds`。

01/B 首轮出现的关键顺序是点击、读取、补等待。完成门随后明确要求读取，模型继续提议 `done`，因此没有合格的首轮完成回执可供调度器使用。01/A 和 02/A 都在收到缺第二轮导航的反馈后真正开始了第二轮。01/A 的失败发生在动作齐全后的完成检查。

定向 pytest **7 项通过**，Ruff 和两份实验工具的 strict mypy 通过。已审计 23 次实际 HTTP 模型请求的 seed、temperature 和流式设置，两对任务文字相同，生产源码和冻结脚本摘要前后一致。证据见 [summary.json](../.e2e-artifacts/protocol-page-reset-navigation-live-20261111-01/summary.json) 及各单元的 `provider.jsonl`、`page-reset-checks.jsonl` 和持久回执。生产源码和生产提示模板未改。
