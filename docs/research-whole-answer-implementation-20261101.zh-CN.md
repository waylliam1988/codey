# 整篇研究交付：实施与验证记录

起点：`ca29a4ff`。目标是让固定本地 Gemma4 12B 在原 kernel 中直接读取材料、提交带引用和缺口的整篇回答；原发布事务是唯一答案知识写入。没有第二套研究循环，不增加可写正文缓存。模型声明、执行交付和内容验收分别记录。

## 第一批：冻结合同与证据归档准备

- 新增整个任务的冻结 scope、`markdown + state` 提交合同、由原阅读回执稳定派生的 eN 短引用。
- 引用只允许本轮实际呈现的整窗；未呈现窗口不可引用。重复读取不重编号，同一 URL 的新版本不覆盖旧引用。代码示例中的引用不自动采用。
- 跨来源提交准备原 KnowledgeStore 的 source/evidence 变更，不拆分或制造 claim；答案留在原发布事务写入。本批准备函数不执行知识写入。
- 冻结报告保留正文引用位置、原 passage、来源及证据版本。失败调查可以形成真实 unresolved 报告，不制造来源。
- 本批尚未接通生产默认入口，也未发起模型请求。

验证：新增合同/归档测试及原 finding 相关测试 **20 passed, 2 deselected**；Ruff、`git diff --check` 通过。原 finding 文件的两项 shared-driver 测试在未修改的 `ca29a4ff` 独立 worktree 中同样失败（旧脚本提交字符串计划，随后 StopIteration），故单独记录，后续随新入口测试更新；没有把它们算作通过。未运行全量 pytest。

## 第二批：接通普通研究默认入口

- 新建的普通 strict research 使用完整任务与 `markdown + state`，取消强制计划、逐题、finding/采用手续。历史冻结合同仍按原 required_checks 与 scope 版本解码。
- 原 kernel 冻结材料标签与工具 schema，原 effect 记录提交；完成检查验证明确引用与原始阅读回执。正文不通过另一模型改写。
- 原发布事务原子保存所选 source/evidence 与唯一 answer；synthesis note 是原事务中的展示投影，不增加另一套提交/发布循环。不自动生成 claim。
- 发布证明绑定已结算 answer 的精确版本和报告摘要。普通缺口报告可交付；open_question 在 partial/unresolved 时仍保持未解决。
- 本批实现首次发布，未新增一般答案编辑接口。后续修改仍须通过原知识版本机制，不能编辑冻结提交或展示投影来改变正文权威。

验证：相关合同、读取复用、完成、队列和真实进程恢复测试 **145 passed**。其中新入口覆盖 JSON/native、错误引用修复、缺口交付，以及请求冻结、响应冻结、工具执行、kernel 结算、发布准入、知识提交、发布回执七个中断点；恢复不重复模型请求或知识写入。架构检查 **99 passed, 3 failed, 460 subtests passed**；三项失败均在未修改的 `ca29a4ff` 独立 worktree 复现（工具名单基线、已有超长文件、report_sections 非 stdlib 依赖），未放宽检查。本批仍未请求实机模型，离线通过不等于内容质量通过。

## 第三批：实机发现的任务丢失与测评检查

固定 `8e516e3f` 独立 worktree，运行 WAL/74/native。真实第二轮 payload 因原有历史裁剪仅保留最新工具组，原任务及整体指导不再出现。模型输出英文 WAL 概述，缺少用户要求的部分问题与证据边界；虽成功保存整篇答案，**不算内容通过**。另外旧 probe 仍要求 claim，导致发布后测评进程退出 1。该样本完整保留在 `.e2e-artifacts/research-whole-20261101/batch2-native/`，不得合并成修改后通过率。

- 完整原任务及整体提交指导现在从原会话单向投影到每轮冻结工作视图，覆盖 native 和 JSON；不依赖历史消息一定保留。
- 明确的分组引用 `[e1, e2]` 与 `[e1][e2]` 同样可解析；保留原正文位置，拒绝范围猜测与未知引用，不自动选择证据。
- 原测评 probe 对新合同检查唯一 answer、原提交/调查回执与精确 evidence，允许诚实缺口；旧 claim 合同仍使用原检查。内容评分继续独立。
- 两个矩阵 runner 在 worker 启动、每次推理前和样本结束校验源码/脚本身份。变化立即拒绝模型请求并停止矩阵。正式测评另外固定独立源码 worktree。

验证：合同/恢复/实际 API payload/旧 fixture **53 passed**，源码变更拦截与 held-out fixture **6 passed**。新增 payload 测试经实际 ApiProvider 历史裁剪路径，读取后与修复后均保留完整原任务。未运行全量 pytest。

## 第四批：扩大封闭材料对照范围（先冻结材料与评分）

- 同一比较 runner 现在接受额外固定 fixtures，并交给两个产品各自的原入口；没有为 Codey 增设代理循环或答案修补。
- 冻结九个扩展案例：已有 queue/tempfile/rlock 三组充分/邻近缺证据对照，以及新增跨来源导出规则、相同版本来源冲突、18858 字符长手册。三个新增案例明确标记为合成规范，不能当作真实产品资料。
- 扩展评分单独存放，不进入任务正文或材料读取接口。长手册的完成/到期条件位于 18000 字符之后，不能只读开头就通过。
- 源码守卫同时核对固定材料、协议及预算文件，防止同一矩阵中途改变条件。
- 预定先对九例各 seed 74 运行双方对照，必要时单列追加 seed。原 WAL/asyncio 六例仍用固定 `ff6cba12` worktree 继续，不能与其他实现混计。

验证：测评身份、材料一致性和旧 evidence fixture **26 passed**，Ruff 通过。本批只扩展测评设施，尚未把扩展案例视为已通过。

## 第五批：连贯阅读与一次原文呈现

`ff6cba12` 的 WAL/asyncio 六例都形成唯一整篇交付，每例三次推理；同时完成六例 OpenScience 同材料对照，逐例内容评阅另记。已观察到 WAL 三例都把跨 1000 字符边界的只读版本/条件引用到相邻片段；额外缺口和无依据机制也仍存在，不能把交付率直接当作内容通过率。

- 普通整篇研究按实际已读窗口中的 Markdown 章节分组；无章节时保留连贯窗口，PDF 仍不跨页。范围不越过原读取边界，旧逐题合同仍使用原片段规则。
- 当完整阅读结果已进入本轮冻结视图时，工具返回只呈现成功回执及引用标签；原文在工作视图中完整呈现一次。若有任何原段落未入选，则保留原工具正文，避免隐藏刚读的材料。
- 原阅读回执、来源版本、hash/offset 身份和重启恢复不变。此修改不替模型选择引用或判断语义；章节引用的粒度比旧 1000 字符片段粗，完整支持关系仍须人工核对。

验证：整篇合同、实际 API payload、恢复、旧 inline 与阅读复用 **95 passed**；Ruff 通过。实际 payload 测试验证原文只出现一次，未知/未呈现引用仍拒绝。

## 第六批：直接调用提交工具与正文权威保护

- `ff6cba12` 原始请求显示六例均先产生普通文本，再因合同要求重写成提交调用。新整篇 native 请求通过冻结的 `require_tool_call` 使用已有 API 的 `tool_choice=required`；模型仍自由选择读取、搜索、询问或提交，程序不替它指定答案或证据。选项仅作用于本次请求，不修改共享 provider；历史请求按原冻结参数恢复。
- 原 synthesis 展示快照绑定精确 answer 版本后，不允许通过 note 写入独立修改其正文。修改标题等元数据仍保持原版本绑定；显式知识修订产生同一 answer 的新版本，原交付快照保持原内容。首次发布也验证 note 正文与唯一 answer 一致。
- 第三批完整内容评阅保存到 `docs/reports/research-whole-batch3-20261101.json`：双方均交付 6/6，Codey 内容 1/6、OpenScience 6/6；双方各 18 次实际推理（OpenScience 含标题生成）。这是中间开发版本，不冒称已达到目标。第五批单例只证明章节引用改善，仍有错误扩写。

验证：原工具协议、整篇发布/恢复、请求选项和投影保护初轮 **61 passed**；校验位置整理后的相关组 **64 passed**；知识 authority/repository **8 passed**；新增冻结 native 选项恢复 **1 passed**。Ruff 通过。未运行全量 pytest。

## 第七批：将提交合同放回材料后的当前指令

第六批 WAL/74 实机请求确实发送了 `tool_choice=required`，但当前 KoboldCpp 第二轮仍输出普通文本，第三轮才提交。不能声称该服务器已强制执行该选项。

将每轮完整提交指导放到已读材料之后，明确下一步工具调用，以及按用户语言/问题顺序直接写入提交参数；缩短指导，并只要求说明任务中确实缺证据的点，不要求额外“缺口清单”。原工具/schema、effect 与正文权威没有新增分支。API required 选项继续用于支持它的后端，实际返回仍按原冻结合同校验。

验证：实际 API 工作视图与整篇合同 **23 passed**，Ruff 通过。九例 OpenScience 扩展对照已在固定 `c89bba02` 测评 worktree 开始；其 executable、问题/材料/预算与后续 Codey 对照保持一致，源码身份分别记录，不合并到同一实现矩阵。

## 第八批：让原问题紧邻生成位置

第七批六例均用两次实际推理交付，但仍有必要条件遗漏：asyncio 三例未明确说明父 gather 取消传播不受 return_exceptions 影响；WAL 存在复合问题只回答前半句等情况。因此两次交付只代表协议路径改善，不能代表内容验收通过。

将完整原任务逐字放到已读材料之后、提交指导之前；增加通用要求：复合问题各子句都要明确回答，判断题先给出直接结论或材料不足。没有加入案例答案、逐题 JSON、自动证据选择或额外模型审稿步骤。

验证：实际 API 工作视图与整篇合同 **23 passed**，相关 Ruff 通过。第八批实机结果单独记录，不与第七批合并。
