# 首次研究：新证据与结构化知识同事务提交

日期：2026-11-02。基线为 `020c302b`；候选分支为 `research/first-pass-knowledge-updates`。本轮只处理首次研究中新材料的结构化积累，不重新启用旧 finding 采用协议。

验证结论：最终版本完成八例实机交付，四例实际完成首次结构化积累；扩大回归和九组类型检查全部通过。本次提交保留首次积累的工程修复；知识草稿的严格语义验收未全部通过。本文分别记录工程接通、正文质量与知识草稿的语义限制，不把它们合并为正确率。

## 修改边界

`submit_research_answer` 新增可选的 `knowledge_updates`，最多 16 条。正文继续只引用已显示的 `[eN]`。模型不填写数据库 ID、版本、scope、origin 或 status。

知识条目包含 `key`、`kind`、`content`、`references`，可选 `title`、`aliases` 和 `conditions`：

- `claim.references` 填当前可见的证据字符串，例如 `["e1"]`；程序生成 supported_by。可用 `limited_by`、`refuted_by` 字符串列表保留限制或反证。
- `inference.references` 填全部前提，例如 `["limit", "e1"]`；程序生成 depends_on。
- `question.references` 填调查动机，程序生成 motivated_by。

key 可用 `k1`，也可用 `writer_limit` 等批次内名称；程序生成数据库身份。eN 名称保留给证据，不能被批次 key 覆盖。引用中的 `e1`、`[e1]` 按同一已显示证据解析，未知引用不会因此变成可读材料。批次 key 不是正文证据引用。未知目标、重复 key、非法关系、循环依赖、越权字段以及缺少原文证据引用的 claim 都拒绝整个提交。引用存在不证明语义支持。没有知识批次或显式空批次时，继续生成原 v1 提交与报告；非空批次使用 v2，旧报告读取保留。

```json
{
  "key": "consequence",
  "kind": "inference",
  "content": "此处填写基于原主张和原文的完整候选推论。",
  "references": ["limit", "e1"]
}
```

以上条目放在 submit 的 `knowledge_updates` 数组中；`limit` 须由同批另一条主张定义。模型只表达内容和依据，不填写关系枚举、提交 ID、数据库版本和存储权限。

## 原子发布与恢复

准备阶段按“正文引用与知识条目引用的并集”解析原始阅读窗口和历史精确版本，生成 source/evidence 的待提交变更。程序从冻结的提交、会话和提交回执生成新知识身份，按选中材料继承限制范围。混合不兼容的范围拒绝处理。

候选 claim 保留 `model_extraction` 来源；inference/question 为 `model_inference`。新条目保持 candidate，claim/inference 的语义审查状态仍为 unreviewed。程序不会从正文自动提炼主张，也不会把发布成功当作内容正确的证明。

这些知识下次仍作为历史线索读取。整篇回答需要沿依赖读取原 source/evidence 的精确版本取得 eN；新建候选条目不会自动成为下一篇答案的正式证据。

来源、证据、显式知识条目和唯一 answer 通过原 publication effect、原 `KnowledgeStore.publish_note()` 和同一个 SQLite 事务写入。本批知识在准备阶段不提前落库；事务失败不能只留下答案或部分知识。恢复使用冻结命令与原提交身份，不重新查询当前 head，不让模型重写知识批次。

只为知识条目保存的证据不会变成正文引用、答案的 uses 依赖或交付历史中的 cited evidence。相关候选知识仍通过知识仓库和图谱保留其真实依赖。

通用 `knowledge_commit` 保留用于已有存储对象的明确编辑，当前 eN 通过本次 submit 的可选批次处理。本轮没有增加通用历史对象修订合同，也没有后台自动提炼代理。

## 验证与实机验收

新增测试覆盖冷启动新材料、同批 claim/inference、条件保留、无提前写入、发布失败回滚、精确历史版本、限制范围、非法批次整体拒绝、冻结内容篡改拒绝以及七个真实进程中断位置的恢复。原整篇交付、旧局部协议、历史知识读取与跨会话修订继续回归。

最终版本扩大相关回归为 **829 passed、58 subtests passed**，耗时 603.65 秒，结果保存在 `slots-tests.xml`；这是相关测试选择集，不是全仓测试。此前 106 项定向及扩展测试、15 个子测试也通过。Ruff 和 diff whitespace 检查通过。最终源码的完整生产目录 582 个 Python 文件通过 Mypy、Pyrefly、ty 各自的 Python 3.11/3.12/3.13 检查，共九组，日志为 `slots-typechecks.txt`。Pyrefly 仍有既有的 35 项抑制与 80 条警告，未新增类型豁免。

第一轮扩大回归曾有两项材料哈希失败，原因是隔离工作树检出时的文件换行字节与既有冻结哈希不一致。恢复主工作区原始材料字节后重测通过；没有改写 rubric 或更新预期哈希。随后复核又补上了只为知识保存的证据与正文引用的展示区分，最终整批回归在这版源码上重新跑过。

实机使用既有 `research_framework_comparison` 驱动原 headless 入口。材料、评分条件、seed、预算在推理前固定；没有预填计划、预读材料或替代研究运行时。采用本机 Gemma4 12B、native tools、seed 74/75、temperature 0.3、top_p 0.9、最多 4096 输出 token、thinking 关闭，每例 6 次请求预算。

比较 Queue.join 和 SQLite WAL 只读条件两个主题，各有明确积累要求与普通答案对照。积累必须实际保存有精确证据依赖的候选 claim 和依赖该 claim 的候选 inference，并在另一会话检索到；正文声称“已保存”不算成功。按冻结材料和 rubric 逐条检查正文与知识条目，不调用受测 Gemma 给自己评分。

基线 Queue 两个 seed 都陷入不存在的证据目标引用修复，6 次请求后 no_progress。WAL seed 74 在第三次请求发生后端超时，用户重启后重测仍出现相同 HTTP 不返回、后端持续 busy 的情况。这两次保留为后端故障，不据此给版本内容评分。

用户第二次重启后先跑候选及普通对照，后端继续完成各批测试。三个候选按顺序冻结，运行期间没有改源码：

| 版本／材料集 | 正式交付 | 完成所要求的 claim→inference 积累 | 请求数 |
| --- | --- | --- | --- |
| A：Queue 积累，两 seed | 0/2 | 0/2 | 12 |
| B-final：初版严格 key 与关系对象，四例积累 | 2/4 | 1/4 | 20 |
| B-flexible：放宽批次 key 与方括号拼写，四例积累 | 2/4 | 1/4 | 17 |
| B-slots：引用字符串，程序确定关系，四例积累 | 4/4 | 4/4 | 8 |

| B-slots：四例普通对照 | 4/4 | 未要求，未自动生成 | 9 |

B-flexible 的两例 WAL 都存下 claim/inference，但其中一例推论只连证据，没有用户要求的主张前提，因而仅计 1/4。Queue 的失败来自模型把推论的证据关系写成 supported_by；把这种由 kind 决定的手续交给程序后，最终四例都用“读取一次、提交一次”完成。最终每例均只有一版来源、证据、claim、inference、answer，候选知识在另一会话按原措辞检索可召回。这里只证明该种召回，不证明跨主题改写检索能力提升。

四例普通正文的计数机制、SQLite 版本与三项 OR 条件均保留。Queue seed 75 出现一次原有 native 工具响应修复，总请求 8→9；后端报告的输入 token 从 26,218 增至 36,743，约增加 40.1%。这是新增工具合同和一次修复的成本，不能宣传成普通研究请求或 token 的全面下降。有效的 Queue 配对则由积累失败的 12 次请求变为完成积累的 4 次请求。

**知识语义限制仍然存在。** 最终四例的 conditions 字典均为空；WAL seed 75 的候选推论把“已有可读 shm/wal”等条件缩写为“如文件已存在”，省略了可读限定，完整正文及其精确证据仍保留该限定。按知识条目条件完整性的严格口径，该例不能计为通过，不能宣称预登记的“四例知识内容全部合格”已达到。工程接通为 4/4，知识草稿的严格条件审计为 3/4，正文为 4/4；这三项不是同一指标。

保留最终候选的依据是本轮要求的工程收益已经出现：首次材料能在原事务内积累明确候选知识，原文版本与依赖可追溯，普通交付仍完成。没有把不完整草稿升级为 active 或已验证结论；本轮不作为结构化知识内容质量或自主条件提炼能力的验收。跨来源、长文、新 seed 与长期跨主题使用仍需后续评估。
