# 12B 反例核验 Reviewer：隔离实验报告

日期：2026-10-11。结论：本轮候选没有显示净收益，不建议合入生产。结果说明这一实现尚不能可靠地产生可执行、有效的反例，不足以否定反例核验的方法，也不能证明它提升了未知任务的审核能力。

## 实验范围与控制

生产基线为 `4f0237e59ae505592ec479a92a5db42f43a2f68a`。模型为 KoboldCpp 的 `Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，仅访问 `127.0.0.1:5001`，没有使用 Zen、网页或外部 API。

预先固定种子 71/72、temperature 0.2、32,768 上下文、1,536 输出上限、12 个 Writer 轮次、每臂最多 24 次物理生成、240 秒期限。轮换比较臂的执行顺序，每臂使用独立项目、状态目录和聊天。没有依据结果修改提示、重抽种子或丢弃有效失败。

- 第一阶段：零边界、闭区间、大整数精确截断、缺失键默认值四类任务，各有错误及正确候选；16 个候选/种子，比较当前 Reviewer 与候选方法，共 32 臂。
- 第二阶段：预先指定的保留任务为精确整数截断和默认值合并；8 个候选/种子，比较关闭实际审核、当前 Reviewer、候选方法，共 24 臂。保留任务没有被用于调参；两阶段会重复这些冻结候选，不能当成两个独立样本。
- 全部候选为实验作者准备；生产工具真实安装同一个候选、运行可见测试，然后触发审核及修复。这不是自然 Writer 对自己刚生成代码的实验，不能外推为所有自我审核任务。

关闭审核只移除实际 `run_review` 调用，保留生产验证、回执、修复及完成生命周期，没有放宽完成门。可见测试刻意不足以区分错误和正确实现；隐藏验收及参考函数仅在比较臂结束后评分，没有出现在 Reviewer、Writer、修复提示或工作区中。

## 候选方法实际做了什么

实验子进程中的 Reviewer adapter 要求最多两条假设，携带原始要求引用、前提、JSON 参数、拟议期望值、错误解释及修复建议。固定 worker 在临时目录中执行冻结的同步 Python `select` 函数，记录返回值或异常、执行源码哈希及结束时哈希。

引用检查只证明原文存在，明确记录 `semantic_admission: unverified`。执行器不读取模型期望值，不计算“检查通过”，不执行模型提供的脚本或表达式。观察结束后，同一个 12B 重新判断并提交生产格式的审核结果。

因此，这一候选仍然依赖模型判断预期与前提是否成立；它没有完成通用、可信的自然语言依据准入。离线参考函数只能评分，不能成为在线 oracle。

执行权限只针对用户授权的合成实验 fixture，未增加生产工具或 Writer 命令权限。临时子进程不是操作系统安全沙箱，不适用于未经授权的任意项目。复制身份、别名及修改返回对象的性质不在本轮返回值观察范围。

## 第一阶段：发现与反例质量

| 指标 | 当前 Reviewer | 反例核验候选 |
|---|---:|---:|
| 缺陷候选数 | 8 | 8 |
| `changes_requested` | 6/8 | 4/8 |
| 人工核对后有效缺陷发现 | 5/8 | 4/8 |
| 正确候选误拒绝 | 0/8 | 0/8 |
| 审核不可用 | 2/16 | 1/16 |
| 服务端 input + output token | 17,438 | 46,943 |
| 总耗时 | 113.77 秒 | 169.97 秒 |

候选 token 多 169.2%，耗时多 49.4%。当前 Reviewer 的闭区间 seed 72 说 `range(start,end)` 在两者相等时返回 `[start]`，事实错误，虽然建议替换为 `range(start,end+1)` 恰好能修好缺陷。因此这条不计有效发现，不能用正确建议掩盖错误诊断。

候选实际执行了 5 个探针：4 个不满足任务输入域，另 1 个预期正确但没有区分力；有效、实测区分反例为 **0**。不能把“错误期望值计数为零”解读为推导能力可靠，因为有效探针太少。

典型问题：

- 零边界：提出 `select(5, low=0, high=10)`，返回 5。正确和错误实现都返回 5，不能证明零边界缺陷。最终意见可能发现真实问题，但这次观察没有提供证明。
- 闭区间：把参数名 `"start"`、`"end"` 当成实际 JSON 字符串；产生 TypeError 后又批准了存在相等端点缺陷的代码。
- 精确整数：经常提出小负数除法。这不能区分浮点截断和精确截断；真正的缺陷需要足够大的整数。另有把 `args` 写成对象、把 Python `None` 写入 JSON 的格式失败。
- 默认值：有探针只把参数写在前提文字里，实际 `args` 和 `kwargs` 都为空；缺参数异常不能证明业务缺陷。

原始探针、格式拒绝、观察与最终意见全部保存。无效探针没有被偷偷补全或升级为可信检查。

“合格补丁”还不是交付：需要正常结束、成功进程退出及可信 completion proof。隐藏验收不会替代 agent 自己的验证。

候选这一阶段 token 少 13.8%，但两次直接批准错误整数实现，没有进行必要修复。少工作和提前误完成不能算效率提升。关闭审核组没有模型生成请求；通用 usage 汇总把无请求标记为不完整，表中明确列为“无生成请求”，没有把供应商缺少 usage 伪装成零。

### 当前 Reviewer 的收益与问题

- 整数缺陷 seed 72：修复为精确符号处理，真实重新验证及当前审核通过，正常完成。
- 整数缺陷 seed 71：源码和新验证正确，但后续 Reviewer 错误声称 `-(-a // b)` 的负除数处理不正确，完成门阻塞。这是误拒绝，不是正确补丁交付成功。
- 正确整数候选 seed 72：首次审核请求改动，却在 finding 中承认“实现正确，无须修改”；后续重新审核放行。最终成功仍有额外成本。
- 两个默认值缺陷：初次审核与一次格式纠正都没有形成可解析的结果，错误候选仍沿既有无可用审核意见路径完成，记为两次误完成。日志显示非法 JSON 转义或未转义空字符串，不是 parser 将拒绝伪装为批准。

### 候选方法的收益与问题

- 两个默认值缺陷都被指出并修正，说明它并非完全没有发现能力。
- seed 71：补丁语义、范围及真实新验证通过，但模型用完轮次，缺正常完成和 proof。
- seed 72：补丁语义正确、测试通过，但 Writer 修改了任务禁止修改的 `test_app.py`，当前审核不完整，完成门阻塞。不能当成成功修复交付。
- 两个整数缺陷直接被批准，均产生误完成。
- 第二阶段实际执行的 3 个探针全部不符合函数调用前提，没有有效实测区分反例。

## 哪些原因可以归到哪里

**实验实现的限制**：新增自由 JSON 探针格式没有受约束生成；阶段一同时要求先交探针计划、后交原生产审核格式，增加小模型协议负担。第二次模型调用会增加成本，也可能放大无效观察的干扰。引用核对不是语义准入；本轮未隔离“提示变化”和“实际执行”的独立收益，也没有独立输出格式消融组。

**模型表现**：参数名代替实参、非区分输入、错误解释相等区间、对正确修复误拒绝、提出不必要更改、修复中改动禁止修改文件，以及没有提交完成动作。原始要求和实际观察不足以保证 12B 正确使用它们。

**生产策略边界**：初次不可用审核不等于审批通过，但既有流程可能在没有可用意见时完成；真实可见测试并不能证明未覆盖的语义要求。修复候选需要当前有效审核，因而会安全阻塞。这里记录结果，不修改策略，也不借实验授予新的 shell 命令权限。

三者会共同影响结果。不能把所有失败归因于模型，也不能把合成候选的所有失败都推断为生产内核 bug。

## 后续最值得独立验证的方向

1. 在实验里改用明确、受约束的函数调用数据结构，减少格式损失；单独测输出可靠性，别把收益冒认为语义提升。
2. 让模型给出具体、可能区分解释的输入；先核对实际函数绑定，不允许参数只存在于前提文字中。绑定合法仍不代表任务前提成立。
3. 保存“依据未核实”“观察不可用”“没有区分力”等状态，不能据此自动批准或强制修复。自然语言依据准入仍需单独验证。
4. 用新的预先固定任务检验方法，继续同时测正确候选、真实缺陷、修复、误拒绝、范围及完成成本。本轮不以继续调参直至赢为验收方式。

目前没有满足合入条件，生产仍保持原样。
