**浏览器直接入口与后续交付：自主实机消融实验，2026-11-13**

有收益。建议在已绑定页面、已有相应授权的浏览器任务中，逐项推进四个直接入口、填写后交付当前观察、点击后交付正式读取。后两项各自降低了成功完成相同任务的请求数和输入 token。额外的引用提示未显示稳定收益；只开放观察读取或只开放填写点击，均明显降低了本轮操作采用。

本次只新增[实验脚本](../tools/browser_followup_ab.py)、[测试](../tests/test_browser_followup_ab.py)和本报告，未修改生产代码、原有实验文件，也未创建分支或 worktree。以下为一个固定生产源码版本的结果，不能当作随后所有生产修改的验收。

**请求具体省在哪里。** 按原始提案和同轮正式回执分阶段，四入口基线是操作 22 次、旧引用及紧接的恢复 8 次、提交 12 次；组合是操作 16 次、恢复 0 次、提交 8 次。轨迹差异为少了 8 次引用相关往返、6 次模型单独发起的读取、4 次提前提交。

这里的观察和读取仍实际执行。基线与组合都产生 10 次成功观察、4 次成功填写、6 次成功点击和 6 次正式读取；页面实际有效点击也都是 6 次，每个交互单元一次。程序把必要后续步骤放进一次原执行链，减少模型往返；没有省略证据或重复点击。基线另有 4 次被拒的点击请求，组合没有这些请求。

两个“已有答案”单元在所有配置下都一次完成、无需操作。四入口首请求比 CodeMode 多 268/265 个输入 token；组合比四入口又多 121/130 个。直接显露与提示存在固定成本，收益主要出现在需要交互的任务中。

**模型编程负担。** CodeMode 组有 7 次模型编写 JavaScript 的提案，四入口和其余直接入口配置为 0。CodeMode 的改问备注任务出现一次明确的 `Result<T>` 解包合同错误：直接读取 `snapshot.elements`；随后三个执行回执出现将 `browser_read` 的字符串当对象访问 `dataRead.text.match(...)` 的错误。后一类属于普通 `execution_error`，未混计进脚本的窄口径 `result_contract_errors=1`。脚本保留所有原始提案与回执，便于区分提案次数和实际执行次数。

该失败单元还把换行写成了字面量反斜杠加 n，实际 textarea 值不符合用户要求，并出现三次旧引用点击拒绝。直接入口的备注单元均通过实际字段值校验。这是本轮可见的减负证据，样本不足以估计一般网站上的编程错误率。

**引用问题。** 当前生产代码已经从已提交的知识读取回执生成 `knowledge_refs` 选择；没有读取知识对象时不显露该字段。本轮所有配置都没有网页来源误填知识引用的提案，额外提示没有稳定收益，不建议再增加一层重复提示。机制测试另验证了原冻结合同拒绝网页来源冒充知识对象，包括存在真实知识选择的情况。

成功的交互单元均取得含正确结果的新正式 `browser_read` 正文，并引用该来源；没有把点击预览当成正式证据。全部实机仍使用来源级 `[sN]`，没有精确 passage 引用，因此不能声称模型已经绑定了某一个精确正文版本。字段值、页面有效点击、正式正文和最终引用分别校验。

**为什么两个精简组合反而失败。** 只显露观察读取时，六个交互单元都反复观察至 10 轮，未采用 CodeMode 完成动作。只显露填写点击时，六个交互单元都尝试无有效观察支持的引用，合计 18 次 `stale_ref` 拒绝，实际点击为零。它们的机制测试可以通过原 CodeMode 执行隐藏能力，但自主模型没有走通，不能用脚本化成功替代自主成绩。

**实验接线与架构边界。** 四入口是 `browser_snapshot`、`browser_fill`、`browser_click`、`browser_read`。每次请求仍从原 `build_turn_snapshot` 构建、保存、恢复，并核对授权、controller 限制、全部嵌套能力、定义和执行器没有变化。显露也尊重显式限制及已有简化输入绑定。

自动后续步骤仅对已通过原规范化的单个直接动作生效：实验把填写转换为“原填写＋原观察”，点击转换为“原点击＋原正式读取”的固定 CodeMode 程序，用户内容原样放在 `inputs` 中。生成的程序再通过原规范化，实际子动作由原 kernel、CodeMode、durable admission、回执及证据投影执行。没有新增工具注册、执行器、运行时、权限或完成判定。

交付从真实已提交子回执派生，不另存一份页面事实。自动步骤失败时保留动作成功与后续失败的区别；不自动重放动作，不静默替换旧引用，不注入预期答案。没有程序侧自动等待；模型自己在 CodeMode 中选择的等待仍按原实现计入。

**合入建议。** 四入口对本轮模型的操作采用有明确收益，可先用于已绑定页面、授权满足的浏览器任务。填写后交付当前观察和点击后交付正式读回均可作为独立小改动推进；正式读回优先限定在已有任务要求需要操作后正文的路径，避免对所有点击盲目增加读取。额外引用提示和两个精简入口组合暂不推荐。

生产实现应接入已有输入冻结、验证、转换、恢复和结果交付链，让固定转换也能在原请求恢复时重建；实验的进程补丁不直接成为生产实现。本轮验证了生产快照往返和原回执恢复，没有完成新增自动编排在进程崩溃后的端到端恢复验收。下一次生产改动也应继续从同一合同生成声明、沿原执行器和回执链交付。

**实验有效性与测试状态。** 正式模型为 `koboldcpp/Gemma4-12B-QAT-Uncensored-HauhauCS-Balanced-Q4_K_M`，temperature 0、seed `123456789`、非流式、文本 JSON Schema 协议，每请求输出预算 8192 token、超时 90 秒、每任务 10 轮。各任务轮转配置顺序，改问反向运行。全部实机自主选择入口，无固定首步。预先打开页面是两臂共同的正式 `open_url`，先于模型请求。

64 个单元、277 次 HTTP 请求的审计通过：任务输入逐字相同，授权和冻结执行定义相同，采样配置相同，无隐藏 HTTP 重试，无首次请求泄露业务结果码，分阶段请求与 token 总量能对齐。额外核对了首请求输出预算均为 8192，并复核全部成功交互答案。正式矩阵结束前源码与脚本摘要一致。
